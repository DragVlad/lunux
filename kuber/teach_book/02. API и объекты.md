# Лекция 02. API и объекты

На прошлой лекции мы разобрали, из чего состоит кластер и кто чем управляет. Теперь давай поговорим о том, как ты с этим кластером общаешься. А общаешься ты с ним через API — декларативно, описывая объекты. Понимание этой модели важнее заучивания команд, потому что команды меняются, а модель остаётся.

## API Kubernetes: не просто REST

API Kubernetes — это REST API. У каждого объекта есть URL, методы GET/POST/PUT/PATCH/DELETE. Но есть нюансы, которые отличают его от обычного REST.

**Ресурсы и версии.** Каждый тип объекта — это ресурс. Например, `pods`, `deployments`, `services`. У каждого ресурса есть группа (`apps`, `batch`, `networking.k8s.io`) и версия (`v1`, `v1beta1`). Полный путь выглядит так:

```
/apis/apps/v1/namespaces/default/deployments
```

Есть исключение — core-группа (Pod, Service, ConfigMap, Secret, Namespace) живёт без префикса группы:

```
/api/v1/namespaces/default/pods
```

**Почему версии важны.** Kubernetes развивается, и API меняется. Старые версии помечаются deprecated и в какой-то момент удаляются. Например, `extensions/v1beta1` для Ingress удалён в 1.22. Если твои манифесты используют старую версию — они перестанут применяться. Поэтому всегда проверяй актуальную версию API для своего кластера:

```bash
kubectl api-resources
kubectl explain deployment.spec
```

**Watch-механизм.** Помимо обычных GET, API умеет `watch` — долгоживущее соединение, по которому сервер шлёт события об изменениях объектов. На этом построена вся реактивность Kubernetes: контроллеры не опрашивают API каждую секунду, а подписываются на поток событий и реагируют на изменения. Это ключевая деталь: если ты пишешь свой контроллер или оператор — ты будешь использовать watch.

## kubectl: тонкая обёртка

`kubectl` — это CLI-клиент API-сервера. Он не делает ничего магического: формирует HTTP-запросы, отправляет их, красиво печатает ответы. Понимание этого помогает, когда что-то не работает: почти любую проблему kubectl можно воспроизвести через `curl` к API-серверу.

Базовые команды делятся на три категории.

**Императивные — для быстрых действий и экспериментов:**

```bash
kubectl run nginx --image=nginx           # создать Pod
kubectl create deployment web --image=nginx
kubectl expose deployment web --port=80
kubectl delete pod nginx
```

**Декларативные — для реальной работы:**

```bash
kubectl apply -f deployment.yaml          # создать или обновить
kubectl delete -f deployment.yaml
kubectl diff -f deployment.yaml           # показать, что изменится
```

**Информационные — для наблюдения:**

```bash
kubectl get pods                          # список
kubectl get pods -o wide                  # с доп. колонками
kubectl get pods -o yaml                  # полный YAML
kubectl describe pod nginx                # человекочитаемое описание
kubectl logs nginx                        # логи контейнера
kubectl exec -it nginx -- sh              # зайти внутрь
kubectl port-forward nginx 8080:80        # проброс порта
```

Запомни главное правило: **императивные команды — для обучения, декларативные манифесты — для работы**. Всё, что должно жить дольше пяти минут, описывается в YAML и хранится в git.

## Анатомия манифеста

Любой объект Kubernetes описывается в YAML. У всех объектов есть четыре обязательных поля верхнего уровня:

```yaml
apiVersion: apps/v1        # какая версия API
kind: Deployment           # какой тип объекта
metadata:                  # метаданные
  name: web
  namespace: default
  labels:
    app: web
spec:                      # желаемое состояние — тут самое важное
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:                # шаблон Pod'а
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
```

И отдельно — поле `status`, которое заполняет сам Kubernetes. Ты его не пишешь, ты его читаешь. Оно показывает текущее состояние объекта.

```
┌─────────────────────────────────────┐
│  spec      (ты пишешь)              │  ← желаемое
│  ────────────────────────────────   │
│  status    (Kubernetes пишет)       │  ← реальное
└─────────────────────────────────────┘
        reconciliation loop
        сводит status к spec
```

Это разделение spec/status — сердце декларативной модели. Ты описываешь spec, контроллеры приводят status к spec. Всё остальное — детали.

## Labels, Selectors, Annotations

Это три механизма метаданных, и их постоянно путают. Давай раз и навсегда.

### Labels

Пары ключ-значение, по которым объекты **группируются и выбираются**. Например:

```yaml
labels:
  app: web
  env: production
  version: v1.2.3
```

Labels — это то, на что ссылаются selectors. Они не для человека, они для машины.

### Selectors

Способ выбрать объекты по labels. Бывают двух видов.

**Equality-based** — простое совпадение:

```yaml
selector:
  matchLabels:
    app: web
    env: production
```

**Set-based** — более гибкий:

```yaml
selector:
  matchExpressions:
    - key: env
      operator: In
      values: [production, staging]
    - key: version
      operator: Exists
```

Selectors используются везде: Deployment выбирает свои Pod'ы, Service выбирает Pod'ы для балансировки, NetworkPolicy выбирает, к кому применять правила.

```
Deployment (selector: app=web)
        │
        │  находит Pod'ы с label app=web
        ▼
   ┌─────────┐  ┌─────────┐  ┌─────────┐
   │ Pod     │  │ Pod     │  │ Pod     │
   │app=web  │  │app=web  │  │app=web  │
   └─────────┘  └─────────┘  └─────────┘
```

Важно: selector в Deployment **неизменяемый** после создания. Если ошибёшься — придётся удалить и создать заново.

### Annotations

Тоже пары ключ-значение, но для другой цели. Annotations — это **метаданные для инструментов и людей**, а не для выбора объектов. По ним ничего не выбирается.

```yaml
annotations:
  description: "Main web application"
  prometheus.io/scrape: "true"
  prometheus.io/port: "9090"
  kubectl.kubernetes.io/last-applied-configuration: "..."
```

Ingress-контроллеры, Prometheus, ArgoCD, cert-manager — все они читают свои настройки из annotations. Это способ расширять поведение без изменения API.

**Правило запоминания:**

- **Labels** — для выбора. Короткие, структурированные, стабильные.
- **Annotations** — для информации. Длинные, свободные, для инструментов.

## Namespaces

Namespace — это логическое разделение кластера. Один физический кластер, но внутри — несколько виртуальных «подкластеров». Имена объектов уникальны внутри namespace, но могут повторяться в разных.

```
Кластер
├── namespace: default        ← сюда попадает всё, если не указать явно
├── namespace: kube-system    ← системные компоненты
├── namespace: kube-public    ← публичные данные (cluster-info)
├── namespace: kube-node-lease ← lease-объекты для heartbeat узлов
├── namespace: production
└── namespace: staging
```

Что дают namespaces:

- **Изоляция имён.** Два Deployment с именем `web` могут спокойно жить в `production` и `staging`.
- **Разграничение доступа.** RBAC-роли можно выдать только на конкретный namespace — пользователь видит и меняет только своё.
- **ResourceQuota и LimitRange.** Можно ограничить суммарные ресурсы namespace.
- **Удобная уборка.** `kubectl delete namespace staging` сносит всё содержимое.

**Важное ограничение.** Namespaces **не изолируют сеть** сами по себе. Pod'ы в разных namespace видят друг друга по умолчанию. Для сетевой изоляции нужны NetworkPolicy. Это частая ошибка новичков: думать, что namespace = безопасность. Нет, namespace = организация и RBAC, а сеть — отдельно.

Также не все объекты живут в namespace. Nodes, PersistentVolumes, StorageClasses, ClusterRoles, Namespace'ы — они cluster-scoped, у них нет поля `namespace`.

## Как объекты связаны между собой

В Kubernetes объекты не ссылаются друг на друга жёсткими ID. Вместо этого используется **связывание через labels и selectors**, и это делает систему гибкой.

```
Deployment (selector: app=web, version=v1)
        │
        │ создаёт
        ▼
ReplicaSet (selector: app=web, version=v1)
        │
        │ создаёт
        ▼
Pod'ы (labels: app=web, version=v1)
        ▲
        │ выбирает
Service (selector: app=web)
```

Обрати внимание: Service не знает, какой Deployment его создал. Он просто выбирает все Pod'ы с меткой `app=web`. Если ты добавишь ещё один Deployment с такой же меткой — Service начнёт балансировать и на его Pod'ы тоже. Это одновременно и мощно, и опасно: неаккуратные labels могут привести к неожиданному поведению.

Именно поэтому labels — это контракт. Меняешь labels — проверь, кто на них ссылается через selectors.

## Практический совет: declarative workflow

Когда ты работаешь с Kubernetes всерьёз, рабочий процесс выглядит так:

1. Пишешь YAML в git-репозитории.
2. `kubectl apply -f .` — применяешь.
3. `kubectl diff -f .` перед изменениями — смотришь, что изменится.
4. `kubectl get` и `kubectl describe` — проверяешь статус.
5. Никогда не редактируешь объекты через `kubectl edit` в production — иначе git и кластер разойдутся.

`kubectl edit` полезен для экспериментов, но он ломает декларативность: твои изменения не попадут в git, а следующий `apply` их перезапишет. В production правда живёт в git, а не в кластере.

## Что запомнить

1. **API — REST с версиями и watch.** Всё общение идёт через API-сервер, контроллеры подписаны на watch.

2. **Манифест = apiVersion + kind + metadata + spec.** spec — твоё желаемое, status — реальное, контроллеры сводят одно к другому.

3. **Labels — для выбора, annotations — для информации.** Selectors связывают объекты без жёстких ссылок.

4. **Namespace — это организация и RBAC, а не сетевая изоляция.** Сеть изолируется отдельно.
