# Устройство кластера

На прошлой лекции мы разобрались, зачем нужен Kubernetes и что такое декларативность. Теперь давай заглянем внутрь и поймём, из чего состоит кластер. Это фундамент: если ты не понимаешь, кто чем управляет, дальше всё будет казаться магией.

## Control Plane: мозг кластера

Control Plane — это набор процессов, которые принимают решения. Он не запускает твои контейнеры. Он решает *что* должно быть запущено, *где* и *когда*. Давай разберём каждый компонент.

### API Server

Это центральная точка входа. Абсолютно всё в кластере общается через него — `kubectl`, kubelet на узлах, scheduler, контроллеры, операторы, твои CI/CD пайплайны. API-сервер — это HTTP/REST-сервер, который принимает запросы на чтение и изменение объектов.

Важно понять: API-сервер не хранит состояние сам. Он — это валидатор и посредник. Когда ты говоришь «создай Deployment», API-сервер проверяет, что объект корректный, применяет к нему admission-контроллеры (об этом позже), и записывает его в etcd. Когда кто-то спрашивает «покажи мне все Pod'ы» — API-сервер читает их из etcd и отдаёт.

```
kubectl ──► API Server ──► etcd
              (валидация,
               авторизация)
```

Почему всё через один компонент? Потому что так проще обеспечить согласованность. Есть одно место, где проверяются права (RBAC), где валидируются схемы, где можно поставить аудит. Если бы каждый компонент лез в etcd напрямую — был бы хаос.

### etcd

Это распределённое key-value хранилище. Единственный источник правды о состоянии кластера. Всё, что ты создаёшь — Pod'ы, Service'ы, Secret'ы, конфиги — лежит там в виде пар ключ-значение.

etcd использует алгоритм консенсуса Raft, поэтому его запускают в нечётном количестве экземпляров (обычно 3 или 5), чтобы пережить падение одного-двух узлов. Потеря etcd без бэкапа = потеря кластера. Это не преувеличение. Все объекты, все секреты, всё состояние — только там.

Запомни важное правило: **etcd — это не база данных для приложений**. Это база для состояния самого Kubernetes. Не надо туда лазить руками.

### Scheduler

Когда создаётся новый Pod, он сначала появляется в etcd в статусе `Pending` — то есть «я есть, но ещё ни на каком узле не запущен». Scheduler смотрит на такие Pod'ы и решает, на какой worker-узел их посадить.

Как он принимает решение? В два этапа.

**Фильтрация (Filtering).** Scheduler отбрасывает узлы, которые физически не подходят: где не хватает CPU или памяти под запросы Pod'а, где не совпадают nodeSelector/affinity, где стоят taints, которые Pod не терпит.

**Приоритизация (Scoring).** Из оставшихся узлов выбирается лучший по баллам: где меньше загрузка, где уже есть нужный образ, где Pod'ы того же приложения — чтобы равномерно распределить нагрузку.

```
Новый Pod (Pending)
        │
        ▼
┌───────────────────┐
│   Scheduler       │
│                   │
│  1. Filter        │  ← отбросить неподходящие узлы
│  2. Score         │  ← отсортировать оставшиеся
│  3. Bind          │  ← назначить лучший
└─────────┬─────────┘
          │
          ▼
Pod привязан к Node ──► kubelet на этом узле запускает контейнеры
```

Scheduler ничего не запускает сам. Он только записывает в объект Pod поле `spec.nodeName`. Дальше за дело берётся kubelet на выбранном узле.

### Controller Manager

Это, пожалуй, самый интересный компонент с точки зрения идеологии Kubernetes. Controller Manager — это набор контроллеров, каждый из которых реализует свой *reconciliation loop*.

Вспомни идею декларативности: ты описываешь желаемое состояние, система приводит реальное к желаемому. Контроллер — это и есть та самая «система» для конкретного типа объектов.

Примеры контроллеров:

- **Deployment Controller** следит, чтобы число реплик соответствовало указанному. Упал Pod — создаёт новый.
- **ReplicaSet Controller** — то же самое, но на уровень ниже (Deployment управляет ReplicaSet'ами, а те — Pod'ами).
- **Node Controller** следит за здоровьем узлов. Узел перестал отвечать — помечает его NotReady и эвакуирует Pod'ы.
- **Endpoint Controller** обновляет список IP-адресов Pod'ов, стоящих за Service'ом.
- **ServiceAccount Controller**, **Namespace Controller**, **Job Controller** и десятки других.

Общая схема любого контроллера:

```
        ┌──────────────────────────────┐
        │      Reconciliation Loop     │
        │                              │
        │  ┌────────────────────────┐  │
        │  │ 1. Прочитать желаемое  │  │
        │  │    (spec объекта)      │  │
        │  └───────────┬────────────┘  │
        │              │               │
        │  ┌───────────▼────────────┐  │
        │  │ 2. Прочитать реальное  │  │
        │  │    (status объекта)    │  │
        │  └───────────┬────────────┘  │
        │              │               │
        │  ┌───────────▼────────────┐  │
        │  │ 3. Если не совпадает — │  │
        │  │    сделать действие    │  │
        │  └───────────┬────────────┘  │
        │              │               │
        │              └────► повтор   │
        └──────────────────────────────┘
```

Контроллеры не «создают Pod'ы» в императивном смысле. Они видят, что «должно быть 3 Pod'а, а есть 2», и создают третий через API-сервер. Потом снова смотрят. И снова. Это бесконечный цикл, который и даёт Kubernetes его устойчивость.

## Worker Node: руки кластера

Теперь про узлы, где реально живут контейнеры. На каждом worker-узле работают три ключевых компонента.

### kubelet

Это агент, который живёт на каждом узле и общается с API-сервером. Его работа — следить, чтобы на узле были запущены те Pod'ы, которые ему назначены.

kubelet не запускает контейнеры сам. Он получает от API-сервера список Pod'ов для своего узла, и для каждого обращается к контейнерному рантайму через CRI (Container Runtime Interface) — стандартный gRPC-интерфейс. «Запусти мне контейнер из такого-то образа с такими-то параметрами». Рантайм запускает, kubelet следит за состоянием, сообщает статус обратно в API-сервер.

Схема:

```
API Server ◄────► kubelet ──CRI──► containerd ──► контейнер
                    │
                    ├─ следит за Pod'ами на узле
                    ├─ запускает/останавливает контейнеры
                    ├─ выполняет probes (liveness/readiness)
                    ├─ монтирует volumes
                    └─ сообщает статус в API
```

Если kubelet умрёт — узел перестанет получать новые Pod'ы и обновлять статусы. Через какое-то время Node Controller пометит его NotReady и начнёт эвакуацию.

### kube-proxy

Отвечает за сетевые правила на узле. Когда ты создаёшь Service типа ClusterIP, у него есть виртуальный IP. Кто-то должен сделать так, чтобы пакеты, отправленные на этот IP, попадали на реальный Pod. Этим и занимается kube-proxy.

Он работает в одном из режимов — обычно `iptables` или `ipvs`. В режиме iptables он прописывает правила в ядре Linux: «трафик на 10.96.0.10:80 → раскидать по этим трём Pod'ам: 10.244.1.5, 10.244.2.7, 10.244.3.9». Балансировка происходит на уровне ядра, максимально быстро.

```
Клиент ──► Service IP (10.96.0.10)
                  │
                  ▼
           ┌──────────────┐
           │  kube-proxy  │  ← правила iptables/ipvs
           └──────┬───────┘
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     Pod 1     Pod 2     Pod 3
```

Важно: kube-proxy не проксирует трафик в классическом смысле (не гоняет пакеты через себя). Он настраивает правила, по которым ядро само перенаправляет пакеты. Поэтому это не bottleneck.

### Container Runtime

Это тот самый CRI-совместимый рантайм, который реально запускает контейнеры. Сейчас стандарт — `containerd` (выделился из Docker) или `CRI-O` (сделан Red Hat специально для Kubernetes).

Рантайм занимается низкоуровневыми вещами: скачивает образы, создаёт namespaces и cgroups, запускает процессы, монтирует файловые системы. kubelet даёт ему команды через CRI, рантайм их выполняет.

## Три интерфейса: CRI, CNI, CSI

Kubernetes намеренно сделан расширяемым. Вместо того чтобы жёстко зашить конкретные реализации, он определяет стандартные интерфейсы, и любой может подключить свою. Это одна из главных причин, почему Kubernetes победил.

### CRI — Container Runtime Interface

Отвечает за запуск контейнеров. Любой рантайм, реализующий CRI, может быть использован в Kubernetes. Поэтому Docker как рантайм ушёл — он не реализовывал CRI напрямую, а работал через прослойку `dockershim`, которую в итоге удалили.

### CNI — Container Network Interface

Отвечает за сеть. Когда создаётся Pod, CNI-плагин выделяет ему IP-адрес и настраивает сетевые маршруты так, чтобы Pod'ы на разных узлах видели друг друга напрямую, без NAT.

Примеры CNI-плагинов: Calico, Cilium, Flannel, Weave. Выбор CNI — важное решение при установке кластера, потому что от него зависит производительность сети, поддержка NetworkPolicy, eBPF-ускорение и многое другое.

Схема:

```
Новый Pod создан
        │
        ▼
kubelet ──► CNI plugin ──► выдал IP, настроил маршруты
                                │
                                ▼
                        Pod получил сеть
```

### CSI — Container Storage Interface

Отвечает за хранилище. Когда Pod'у нужен volume, CSI-драйвер монтирует его. Разные CSI-плагины умеют работать с разными бэкендами: локальный диск, AWS EBS, GCP Persistent Disk, Ceph, NFS, любые СХД.

```
Pod запрашивает PVC
        │
        ▼
StorageClass ──► CSI driver ──► создал и примонтировал volume
```

Эта тройка интерфейсов — причина, по которой Kubernetes не привязан ни к одному вендору. Ты можешь собрать кластер из чего угодно: любой рантайм, любая сеть, любое хранилище. Главное — чтобы реализовывали стандартный интерфейс.

## Как всё это работает вместе: путь Pod'а

Давай проследим путь Pod'а от твоего `kubectl apply` до запущенного контейнера. Это лучший способ закрепить понимание.

```
1. Ты: kubectl apply -f deployment.yaml
        │
        ▼
2. kubectl ──► API Server (проверка прав, валидация)
        │
        ▼
3. API Server ──► etcd (сохранил Deployment)
        │
        ▼
4. Deployment Controller видит новый Deployment
   ──► создаёт ReplicaSet
        │
        ▼
5. ReplicaSet Controller видит новый ReplicaSet
   ──► создаёт Pod'ы (в статусе Pending)
        │
        ▼
6. Scheduler видит Pending Pod'ы
   ──► выбирает узлы, записывает spec.nodeName
        │
        ▼
7. kubelet на выбранном узле видит «свой» Pod
   ──► через CRI говорит containerd запустить контейнер
        │
        ▼
8. containerd ──► скачал образ, запустил контейнер
        │
        ▼
9. CNI плагин ──► выдал Pod'у IP, настроил сеть
        │
        ▼
10. kubelet ──► сообщил статус Running в API Server
        │
        ▼
11. API Server ──► записал статус в etcd
```

Обрати внимание: между шагами 3 и 9 нет ни одной императивной команды «запусти контейнер здесь». Всё построено на том, что компоненты наблюдают за объектами в API-сервере и реагируют на изменения. Это и есть декларативная модель в действии.

## Что запомнить

Три главных тезиса этой лекции:

1. **Control Plane принимает решения, worker nodes их исполняют.** API Server — точка входа, etcd — хранилище правды, Scheduler выбирает узел, Controller Manager поддерживает желаемое состояние.

2. **kubelet — агент на узле, kube-proxy — сеть на узле, containerd — рантайм на узле.** Три компонента, каждый со своей задачей.

3. **CRI, CNI, CSI — интерфейсы расширения.** Благодаря им Kubernetes не привязан к конкретным рантаймам, сетям и хранилищам.
- Зачем нужны CRI, CNI и CSI? Что было бы, если бы их не было?

Если можешь ответить на эти вопросы своими словами — ты понял устройство кластера. На следующей лекции разберём API и объекты: как устроены манифесты, что такое labels и selectors, и почему namespaces — это не то же самое, что Linux namespaces.
