# 01. Эксплуатация кластера: upgrade, etcd backup/restore, сертификаты

Мы научились разворачивать приложения, настраивать сеть, хранилища, безопасность. Но кластер — это живой организм. Его нужно **обновлять**, **резервировать** и **защищать сертификатами**. В этой лекции разберём эксплуатацию кластера.

> **Эксплуатация кластера** — это не разовая настройка, а непрерывный процесс: обновления, бэкапы, ротация сертификатов, мониторинг.

---

## Часть 1: Обновление кластера (Upgrade)

> **Upgrade** — обновление версии Kubernetes. Требует планирования и осторожности.

### Версионирование Kubernetes

Формат: `vMAJOR.MINOR.PATCH`

```
v1.28.3
 │  │  │
 │  │  └── Patch (багфиксы, security)
 │  └───── Minor (новые фичи, 3 раза в год)
 └──────── Major (breaking changes, редко)
```

**Правило:** обновляться можно только на **одну minor-версию** за раз.

```
v1.27 → v1.28 ✅
v1.27 → v1.29 ❌ (нужно через v1.28)
```

### Порядок обновления

1. **Control Plane** (по одному узлу).
2. **Worker Nodes** (по одному узлу).
3. **kubelet** на каждом узле.
4. **kubectl** (можно обновить заранее).

### Стратегии обновления

| Стратегия | Описание |
|-----------|----------|
| **In-place** | Обновление на месте (kubeadm upgrade) |
| **Blue-Green** | Новый кластер, переключение трафика |
| **Rolling** | По одному узлу (kubeadm) |

### Обновление через kubeadm

**Шаг 1: Проверить текущую версию**

```bash
kubectl version --short
kubeadm version
kubelet --version
```

**Шаг 2: Прочитать release notes**

```bash
# Проверить deprecated API
kubectl deprecations --k8s-version=v1.29
# Или
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis
```

**Шаг 3: Обновить kubeadm**

```bash
# Debian/Ubuntu
apt-mark unhold kubeadm
apt-get update && apt-get install -y kubeadm=1.29.0-1.1
apt-mark hold kubeadm

# RHEL/CentOS
yum install -y kubeadm-1.29.0-0
```

**Шаг 4: Проверить план обновления**

```bash
kubeadm upgrade plan
```

**Шаг 5: Обновить Control Plane (по одному узлу)**

```bash
# На первом control-plane узле
kubeadm upgrade apply v1.29.0

# На остальных control-plane узлах
kubeadm upgrade node
```

**Шаг 6: Drain узел**

```bash
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
```

**Шаг 7: Обновить kubelet и kubectl**

```bash
apt-mark unhold kubelet kubectl
apt-get update && apt-get install -y kubelet=1.29.0-1.1 kubectl=1.29.0-1.1
apt-mark hold kubelet kubectl

# Перезапустить kubelet
systemctl daemon-reload
systemctl restart kubelet
```

**Шаг 8: Uncordon узел**

```bash
kubectl uncordon <node>
```

**Шаг 9: Повторить для всех узлов**

### Проверка после обновления

```bash
kubectl get nodes
kubectl version --short
kubectl get pods -A
kubectl get --raw='/readyz?verbose'
```

### Обновление managed Kubernetes

| Провайдер | Как обновить |
|-----------|--------------|
| **EKS** | `eksctl upgrade cluster` или через консоль |
| **GKE** | Автоматически или через консоль |
| **AKS** | `az aks upgrade` или через консоль |

> [!note]
> В managed Kubernetes Control Plane обновляется провайдером. Вы обновляете только worker nodes.

### Best practices для upgrade

| Практика | Почему |
|----------|--------|
| Backup etcd перед обновлением | Откат при проблемах |
| Тестировать на staging | Не сломать production |
| Обновлять по одной minor | Требование Kubernetes |
| Читать release notes | Breaking changes |
| Проверять deprecated API | Могут перестать работать |
| Drain узлы | Не потерять Pod |
| Обновлять в maintenance window | Минимизировать downtime |
| Мониторить после обновления | Раннее обнаружение проблем |

## Часть 2: Backup и Restore etcd

> **etcd** — единственный источник правды. Потеря etcd = потеря кластера.

### Что хранится в etcd

- Все объекты Kubernetes (Pod, Service, Deployment).
- Secrets (зашифрованные, если настроено).
- Состояние кластера.
- RBAC.
- CRD и CR.

### Стратегия бэкапов

| Тип | Описание |
|-----|----------|
| **Snapshot** | Полный снимок etcd |
| **Velero** | Бэкап объектов + PV |
| **etcdctl snapshot** | Встроенный механизм |

### Backup etcd через etcdctl

**Шаг 1: Установить etcdctl**

```bash
# Debian/Ubuntu
apt install etcd-client

# Или скачать
ETCD_VER=v3.5.10
curl -L https://github.com/etcd-io/etcd/releases/download/${ETCD_VER}/etcd-${ETCD_VER}-linux-amd64.tar.gz -o etcd.tar.gz
tar xzvf etcd.tar.gz
sudo mv etcd-${ETCD_VER}-linux-amd64/etcdctl /usr/local/bin/
```

**Шаг 2: Создать snapshot**

```bash
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot-$(date +%Y%m%d-%H%M%S).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

**Шаг 3: Проверить snapshot**

```bash
ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-snapshot.db \
  --write-out=table
```

**Пример вывода:**

```
+----------+----------+------------+------------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE |
+----------+----------+------------+------------+
| 3a5b8c7d |   123456 |       1234 |     45 MB  |
+----------+----------+------------+------------+
```

### Restore etcd

**Шаг 1: Остановить API-сервер и etcd**

```bash
# Для kubeadm
mv /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/
mv /etc/kubernetes/manifests/etcd.yaml /tmp/
```

**Шаг 2: Восстановить snapshot**

```bash
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot.db \
  --data-dir=/var/lib/etcd-restore \
  --initial-cluster=master-1=https://192.168.1.10:2380 \
  --initial-advertise-peer-urls=https://192.168.1.10:2380 \
  --name=master-1
```

**Шаг 3: Заменить data-dir**

```bash
mv /var/lib/etcd /var/lib/etcd-backup
mv /var/lib/etcd-restore /var/lib/etcd
chown -R etcd:etcd /var/lib/etcd
```

**Шаг 4: Вернуть манифесты**

```bash
mv /tmp/kube-apiserver.yaml /etc/kubernetes/manifests/
mv /tmp/etcd.yaml /etc/kubernetes/manifests/
```

**Шаг 5: Проверить**

```bash
kubectl get nodes
kubectl get pods -A
```

### Автоматизация бэкапов

**CronJob для бэкапа etcd:**

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: etcd-backup
  namespace: kube-system
spec:
  schedule: "0 */6 * * *"          # каждые 6 часов
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          nodeSelector:
            node-role.kubernetes.io/control-plane: ""
          tolerations:
            - key: node-role.kubernetes.io/control-plane
              operator: Exists
              effect: NoSchedule
          hostNetwork: true
          containers:
            - name: etcd-backup
              image: bitnami/etcd:3.5
              command:
                - /bin/sh
                - -c
                - |
                  etcdctl snapshot save /backup/etcd-$(date +%Y%m%d-%H%M%S).db \
                    --endpoints=https://127.0.0.1:2379 \
                    --cacert=/etc/kubernetes/pki/etcd/ca.crt \
                    --cert=/etc/kubernetes/pki/etcd/server.crt \
                    --key=/etc/kubernetes/pki/etcd/server.key
                  # Удалить старые бэкапы (> 7 дней)
                  find /backup -name "etcd-*.db" -mtime +7 -delete
              volumeMounts:
                - name: etcd-certs
                  mountPath: /etc/kubernetes/pki/etcd
                  readOnly: true
                - name: backup
                  mountPath: /backup
          volumes:
            - name: etcd-certs
              hostPath:
                path: /etc/kubernetes/pki/etcd
            - name: backup
              hostPath:
                path: /backup/etcd
          restartPolicy: OnFailure
```

### Velero: бэкап объектов и PV

> **Velero** — бэкап и восстановление объектов Kubernetes и PersistentVolume.

**Установка:**

```bash
# CLI
brew install velero
# или
curl -L https://github.com/vmware-tanzu/velero/releases/latest/download/velero-v1.12.0-linux-amd64.tar.gz | tar xz
sudo mv velero-v1.12.0-linux-amd64/velero /usr/local/bin/

# Сервер
velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:v1.8.0 \
  --bucket my-velero-bucket \
  --secret-file ./credentials-velero \
  --backup-location-config region=us-east-1 \
  --snapshot-location-config region=us-east-1
```

**Создать бэкап:**

```bash
# Все namespace
velero backup create my-backup

# Конкретный namespace
velero backup create my-backup --include-namespaces production

# С расписанием
velero schedule create daily-backup --schedule="0 3 * * *"
```

**Восстановить:**

```bash
velero restore create --from-backup my-backup
velero restore create --from-backup my-backup --include-namespaces production
```

**Проверка:**

```bash
velero backup get
velero restore get
velero backup describe my-backup
```

### Best practices для etcd

| Практика | Почему |
|----------|--------|
| Backup каждые 6-24 часа | RPO |
| Хранить вне кластера | Если кластер упал |
| Тестировать restore | Backup без restore бесполезен |
| Шифровать бэкапы | Secrets в etcd |
| Мониторить размер etcd | Растёт → проблемы |
| Defrag etcd | Освободить место |
| Multi-node etcd | 3 или 5 узлов |

### Defrag etcd

```bash
ETCDCTL_API=3 etcdctl defrag \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

## Часть 3: Сертификаты

> **Сертификаты** — основа безопасности Kubernetes. Все компоненты общаются по TLS.

### Компоненты TLS

| Компонент | Сертификат |
|-----------|------------|
| **kube-apiserver** | Server cert, client cert (etcd, kubelet) |
| **etcd** | Server cert, peer cert, client cert |
| **kubelet** | Server cert, client cert (apiserver) |
| **kube-controller-manager** | Client cert (apiserver) |
| **kube-scheduler** | Client cert (apiserver) |
| **kubectl** | Client cert |
| **ServiceAccount** | JWT tokens |

### Расположение сертификатов

```
/etc/kubernetes/pki/
├── apiserver.crt
├── apiserver.key
├── apiserver-kubelet-client.crt
├── apiserver-kubelet-client.key
├── ca.crt
├── ca.key
├── front-proxy-ca.crt
├── front-proxy-ca.key
├── front-proxy-client.crt
├── front-proxy-client.key
├── sa.key
├── sa.pub
└── etcd/
    ├── ca.crt
    ├── ca.key
    ├── server.crt
    ├── server.key
    ├── peer.crt
    ├── peer.key
    ├── healthcheck-client.crt
    └── healthcheck-client.key
```

### Обновление сертификатов

**kubeadm:**

```bash
# Обновить все сертификаты
kubeadm certs renew all

# Обновить конкретный
kubeadm certs renew apiserver

# Перезапустить компоненты
systemctl restart kubelet
# Для static pods — пересоздать манифесты
```

**Вручную:**

```bash
# Проверить срок
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -dates

# Создать CSR
openssl req -new -key apiserver.key -out apiserver.csr -config openssl.cnf

# Подписать
openssl x509 -req -in apiserver.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out apiserver.crt -days 365 -extensions v3_ext -extfile openssl.cnf
```

### cert-manager: автоматизация

> **cert-manager** — автоматическое управление TLS-сертификатами в Kubernetes.

**Установка:**

```bash
helm repo add jetstack https://charts.jetstack.io
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set installCRDs=true
```

**ClusterIssuer (Let's Encrypt):**

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@example.com
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
      - http01:
          ingress:
            class: nginx
```

**Certificate:**

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: my-app-tls
  namespace: default
spec:
  secretName: my-app-tls-secret
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  dnsNames:
    - app.example.com
    - www.app.example.com
```

**Ingress с автоматическим TLS:**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: my-app-tls-secret
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: my-app
                port:
                  number: 80
```

**Что произойдёт:**
1. cert-manager увидит Ingress с аннотацией.
2. Создаст Certificate.
3. Запросит сертификат у Let's Encrypt.
4. Сохранит в Secret.
5. Ingress Controller использует Secret.

### Внутренние сертификаты через cert-manager

**Self-signed Issuer:**

```yaml
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: selfsigned-issuer
  namespace: default
spec:
  selfSigned: {}
```

**CA Issuer:**

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: my-ca-issuer
spec:
  ca:
    secretName: my-ca-key-pair
```

### Ротация сертификатов

| Сертификат | Срок | Ротация |
|------------|------|---------|
| kubeadm | 1 год | `kubeadm certs renew` |
| cert-manager | 90 дней (Let's Encrypt) | Автоматически |
| ServiceAccount | 1 год | Автоматически |
| Внутренние CA | 10 лет | Вручную |

> [!important]
> **Проверяйте срок действия сертификатов.** Просроченный сертификат API-сервера = кластер недоступен.

### Мониторинг сертификатов

**Prometheus правила:**

```yaml
groups:
  - name: certificates
    rules:
      - alert: CertificateExpiringSoon
        expr: |
          certmanager_certificate_expiration_timestamp_seconds - time() < 86400 * 30
        for: 1h
        labels:
          severity: warning
        annotations:
          summary: "Certificate {{ $labels.name }} expires in 30 days"
```

**kubeadm сертификаты:**

```bash
# Скрипт для проверки
kubeadm certs check-expiration | grep -v "CERTIFICATE AUTHORITY"
```

**Ключевые алерты:**

```yaml
- alert: KubeAPIServerDown
  expr: up{job="kube-apiserver"} == 0
  for: 5m
  labels:
    severity: critical

- alert: EtcdNoLeader
  expr: etcd_server_has_leader == 0
  for: 1m
  labels:
    severity: critical

- alert: NodeNotReady
  expr: kube_node_status_condition{condition="Ready",status="true"} == 0
  for: 5m
  labels:
    severity: critical

- alert: PodCrashLooping
  expr: rate(kube_pod_container_status_restarts_total[15m]) > 0
  for: 15m
  labels:
    severity: warning
```

## Troubleshooting

### etcd не запускается после restore

**Причины:**
- Неверные права на data-dir.
- Неверные флаги.
- Конфликт с существующим etcd.

**Решение:**

```bash
chown -R etcd:etcd /var/lib/etcd
journalctl -u etcd -f
```

### Сертификат просрочен

```
x509: certificate has expired or is not yet valid
```

**Решение:**

```bash
kubeadm certs renew all
systemctl restart kubelet
```

### Upgrade застрял

**Причины:**
- Недостаточно места.
- Неверная версия.
- Проблемы с сетью.

**Решение:**

```bash
kubeadm upgrade plan
kubeadm upgrade apply v1.29.0 --force
journalctl -u kubelet -f
```

### Node NotReady после upgrade

**Причины:**
- kubelet не запустился.
- Несовместимость версий.
- Проблемы с CNI.

**Решение:**

```bash
systemctl status kubelet
journalctl -u kubelet -f
kubectl describe node <node>
```

### Velero backup fails

**Причины:**
- Нет доступа к S3.
- Неверные credentials.
- Нет snapshot support.

**Решение:**

```bash
velero backup logs my-backup
velero backup describe my-backup
kubectl logs -n velero deploy/velero
```

## Итог

1. **Upgrade** — только на одну minor-версию за раз. Сначала Control Plane, потом nodes.
2. **etcd backup** — критически важен. Каждые 6-24 часа.
3. **etcd restore** — тестируйте регулярно.
4. **Velero** — бэкап объектов и PV.
5. **Сертификаты** — проверяйте срок. kubeadm certs renew.
6. **cert-manager** — автоматизация TLS.
7. **Drain** перед maintenance. **Uncordon** после.
8. **Мониторинг** — Prometheus + алерты.
9. **Disaster Recovery** — план на случай катастрофы.
10. **Регулярные учения** — backup без restore бесполезен.

> [!tip]
> **Правило эксплуатации:**
> - Backup etcd → каждые 6 часов
> - Проверка сертификатов → раз в месяц
> - Upgrade → раз в 3-4 месяца (следуя за релизами)
> - Тестирование restore → раз в квартал
> - Мониторинг → 24/7
> - Maintenance window → для обновлений

> [!warning]
> **Никогда не обновляйте production без бэкапа etcd.** Если что-то пойдёт не так — восстановление займёт часы.
