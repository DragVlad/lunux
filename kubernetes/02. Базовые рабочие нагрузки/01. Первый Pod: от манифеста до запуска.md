# 01. Первый Pod: от манифеста до запуска

Мы разобрались с архитектурой кластера и тем, как устроены объекты API. Теперь пришло время запустить **первое приложение**. И начнём мы с самого фундаментального объекта — **Pod**.

> **Pod** — это минимальная и неделимая единица развёртывания в Kubernetes. Это не контейнер. Это **группа из одного или нескольких контейнеров**, которые разделяют общее сетевое пространство, хранилище и жизненный цикл.

---

## Почему Pod, а не контейнер?

Kubernetes мог бы управлять контейнерами напрямую, как Docker. Но вместо этого он ввёл абстракцию **Pod**. Зачем?

**Причина 1: Совместно размещённые процессы.**  
Иногда двум процессам нужно работать вместе: один генерирует данные, другой их обрабатывает. В мире Docker для этого нужно было бы использовать `--link`, общие тома и вручную связывать контейнеры. В Kubernetes Pod даёт им:
- **Общий сетевой namespace:** все контейнеры в Pod видят друг друга через `localhost`.
- **Общий IPC namespace:** могут общаться через SysV IPC или POSIX queues.
- **Общие тома (Volumes):** могут обмениваться файлами.

**Причина 2: Единица планирования.**  
Scheduler назначает Pod на узел, а не отдельные контейнеры. Все контейнеры Pod гарантированно окажутся на одном узле.

**Причина 3: Единица масштабирования.**  
ReplicaSet масштабирует Pod, а не контейнеры. Это упрощает логику.

> [!note]
> В 99% случаев Pod содержит **один контейнер**. Много контейнеров в Pod — это паттерн **sidecar**, который мы разберём отдельно. Не создавайте много контейнеров в Pod без веской причины.

## Анатомия Pod

### Минимальный Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-first-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
```

Применим:

```bash
kubectl apply -f pod.yaml
kubectl get pods
kubectl describe pod my-first-pod
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `containers` | Список контейнеров в Pod. Обязательное поле |
| `containers[].name` | Имя контейнера. Уникально в рамках Pod |
| `containers[].image` | Образ. Если тег не указан — берётся `latest` (плохая практика) |
| `containers[].ports` | Список портов. **Информационное поле** — не открывает порт, а документирует |
| `containers[].env` | Переменные окружения |
| `containers[].resources` | Запросы и лимиты CPU/RAM |
| `containers[].volumeMounts` | Точки монтирования томов |
| `containers[].command` / `args` | Переопределение ENTRYPOINT и CMD из образа |

> [!warning]
> `ports` в Pod — это **не** открытие порта. Порт открыт, пока процесс внутри контейнера его слушает. `containerPort` нужен только для документации и для Service, который на него ссылается.

## Полный Pod: ресурсы, переменные, probes

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: full-pod
  labels:
    app: myapp
    env: production
spec:
  containers:
    - name: app
      image: nginx:1.25
      ports:
        - name: http
          containerPort: 80
          protocol: TCP
      env:
        - name: ENV
          value: "production"
        - name: DB_HOST
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: db_host
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: password
      resources:
        requests:
          memory: "128Mi"
          cpu: "250m"
        limits:
          memory: "256Mi"
          cpu: "500m"
      livenessProbe:
        httpGet:
          path: /healthz
          port: 80
        initialDelaySeconds: 10
        periodSeconds: 5
      readinessProbe:
        httpGet:
          path: /ready
          port: 80
        initialDelaySeconds: 5
        periodSeconds: 3
      volumeMounts:
        - name: data
          mountPath: /var/lib/data
        - name: config
          mountPath: /etc/app/config
          readOnly: true
  volumes:
    - name: data
      emptyDir: {}
    - name: config
      configMap:
        name: app-config
  restartPolicy: Always
  nodeSelector:
    disktype: ssd
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "app"
      effect: "NoSchedule"
```

### Ключевые поля Pod

| Поле | Назначение |
|------|------------|
| `restartPolicy` | `Always` (по умолчанию), `OnFailure`, `Never` |
| `nodeSelector` | Простейший способ привязать Pod к узлу по метке |
| `nodeName` | Прямое указание узла (обход scheduler — не рекомендуется) |
| `affinity` | Более гибкие правила привязки (nodeAffinity, podAffinity, podAntiAffinity) |
| `tolerations` | Разрешение запуска на узлах с taints |
| `volumes` | Список томов |
| `initContainers` | Контейнеры, выполняемые до основных |
| `serviceAccountName` | ServiceAccount для доступа к API |
| `securityContext` | Настройки безопасности (UID, capabilities, seccomp) |
| `hostNetwork`, `hostPID`, `hostIPC` | Использование namespace узла (опасно) |
| `dnsPolicy` | Политика DNS (`ClusterFirst` по умолчанию) |

## Жизненный цикл Pod

Pod проходит через несколько **фаз (phases)**:

| Фаза | Описание |
|------|----------|
| `Pending` | Pod создан, но ещё не запущен. Ждёт scheduling, скачивания образа |
| `Running` | Pod назначен на узел, все контейнеры запущены |
| `Succeeded` | Все контейнеры завершились с кодом 0 (для Job) |
| `Failed` | Хотя бы один контейнер завершился с ошибкой |
| `Unknown` | Состояние Pod неизвестно (обычно проблема с узлом) |

**Посмотреть фазу:**

```bash
kubectl get pod my-pod
# NAME       READY   STATUS    RESTARTS   AGE
# my-pod     1/1     Running   0          30s
```

### Состояния контейнеров

У каждого контейнера в Pod есть своё состояние:

| Состояние | Описание |
|-----------|----------|
| `Waiting` | Контейнер ещё не запущен (скачивание образа, ожидание зависимостей) |
| `Running` | Контейнер выполняется |
| `Terminated` | Контейнер завершился (успешно или с ошибкой) |

**Детали:**

```bash
kubectl describe pod my-pod
kubectl get pod my-pod -o jsonpath='{.status.containerStatuses[*].state}'
```

## Init-контейнеры

> **Init-контейнер** — контейнер, который выполняется **до** основных контейнеров Pod. Если init-контейнер упал — Pod перезапускается.

**Зачем нужны:**
- Подготовка данных (скачать конфиг, клонировать репозиторий).
- Ожидание зависимостей (проверить, что БД доступна).
- Установка прав на файлы (chown).
- Генерация сертификатов.

**Пример:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-init
spec:
  initContainers:
    - name: init-config
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          echo "Waiting for database..."
          until nc -z db-service 5432; do
            sleep 2
          done
          echo "Database is ready!"
      volumeMounts:
        - name: config
          mountPath: /config
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: config
          mountPath: /etc/app/config
  volumes:
    - name: config
      emptyDir: {}
```

**Особенности init-контейнеров:**
- Выполняются **последовательно**, один за другим.
- Должны **завершиться успешно** (exit code 0), иначе Pod перезапускается.
- Не поддерживают `livenessProbe` и `readinessProbe`.
- Не могут быть перезапущены отдельно от Pod.

## Probes: проверки здоровья

> **Probe** — это проверка, которую kubelet периодически выполняет для контейнера. Существует три типа проб.

### Liveness Probe — жив ли контейнер?

Если liveness probe падает — kubelet **перезапускает** контейнер.

**Когда использовать:** для обнаружения зависаний (deadlock, бесконечный цикл).

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 2
```

### Readiness Probe — готов ли контейнер принимать трафик?

Если readiness probe падает — Pod **убирается из Endpoints Service**. Трафик на него не идёт, но контейнер не перезапускается.

**Когда использовать:** для прогрева (загрузка кэша, подключение к БД).

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 3
  failureThreshold: 2
```

### Startup Probe — запустился ли контейнер?

Используется для **медленно стартующих** приложений (Java, legacy). Пока startup probe не пройдена — liveness и readiness не выполняются.

```yaml
startupProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 30   # 30 * 5 = 150 секунд на старт
```

### Типы проверок

| Тип | Описание | Пример |
|-----|----------|--------|
| `httpGet` | HTTP GET-запрос. Успех = 200-399 | `path: /healthz`, `port: 8080` |
| `tcpSocket` | TCP-подключение к порту | `port: 3306` |
| `exec` | Выполнить команду в контейнере. Успех = exit 0 | `command: ["cat", "/tmp/healthy"]` |
| `grpc` | gRPC health check (с v1.24) | `port: 50051` |

### Параметры проб

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| `initialDelaySeconds` | 0 | Задержка перед первой проверкой |
| `periodSeconds` | 10 | Интервал между проверками |
| `timeoutSeconds` | 1 | Таймаут одной проверки |
| `successThreshold` | 1 | Сколько успехов нужно для перехода из fail в success |
| `failureThreshold` | 3 | Сколько неудач нужно для признания fail |

> [!tip]
> **Не используйте liveness probe для проверки зависимостей** (БД, внешние API). Если БД упадёт, liveness перезапустит все Pod, что только усугубит ситуацию. Для зависимостей используйте readiness probe.

## Полный цикл: от манифеста до запуска

Проследим путь Pod от `kubectl apply` до `Running`.

### Шаг 1: kubectl отправляет запрос

```bash
kubectl apply -f pod.yaml
```

`kubectl` отправляет POST на `kube-apiserver` с манифестом.

### Шаг 2: API-сервер валидирует

- Проверяет синтаксис YAML.
- Проверяет права (RBAC).
- Применяет admission-контроллеры (например, PodSecurity).
- Сохраняет Pod в etcd со статусом `Pending`.

### Шаг 3: Scheduler назначает узел

- Scheduler получает уведомление о новом Pod без `nodeName`.
- Фильтрует узлы: хватает ли ресурсов? Есть ли tolerations?
- Оценивает: выбирает лучший узел.
- Обновляет Pod: `spec.nodeName = node-2`.

### Шаг 4: kubelet запускает Pod

- kubelet на `node-2` видит Pod с его `nodeName`.
- Через CRI просит containerd скачать образ.
- Containerd скачивает образ, создаёт контейнер.
- kubelet запускает init-контейнеры (если есть).
- После успеха init-контейнеров запускает основные.

### Шаг 5: Пробы

- kubelet начинает выполнять startup probe (если есть).
- После успеха startup — liveness и readiness.
- Когда readiness проходит — Pod добавляется в Endpoints Service.

### Шаг 6: Статус Running

- kubelet отправляет статус в API-сервер.
- Pod переходит в фазу `Running`.
- `kubectl get pods` показывает `1/1 Running`.

## Отладка Pod

### kubectl describe

```bash
kubectl describe pod my-pod
```

Показывает:
- Фазу, IP, узел.
- Состояние контейнеров.
- События (Events) — **самое важное** для отладки.

**Пример событий:**

```
Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  30s   default-scheduler  Successfully assigned default/my-pod to node-2
  Normal  Pulling    29s   kubelet            Pulling image "nginx:1.25"
  Normal  Pulled     25s   kubelet            Successfully pulled image "nginx:1.25"
  Normal  Created    25s   kubelet            Created container nginx
  Normal  Started    25s   kubelet            Started container nginx
```

### kubectl logs

```bash
# Логи Pod (если один контейнер)
kubectl logs my-pod

# Логи конкретного контейнера
kubectl logs my-pod -c nginx

# Логи предыдущего запуска (после перезапуска)
kubectl logs my-pod --previous

# Логи в реальном времени
kubectl logs -f my-pod

# Последние 50 строк
kubectl logs my-pod --tail=50
```

### kubectl exec

```bash
# Зайти в контейнер
kubectl exec -it my-pod -- /bin/bash

# Выполнить команду
kubectl exec my-pod -- ls /etc/nginx

# Зайти в конкретный контейнер
kubectl exec -it my-pod -c nginx -- /bin/sh
```

### kubectl port-forward

```bash
# Пробросить порт Pod на локальную машину
kubectl port-forward my-pod 8080:80

# Теперь можно открыть http://localhost:8080
```

### kubectl debug

```bash
# Запустить эфемерный контейнер в Pod для отладки
kubectl debug -it my-pod --image=busybox --target=nginx

# Создать копию Pod с изменённым образом
kubectl debug my-pod --copy-to=my-pod-debug --image=nginx:1.25 --share-processes
```

## Типичные ошибки и их решение

### ImagePullBackOff / ErrImagePull

**Причина:** неверный образ, нет доступа к registry, проблема с сетью.

```bash
kubectl describe pod my-pod | grep -A5 "Events:"
```

**Решение:**
- Проверить имя образа и тег.
- Проверить `imagePullSecrets` для приватных registry.
- Проверить доступность registry с узла.

### CrashLoopBackOff

**Причина:** контейнер запускается и сразу падает. kubelet перезапускает, снова падает.

```bash
kubectl logs my-pod --previous
```

**Решение:**
- Посмотреть логи.
- Проверить command/args.
- Проверить, хватает ли ресурсов.
- Проверить liveness probe (может быть слишком агрессивной).

### Pending

**Причина:** Pod не может быть назначен на узел.

```bash
kubectl describe pod my-pod | grep -A10 "Events:"
```

**Возможные причины:**
- Недостаточно ресурсов (CPU/RAM).
- Нет узлов с нужными labels (nodeSelector).
- Taints на узлах без tolerations.
- PVC не привязан.

### OOMKilled

**Причина:** контейнер превысил лимит памяти.

```bash
kubectl describe pod my-pod | grep -i oom
```

**Решение:**
- Увеличить `limits.memory`.
- Оптимизировать приложение.
- Проверить утечки памяти.

### Terminating (застрял)

**Причина:** Pod не может завершиться (finalizers, проблемы с узлом).

```bash
# Форсированное удаление
kubectl delete pod my-pod --grace-period=0 --force
```

> [!warning]
> Форсированное удаление может привести к «зомби»-процессам на узле. Используйте только в крайнем случае.

## Полный пример: Pod с init-контейнером, пробами и ресурсами

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app
  labels:
    app: web
spec:
  initContainers:
    - name: init-db
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          echo "Waiting for database..."
          until nc -z db-service 5432; do
            sleep 2
          done
          echo "Database ready!"
  containers:
    - name: web
      image: nginx:1.25
      ports:
        - name: http
          containerPort: 80
      env:
        - name: DB_HOST
          value: "db-service"
        - name: DB_PORT
          value: "5432"
      resources:
        requests:
          memory: "128Mi"
          cpu: "100m"
        limits:
          memory: "256Mi"
          cpu: "500m"
      livenessProbe:
        httpGet:
          path: /
          port: 80
        initialDelaySeconds: 10
        periodSeconds: 10
      readinessProbe:
        httpGet:
          path: /
          port: 80
        initialDelaySeconds: 5
        periodSeconds: 5
      volumeMounts:
        - name: cache
          mountPath: /var/cache/nginx
  volumes:
    - name: cache
      emptyDir: {}
  restartPolicy: Always
```

```bash
kubectl apply -f web-app.yaml
kubectl get pods -w
kubectl describe pod web-app
kubectl logs web-app -c init-db
kubectl exec -it web-app -- /bin/bash
```

## Итог

1. **Pod** — минимальная единица развёртывания. Группа контейнеров с общим network, IPC и volumes.
2. **Один контейнер в Pod** — стандарт. Много контейнеров — только для sidecar-паттернов.
3. **`ports` в Pod** — информационное поле, не открывает порт.
4. **Init-контейнеры** — выполняются до основных, последовательно, должны завершиться успешно.
5. **Probes** — liveness (перезапуск), readiness (трафик), startup (медленный старт).
6. **Жизненный цикл:** Pending → Running → Succeeded/Failed.
7. **Отладка:** `describe`, `logs`, `exec`, `port-forward`, `debug`.
8. **Pod не перезапускается сам по себе** — за это отвечает контроллер (ReplicaSet, Deployment). Голый Pod — плохая практика для production.

> [!warning]
> **Не создавайте голые Pod в production.** Если Pod упадёт — никто его не пересоздаст. Используйте Deployment, StatefulSet, DaemonSet. Голый Pod полезен только для отладки и обучения.
