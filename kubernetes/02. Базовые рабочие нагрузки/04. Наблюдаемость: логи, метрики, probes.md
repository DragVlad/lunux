# 04. Наблюдаемость: логи, метрики, probes

Мы научились запускать приложения и передавать им конфигурацию. Но как понять, **что происходит внутри**? Работает ли приложение? Не тормозит ли? Не падает ли? В этой лекции мы разберём три столпа наблюдаемости в Kubernetes: **логи**, **метрики** и **probes**.

> **Наблюдаемость (Observability)** — это способность понять внутреннее состояние системы по её внешним проявлениям. Три столпа: **логи** (что произошло), **метрики** (сколько, как быстро), **трейсы** (где задержка). В этой лекции — логи и метрики. Трейсы — отдельная тема.

---

## Часть 1: Логи

### Как устроено логирование в Kubernetes

В отличие от традиционных серверов, в Kubernetes **нет единого файла лога**. Pod эфемерны: они создаются, умирают, пересоздаются. Логи нужно собирать централизованно.

> **Ключевой принцип:** приложение должно писать логи в **stdout** и **stderr**, а не в файлы.

**Почему:**
- kubelet перехватывает stdout/stderr контейнера и сохраняет их.
- Логи доступны через `kubectl logs`.
- Централизованные системы (Loki, Elasticsearch) собирают их автоматически.

### Просмотр логов через kubectl

```bash
# Логи Pod (если один контейнер)
kubectl logs my-pod

# Логи конкретного контейнера
kubectl logs my-pod -c nginx

# Логи предыдущего запуска (после CrashLoopBackOff)
kubectl logs my-pod --previous

# Логи в реальном времени
kubectl logs -f my-pod

# Последние 50 строк
kubectl logs my-pod --tail=50

# Логи за последний час
kubectl logs my-pod --since=1h

# Логи с timestamp
kubectl logs my-pod --timestamps

# Логи всех Pod с меткой
kubectl logs -l app=nginx --tail=20

# Логи всех Pod в Deployment
kubectl logs -f deploy/web-app
```

### Где kubelet хранит логи

На узле логи хранятся в:

```
/var/log/pods/<namespace>_<pod-name>_<uid>/<container-name>/0.log
```

Или через симлинки:

```
/var/log/containers/<pod-name>_<namespace>_<container-name>-<container-id>.log
```

**Ротация логов:**

kubelet автоматически ротирует логи:
- `containerLogMaxSize` (по умолчанию 10Mi).
- `containerLogMaxFiles` (по умолчанию 5).

Настраивается в `kubelet-config.yaml`.

> [!warning]
> Логи в `/var/log/pods` — **временные**. При удалении Pod они удаляются. Для долгосрочного хранения нужна централизованная система.

### Централизованное логирование

| Решение | Описание |
|---------|----------|
| **Loki + Promtail** | Лёгкий, от Grafana. Индексирует только метки, не текст |
| **Elasticsearch + Fluentd + Kibana (EFK)** | Мощный, полнотекстовый поиск. Тяжёлый |
| **Fluent Bit** | Лёгкий форвардер, часто используется с Loki или Elasticsearch |
| **Datadog / Splunk** | Коммерческие SaaS |
| **Cloud Logging** | GCP, AWS CloudWatch, Azure Monitor |

**Архитектура (на примере Loki):**

```
Pod stdout → kubelet → /var/log/pods → Promtail (DaemonSet) → Loki → Grafana
```

**Пример DaemonSet для Fluent Bit:**

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
  namespace: logging
spec:
  selector:
    matchLabels:
      app: fluent-bit
  template:
    metadata:
      labels:
        app: fluent-bit
    spec:
      containers:
        - name: fluent-bit
          image: fluent/fluent-bit:2.2
          volumeMounts:
            - name: varlog
              mountPath: /var/log
            - name: containers
              mountPath: /var/lib/docker/containers
              readOnly: true
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
        - name: containers
          hostPath:
            path: /var/lib/docker/containers
```

### Структурированные логи

**Плохо (plain text):**

```
2024-01-15 10:00:00 ERROR Failed to connect to database at postgres:5432
```

**Хорошо (JSON):**

```json
{
  "timestamp": "2024-01-15T10:00:00Z",
  "level": "error",
  "message": "Failed to connect to database",
  "db_host": "postgres",
  "db_port": 5432,
  "request_id": "abc-123"
}
```

**Почему JSON:**
- Легко парсится.
- Можно фильтровать по полям.
- Удобно для агрегации.

**Пример на Python:**

```python
import logging
import json
from pythonjsonlogger import jsonlogger

logger = logging.getLogger()
handler = logging.StreamHandler()
handler.setFormatter(jsonlogger.JsonFormatter())
logger.addHandler(handler)
logger.setLevel(logging.INFO)

logger.info("User logged in", extra={"user_id": 123, "ip": "10.0.0.1"})
```

### Sidecar для логов

Если приложение пишет логи **в файл**, а не в stdout, можно использовать sidecar-контейнер, который читает файл и пишет в stdout:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-logging
spec:
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
    - name: log-shipper
      image: busybox:1.36
      command:
        - sh
        - -c
        - tail -f /var/log/app/app.log
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
  volumes:
    - name: logs
      emptyDir: {}
```

> [!tip]
> **Лучшая практика:** приложение пишет в stdout/stderr. Sidecar — только если нельзя изменить приложение.

## Часть 2: Метрики

### Метрики vs Логи

| Логи | Метрики |
|------|---------|
| События | Числа |
| «Что произошло» | «Сколько, как быстро» |
| Дорого хранить | Дёшево хранить |
| Полнотекстовый поиск | Агрегация, графики |
| Пример: `ERROR: DB connection failed` | Пример: `db_connections_active = 42` |

### Типы метрик

| Тип | Описание | Пример |
|-----|----------|--------|
| **Counter** | Только растёт | `http_requests_total` |
| **Gauge** | Может расти и падать | `memory_usage_bytes` |
| **Histogram** | Распределение значений | `http_request_duration_seconds` |
| **Summary** | Как histogram, но с квантилями | `rpc_duration_seconds` |

### Prometheus — стандарт метрик

> **Prometheus** — система сбора и хранения метрик. Pull-модель: Prometheus сам опрашивает endpoints.

**Архитектура:**

```
Pod (exporter) → ServiceMonitor → Prometheus → Grafana
```

### Что собирать

| Категория | Метрики |
|-----------|---------|
| **CPU** | `container_cpu_usage_seconds_total` |
| **Память** | `container_memory_working_set_bytes` |
| **Сеть** | `container_network_receive_bytes_total` |
| **Диск** | `container_fs_usage_bytes` |
| **Приложение** | `http_requests_total`, `http_request_duration_seconds` |
| **Kubernetes** | `kube_pod_status_phase`, `kube_deployment_status_replicas_available` |

### Метрики Kubernetes

**kube-state-metrics** — экспортирует метрики о состоянии объектов Kubernetes:

- `kube_deployment_status_replicas`
- `kube_pod_container_status_restarts_total`
- `kube_node_status_condition`
- `kube_persistentvolumeclaim_status_phase`

**Установка (через Helm):**

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install kube-state-metrics prometheus-community/kube-state-metrics -n monitoring
```

### Метрики узлов

**node-exporter** — экспортирует метрики узла (CPU, RAM, диск, сеть).

**Установка:**

```bash
helm install node-exporter prometheus-community/prometheus-node-exporter -n monitoring
```

### Метрики приложения

Приложение должно экспортировать метрики в формате Prometheus:

```
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 1234
http_requests_total{method="POST",status="500"} 5
```

**Пример на Python (prometheus_client):**

```python
from prometheus_client import Counter, Histogram, start_http_server

REQUEST_COUNT = Counter('http_requests_total', 'Total HTTP requests', ['method', 'status'])
REQUEST_LATENCY = Histogram('http_request_duration_seconds', 'HTTP request latency')

@REQUEST_LATENCY.time()
def handle_request():
    REQUEST_COUNT.labels(method='GET', status='200').inc()
    # ... логика

start_http_server(8000)
```

### ServiceMonitor — как Prometheus находит приложение

**ServiceMonitor** — CRD от Prometheus Operator, описывает, какие Service мониторить:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: my-app
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: my-app
  endpoints:
    - port: metrics
      interval: 30s
      path: /metrics
```

### Просмотр метрик через kubectl

```bash
# Проброс порта к Pod с метриками
kubectl port-forward my-pod 8000:8000

# Открыть http://localhost:8000/metrics
curl http://localhost:8000/metrics
```

### Metrics Server — метрики для HPA и kubectl top

> **Metrics Server** — лёгкий агрегатор метрик CPU/RAM для `kubectl top` и HPA.

**Установка:**

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

**Использование:**

```bash
kubectl top nodes
kubectl top pods
kubectl top pods -A
kubectl top pod my-pod --containers
```

**Пример вывода:**

```
NAME       CPU(cores)   MEMORY(bytes)
my-pod     10m          50Mi
```

> [!note]
> Metrics Server — не для долгосрочного хранения. Он хранит метрики в памяти. Для истории — Prometheus.

## Часть 3: Probes

Probes — это не только health checks, но и **инструмент наблюдаемости**. Они дают kubelet информацию о состоянии контейнера.

### Три типа проб

| Probe | Что проверяет | Действие при fail |
|-------|---------------|-------------------|
| **Liveness** | Жив ли контейнер | Перезапуск контейнера |
| **Readiness** | Готов ли принимать трафик | Удаление из Endpoints Service |
| **Startup** | Запустился ли | Блокирует liveness/readiness |

### Liveness Probe

**Когда использовать:** для обнаружения зависаний (deadlock, бесконечный цикл).

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
```

**Что делать в `/healthz`:**

```python
@app.route('/healthz')
def healthz():
    # Проверяем только, что процесс жив
    return "OK", 200
```

> [!warning]
> **Не проверяйте зависимости в liveness probe.** Если БД упадёт, liveness перезапустит все Pod, что усугубит ситуацию.

### Readiness Probe

**Когда использовать:** для прогрева (загрузка кэша, подключение к БД).

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 3
  failureThreshold: 2
```

**Что делать в `/ready`:**

```python
@app.route('/ready')
def ready():
    # Проверяем зависимости
    if not db.is_connected():
        return "DB not ready", 503
    if not cache.is_warmed():
        return "Cache not warmed", 503
    return "OK", 200
```

### Startup Probe

**Когда использовать:** для медленно стартующих приложений (Java, legacy).

```yaml
startupProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 30   # 30 * 5 = 150 секунд на старт
```

Пока startup probe не пройдена — liveness и readiness **не выполняются**.

### Типы проверок

| Тип | Пример | Когда использовать |
|-----|--------|-------------------|
| `httpGet` | `path: /healthz`, `port: 8080` | HTTP-сервисы |
| `tcpSocket` | `port: 3306` | TCP-сервисы (БД, Redis) |
| `exec` | `command: ["cat", "/tmp/healthy"]` | Сложные проверки |
| `grpc` | `port: 50051` | gRPC-сервисы (с v1.24) |

### Параметры проб

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| `initialDelaySeconds` | 0 | Задержка перед первой проверкой |
| `periodSeconds` | 10 | Интервал между проверками |
| `timeoutSeconds` | 1 | Таймаут одной проверки |
| `successThreshold` | 1 | Сколько успехов нужно для перехода из fail в success |
| `failureThreshold` | 3 | Сколько неудач нужно для признания fail |

### Просмотр состояния проб

```bash
# События Pod
kubectl describe pod my-pod | grep -A10 "Events:"

# Проверка статуса контейнера
kubectl get pod my-pod -o jsonpath='{.status.containerStatuses[*].ready}'

# Логи kubelet
journalctl -u kubelet | grep -i probe
```

**Пример событий:**

```
Events:
  Type     Reason     Age   From     Message
  ----     ------     ----  ----     -------
  Warning  Unhealthy  10s   kubelet  Liveness probe failed: HTTP probe failed with statuscode: 500
  Normal   Killing    5s    kubelet  Container app failed liveness probe, will be restarted
```

### Best practices для проб

| Практика | Почему |
|----------|--------|
| Liveness — только «жив ли процесс» | Не перезапускать из-за зависимостей |
| Readiness — проверять зависимости | Убрать из трафика, если БД недоступна |
| Startup — для медленного старта | Дать приложению время без перезапусков |
| `initialDelaySeconds` > времени старта | Избежать ложных срабатываний |
| `timeoutSeconds` < `periodSeconds` | Иначе пробы будут накладываться |
| Не использовать `exec` для HTTP | `httpGet` эффективнее |
| Логировать провалы | Помогает в отладке |

## Практический пример: полный стек

### Deployment с пробами и метриками

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "8080"
        prometheus.io/path: "/metrics"
    spec:
      containers:
        - name: web
          image: myapp:1.0
          ports:
            - name: http
              containerPort: 8080
            - name: metrics
              containerPort: 9090
          env:
            - name: LOG_LEVEL
              value: "info"
          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "500m"
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 30
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
```

### Service для метрик

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app-metrics
  labels:
    app: web
spec:
  selector:
    app: web
  ports:
    - name: metrics
      port: 9090
      targetPort: 9090
```

### ServiceMonitor

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: web-app
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: web
  endpoints:
    - port: metrics
      interval: 30s
      path: /metrics
```

### Проверка

```bash
# Логи
kubectl logs -f deploy/web-app

# Метрики
kubectl port-forward svc/web-app-metrics 9090:9090
curl http://localhost:9090/metrics

# Пробы
kubectl describe pod <pod-name> | grep -A5 "Liveness\|Readiness\|Startup"

# kubectl top
kubectl top pods -l app=web
```

## Итог

1. **Логи** — приложение пишет в stdout/stderr. kubelet перехватывает. Централизованно — Loki, EFK.
2. **Метрики** — Prometheus + exporters. `kubectl top` — через Metrics Server.
3. **Probes** — liveness (перезапуск), readiness (трафик), startup (медленный старт).
4. **Liveness — только «жив ли процесс».** Зависимости — в readiness.
5. **Структурированные логи (JSON)** — стандарт для production.
6. **ServiceMonitor** — как Prometheus находит приложение.
7. **Metrics Server** — для HPA и `kubectl top`. Не для истории.
8. **Всегда указывайте requests/limits** — иначе scheduler не сможет корректно распределить Pod.

> [!tip]
> Наблюдаемость — это не «поставить Prometheus и Grafana». Это культура: логировать осмысленно, экспортировать метрики, настраивать алерты. Без этого вы будете узнавать о проблемах от пользователей, а не от систем.
