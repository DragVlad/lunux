# 03. Конфигурация и секреты: ConfigMap и Secret

Мы научились запускать приложения через Deployment. Но приложение — это не только код. Ему нужны **настройки**: адреса баз данных, порты, фича-флаги, пароли, API-ключи. И здесь встаёт вопрос: как передать конфигурацию в Pod, не «запекая» её в образ?

> **Главный принцип:** образ должен быть **immutable** и **portable**. Один и тот же образ должен работать в dev, staging и production. Различаться должна только конфигурация.

---

## Проблема: конфигурация внутри образа

Представьте, что вы «запекли» пароль от БД в образ. Что произойдёт:

1. **Безопасность:** пароль виден любому, кто скачает образ.
2. **Портируемость:** для dev и prod нужны разные образы.
3. **Обновление:** чтобы сменить пароль, нужно пересобрать образ.

Kubernetes решает это через два объекта: **ConfigMap** (для несекретных данных) и **Secret** (для секретных).

---

## ConfigMap — несекретная конфигурация

> **ConfigMap** — объект для хранения неконфиденциальных данных в виде пар ключ-значение. Может быть смонтирован как файл или передан как переменная окружения.

### Что хранить в ConfigMap

- Адреса сервисов (`db_host: postgres.default.svc.cluster.local`).
- Порты (`db_port: "5432"`).
- Фича-флаги (`feature_x_enabled: "true"`).
- Файлы конфигурации (`nginx.conf`, `app.properties`).
- Публичные ключи, сертификаты (не приватные!).

### Что НЕ хранить в ConfigMap

- Пароли.
- API-ключи.
- Токены.
- Приватные ключи.
- Всё, что должно быть зашифровано.

> [!warning]
> ConfigMap хранится в etcd **в открытом виде**. Любой, у кого есть доступ к etcd или к API-серверу с правами на чтение ConfigMap, увидит данные.

---

## Создание ConfigMap

### Способ 1: из литералов

```bash
kubectl create configmap app-config \
  --from-literal=db_host=postgres.default.svc.cluster.local \
  --from-literal=db_port=5432 \
  --from-literal=log_level=info
```

### Способ 2: из файла

```bash
# Создать файл
cat > app.properties <<EOF
db.host=postgres.default.svc.cluster.local
db.port=5432
log.level=info
EOF

# Создать ConfigMap (ключ = имя файла, значение = содержимое)
kubectl create configmap app-config --from-file=app.properties

# С несколькими файлами
kubectl create configmap app-config \
  --from-file=app.properties \
  --from-file=nginx.conf
```

### Способ 3: из директории

```bash
kubectl create configmap app-config --from-file=./config/
```

Каждый файл в директории станет отдельным ключом.

### Способ 4: декларативно (YAML)

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: default
data:
  db_host: "postgres.default.svc.cluster.local"
  db_port: "5432"
  log_level: "info"
  app.properties: |
    db.host=postgres.default.svc.cluster.local
    db.port=5432
    log.level=info
  nginx.conf: |
    server {
      listen 80;
      location / {
        root /usr/share/nginx/html;
      }
    }
```

> [!note]
> `data` — для строковых значений. `binaryData` — для бинарных (base64). Обычно используется `data`.

### Просмотр ConfigMap

```bash
# Список
kubectl get configmaps
kubectl get cm

# Детали
kubectl describe cm app-config

# YAML
kubectl get cm app-config -o yaml

# Конкретное значение
kubectl get cm app-config -o jsonpath='{.data.db_host}'
```

## Использование ConfigMap в Pod

### Способ 1: как переменные окружения (все ключи)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
    - name: app
      image: myapp:1.0
      envFrom:
        - configMapRef:
            name: app-config
```

Все ключи из ConfigMap станут переменными окружения:
- `db_host` → `$db_host`
- `db_port` → `$db_port`
- `log_level` → `$log_level`

### Способ 2: как переменные окружения (выборочно)

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      env:
        - name: DB_HOST
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: db_host
        - name: DB_PORT
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: db_port
```

Здесь вы можете переименовать переменные (`db_host` → `DB_HOST`).

### Способ 3: как файлы (volume mount)

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: config-volume
          mountPath: /etc/app/config
          readOnly: true
  volumes:
    - name: config-volume
      configMap:
        name: app-config
```

**Что произойдёт:** каждый ключ ConfigMap станет файлом в `/etc/app/config/`:
- `/etc/app/config/db_host` (содержимое: `postgres.default.svc.cluster.local`)
- `/etc/app/config/db_port` (содержимое: `5432`)
- `/etc/app/config/app.properties` (содержимое: многострочный текст)
- `/etc/app/config/nginx.conf`

### Смонтировать только конкретные ключи

```yaml
volumes:
  - name: config-volume
    configMap:
      name: app-config
      items:
        - key: nginx.conf
          path: nginx.conf
        - key: app.properties
          path: app.properties
```

### Изменить права на файлы

```yaml
volumes:
  - name: config-volume
    configMap:
      name: app-config
      defaultMode: 0644
```

## Автоматическое обновление ConfigMap

> **Важно:** при монтировании ConfigMap как volume, изменения в ConfigMap **автоматически** попадают в Pod (с задержкой до 1 минуты). При использовании как env — **не обновляются** (нужен перезапуск Pod).

| Способ | Автообновление |
|--------|----------------|
| Volume mount | ✅ Да (kubelet синхронизирует) |
| envFrom | ❌ Нет |
| env (valueFrom) | ❌ Нет |

> [!tip]
> Если приложение не умеет перечитывать конфиг на лету — используйте **Reloader** (Stakater) или **ConfigMap reloader**. Он следит за изменениями и перезапускает Deployment.

## Secret — секретные данные

> **Secret** — объект для хранения конфиденциальных данных. По структуре похож на ConfigMap, но с дополнительными мерами защиты.

### Что хранить в Secret

- Пароли.
- API-ключи.
- Токены.
- Приватные ключи SSH.
- Сертификаты TLS.
- Учётные данные Docker registry.

### Чем Secret отличается от ConfigMap

| Аспект | ConfigMap | Secret |
|--------|-----------|--------|
| Шифрование в etcd | ❌ Нет | ✅ Да (если настроено) |
| Кодирование | Plain text | base64 |
| Размер | До 1 MiB | До 1 MiB |
| Монтирование | Volume / env | Volume / env |
| RBAC | Обычный | Можно ограничить отдельно |

> [!warning]
> **base64 — это не шифрование.** Это просто кодирование. Любой, кто прочитает Secret, легко декодирует его. Защита Secret обеспечивается:
> - RBAC (ограничение доступа).
> - Encryption at rest (шифрование etcd).
> - Внешние хранилища (Vault, AWS Secrets Manager).

---

## Создание Secret

### Способ 1: из литералов

```bash
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password='S3cr3tP@ssw0rd!'
```

### Способ 2: из файла

```bash
echo -n 'admin' > username.txt
echo -n 'S3cr3tP@ssw0rd!' > password.txt

kubectl create secret generic db-secret \
  --from-file=username.txt \
  --from-file=password.txt
```

### Способ 3: декларативно (YAML)

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=                          # base64 от "admin"
  password: UzNjcjN0UEBzc3cwcmQh             # base64 от "S3cr3tP@ssw0rd!"
```

### Кодирование в base64

```bash
echo -n 'admin' | base64
# YWRtaW4=

echo -n 'S3cr3tP@ssw0rd!' | base64
# UzNjcjN0UEBzc3cwcmQh

# Декодирование
echo 'YWRtaW4=' | base64 -d
# admin
```

### stringData — удобство

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  username: admin
  password: S3cr3tP@ssw0rd!
```

`stringData` позволяет писать plain text, Kubernetes сам закодирует в base64 при сохранении.

> [!note]
> При чтении Secret через `kubectl get secret -o yaml` вы увидите `data` (base64). `stringData` не отображается.

## Типы Secret

| Тип | Назначение |
|-----|------------|
| `Opaque` | Произвольные данные (по умолчанию) |
| `kubernetes.io/service-account-token` | Токен ServiceAccount |
| `kubernetes.io/dockercfg` | Docker config |
| `kubernetes.io/dockerconfigjson` | Docker config JSON |
| `kubernetes.io/basic-auth` | Username/password |
| `kubernetes.io/ssh-auth` | SSH ключ |
| `kubernetes.io/tls` | TLS сертификат и ключ |
| `bootstrap.kubernetes.io/token` | Bootstrap токен |

### Пример: TLS Secret

```bash
kubectl create secret tls my-tls-secret \
  --cert=path/to/tls.crt \
  --key=path/to/tls.key
```

### Пример: Docker registry Secret

```bash
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=user \
  --docker-password=pass \
  --docker-email=user@example.com
```

Использование в Pod:

```yaml
spec:
  imagePullSecrets:
    - name: regcred
  containers:
    - name: app
      image: registry.example.com/myapp:1.0
```

## Использование Secret в Pod

### Как переменные окружения (все)

```yaml
spec:
  containers:
    - name: app
      envFrom:
        - secretRef:
            name: db-secret
```

### Как переменные окружения (выборочно)

```yaml
spec:
  containers:
    - name: app
      env:
        - name: DB_USER
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: username
        - name: DB_PASS
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password
```

### Как файлы (volume mount)

```yaml
spec:
  containers:
    - name: app
      volumeMounts:
        - name: secret-volume
          mountPath: /etc/app/secrets
          readOnly: true
  volumes:
    - name: secret-volume
      secret:
        secretName: db-secret
        defaultMode: 0400   # только чтение для владельца
```

> [!tip]
> Для Secret всегда используйте `defaultMode: 0400` (или 0440), чтобы файлы не были доступны другим пользователям.

## ConfigMap vs Secret: что выбрать

| Данные | Объект |
|--------|--------|
| Пароли | Secret |
| API-ключи | Secret |
| Токены | Secret |
| TLS сертификаты | Secret (тип `kubernetes.io/tls`) |
| Адреса сервисов | ConfigMap |
| Порты | ConfigMap |
| Фича-флаги | ConfigMap |
| Файлы конфигурации (nginx.conf) | ConfigMap |
| Публичные сертификаты | ConfigMap |

## Immutable ConfigMap и Secret

С версии Kubernetes 1.21 можно сделать ConfigMap и Secret **immutable**:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
immutable: true
data:
  db_host: "postgres.default.svc.cluster.local"
```

**Преимущества:**
- Защита от случайных изменений.
- Улучшение производительности (kubelet не следит за изменениями).

**Недостатки:**
- Нельзя изменить. Только удалить и создать заново.
- Pod, использующие immutable ConfigMap, не обновятся автоматически.

## Практический пример: полный цикл

### Шаг 1: Создать ConfigMap

**Файл `configmap.yaml`:**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  db_host: "postgres.default.svc.cluster.local"
  db_port: "5432"
  log_level: "info"
  app.properties: |
    server.port=8080
    server.timeout=30
    feature.new_ui=true
```

```bash
kubectl apply -f configmap.yaml
```

### Шаг 2: Создать Secret

```bash
kubectl create secret generic app-secret \
  --from-literal=db_username=admin \
  --from-literal=db_password='S3cr3tP@ss!'
```

### Шаг 3: Создать Deployment с использованием обоих

**Файл `deployment.yaml`:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
          env:
            - name: DB_HOST
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: db_host
            - name: DB_PORT
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: db_port
            - name: DB_USER
              valueFrom:
                secretKeyRef:
                  name: app-secret
                  key: db_username
            - name: DB_PASS
              valueFrom:
                secretKeyRef:
                  name: app-secret
                  key: db_password
          volumeMounts:
            - name: config-volume
              mountPath: /etc/app/config
              readOnly: true
            - name: secret-volume
              mountPath: /etc/app/secrets
              readOnly: true
      volumes:
        - name: config-volume
          configMap:
            name: app-config
            items:
              - key: app.properties
                path: app.properties
        - name: secret-volume
          secret:
            secretName: app-secret
            defaultMode: 0400
```

```bash
kubectl apply -f deployment.yaml
```

### Шаг 4: Проверить

```bash
# Pod запущены
kubectl get pods -l app=web

# Переменные окружения
kubectl exec -it <pod-name> -- env | grep DB_

# Файлы
kubectl exec -it <pod-name> -- ls -la /etc/app/config/
kubectl exec -it <pod-name> -- cat /etc/app/config/app.properties
kubectl exec -it <pod-name> -- ls -la /etc/app/secrets/
```

### Шаг 5: Обновить ConfigMap

```bash
kubectl edit cm app-config
# Изменить log_level на "debug"

# Подождать ~1 минуту
kubectl exec -it <pod-name> -- cat /etc/app/config/app.properties
# Изменения появятся автоматически
```

> [!note]
> Изменения в volume-mounted ConfigMap появляются с задержкой (kubelet sync period + cache TTL). Обычно до 1 минуты.

### Шаг 6: Удалить

```bash
kubectl delete -f deployment.yaml
kubectl delete -f configmap.yaml
kubectl delete secret app-secret
```

## Безопасность Secret: продвинутые темы

### Encryption at rest

По умолчанию Secret в etcd хранится в base64 (не зашифрован). Для шифрования нужно настроить `EncryptionConfiguration` в API-сервере.

**Пример `encryption-config.yaml`:**

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <base64-encoded-32-byte-key>
      - identity: {}
```

Затем API-сервер запускается с флагом `--encryption-provider-config`.

### Внешние хранилища секретов

| Решение | Описание |
|---------|----------|
| **HashiCorp Vault** | Централизованное хранилище секретов с динамическими credentials |
| **AWS Secrets Manager** | Секреты в AWS, интеграция через CSI driver |
| **Azure Key Vault** | Секреты в Azure |
| **GCP Secret Manager** | Секреты в GCP |
| **Sealed Secrets** | Шифрование Secret для хранения в Git |
| **External Secrets Operator** | Синхронизация внешних секретов в Kubernetes |

### Sealed Secrets (Bitnami)

Позволяет хранить зашифрованные Secret в Git:

```bash
# Установить kubeseal
# Зашифровать Secret
kubeseal --format yaml < secret.yaml > sealed-secret.yaml

# sealed-secret.yaml безопасно хранить в Git
# В кластере контроллер расшифрует его в обычный Secret
```

## Типичные ошибки

### ConfigMap/Secret не найден

```
CreateContainerConfigError: configmap "app-config" not found
```

**Решение:** создать ConfigMap/Secret в том же namespace, что и Pod.

### Secret в другом namespace

ConfigMap и Secret **namespaced**. Pod не может использовать ConfigMap из другого namespace.

**Решение:** создать ConfigMap/Secret в каждом namespace, либо использовать внешнее хранилище.

### base64 с переносом строки

```bash
echo 'admin' | base64
# YWRtaW4K  ← обратите внимание на K в конце (перенос строки)
```

**Решение:** использовать `echo -n` (без newline) или `printf`.

### Изменения в ConfigMap не применяются

- Если ConfigMap смонтирован как volume — изменения появятся с задержкой.
- Если ConfigMap используется как env — изменения **не появятся** без перезапуска Pod.

**Решение:** использовать Reloader или вручную перезапускать Deployment:

```bash
kubectl rollout restart deploy web-app
```

```bash

kubectl create configmap app-config --from-literal=key=value

echo -n 'text' | base64
echo 'base64' | base64 -d
```

## Итог

1. **ConfigMap** — для несекретных данных. **Secret** — для секретных.
2. **base64 — не шифрование.** Защита Secret — через RBAC и encryption at rest.
3. **Volume mount** — автообновление. **env** — не обновляется.
4. **Immutable** ConfigMap/Secret защищают от случайных изменений.
5. **Используйте внешние хранилища** (Vault, AWS Secrets Manager) для production.
6. **Не «запекайте» конфигурацию в образ.** Образ должен быть immutable.
7. **Sealed Secrets** позволяют безопасно хранить Secret в Git.
8. **Reloader** автоматически перезапускает Pod при изменении ConfigMap/Secret.

> [!tip]
> Для проверки, что Secret не утёк в образ или логи — используйте сканеры (Trivy, kube-score, kubesec). Они находят секреты в манифестах.
