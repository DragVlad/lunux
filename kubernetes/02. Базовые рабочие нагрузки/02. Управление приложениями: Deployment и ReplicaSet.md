# 02. Управление приложениями: Deployment и ReplicaSet

В прошлой лекции мы запустили голый Pod. Но у него есть фатальный недостаток: **если Pod упадёт, никто его не пересоздаст**. В production так работать нельзя. Нужны контроллеры, которые следят за состоянием приложения. В этой лекции мы разберём два ключевых контроллера: **ReplicaSet** и **Deployment**.

> **Контроллер** — это процесс в `kube-controller-manager`, который наблюдает за состоянием объектов и приводит текущее состояние к желаемому. Это и есть reconciliation loop в действии.

---

## ReplicaSet — гарант количества

> **ReplicaSet (RS)** — контроллер, который гарантирует, что в любой момент времени запущено ровно N экземпляров Pod, соответствующих селектору.

### Зачем нужен ReplicaSet

Представьте: у вас есть Pod с веб-приложением. Он упал. Кто его перезапустит? Никто. ReplicaSet решает эту проблему:

- Следит, чтобы всегда было **N Pod**.
- Если Pod упал — создаёт новый.
- Если Pod стало больше N — удаляет лишние.
- Если узел упал — пересоздаёт Pod на другом узле.

### Манифест ReplicaSet

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: my-replicaset
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `replicas` | Желаемое количество Pod |
| `selector` | **Как RS находит свои Pod.** По labels |
| `template` | **Шаблон Pod.** RS создаёт Pod по этому шаблону |

> [!important]
> **`selector` и `template.metadata.labels` должны совпадать.** Иначе RS не сможет найти созданные им Pod и будет создавать бесконечно новые.

### Как работает ReplicaSet

1. **Watch:** RS подписан на API-сервер и получает уведомления о Pod с метками из `selector`.
2. **Подсчёт:** Считает, сколько Pod соответствует селектору.
3. **Сравнение:** Сравнивает с `replicas`.
4. **Действие:**
   - Если Pod меньше — создаёт новые из `template`.
   - Если Pod больше — удаляет лишние.
   - Если Pod ровно N — ничего не делает.

### Практика: работа с ReplicaSet

```bash
# Создать
kubectl apply -f replicaset.yaml

# Посмотреть
kubectl get replicasets
kubectl get rs
kubectl describe rs my-replicaset

# Посмотреть Pod, созданные RS
kubectl get pods -l app=nginx

# Удалить один Pod — RS создаст новый
kubectl delete pod <pod-name>
kubectl get pods -l app=nginx -w
```

**Что произойдёт:**

```bash
kubectl delete pod my-replicaset-abc123
# pod "my-replicaset-abc123" deleted

kubectl get pods -l app=nginx
# NAME                     READY   STATUS    RESTARTS   AGE
# my-replicaset-abc123     1/1     Terminating   0       5m
# my-replicaset-def456     1/1     Running       0       5m
# my-replicaset-ghi789     1/1     Running       0       5m
# my-replicaset-jkl012     1/1     ContainerCreating   0   2s  ← новый Pod
```

### Масштабирование ReplicaSet

```bash
# Изменить replicas вручную
kubectl scale rs my-replicaset --replicas=5

# Или отредактировать YAML
kubectl edit rs my-replicaset
```

### Ограничения ReplicaSet

ReplicaSet **не умеет**:
- Обновлять Pod (rolling update).
- Откатывать изменения.
- Хранить историю версий.

Если вы измените `template` в ReplicaSet — новые Pod будут создаваться по новому шаблону, но **старые Pod не будут обновлены**. ReplicaSet не удалит их, потому что они соответствуют `selector`.

> [!warning]
> **Не используйте ReplicaSet напрямую в production.** Используйте Deployment, который управляет ReplicaSet и добавляет rolling update и rollback.

## Deployment — управление версиями

> **Deployment** — контроллер, который управляет ReplicaSet и добавляет **декларативные обновления** приложений.

Deployment — это высокоуровневая абстракция. Вы описываете желаемое состояние, а Deployment создаёт ReplicaSet, который создаёт Pod. При обновлении Deployment создаёт **новый** ReplicaSet и постепенно переключает Pod.

### Манифест Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests:
              memory: "64Mi"
              cpu: "100m"
            limits:
              memory: "128Mi"
              cpu: "200m"
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `replicas` | Желаемое количество Pod |
| `selector` | Как Deployment находит свои Pod (и ReplicaSet) |
| `template` | Шаблон Pod |
| `strategy` | Стратегия обновления: `RollingUpdate` (по умолчанию) или `Recreate` |
| `strategy.rollingUpdate.maxSurge` | Сколько Pod можно создать **сверх** `replicas` при обновлении |
| `strategy.rollingUpdate.maxUnavailable` | Сколько Pod может быть **недоступно** при обновлении |
| `revisionHistoryLimit` | Сколько старых ReplicaSet хранить (по умолчанию 10) |
| `progressDeadlineSeconds` | Таймаут на прогресс обновления (по умолчанию 600) |

### Как работает Deployment

```
Deployment
    │
    ├── ReplicaSet (v1) ──→ Pod v1 ──→ Pod v1 ──→ Pod v1
    │
    └── ReplicaSet (v2) ──→ Pod v2  (при обновлении)
```

1. Deployment создаёт ReplicaSet с именем `<deployment-name>-<hash>`.
2. ReplicaSet создаёт Pod.
3. При обновлении `template` Deployment создаёт **новый** ReplicaSet.
4. Новый ReplicaSet масштабируется вверх, старый — вниз.
5. Старый ReplicaSet остаётся с `replicas: 0` для возможности отката.

### Стратегии обновления

#### RollingUpdate (по умолчанию)

Постепенное обновление без простоя.

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1          # Может быть числом или процентом (25%)
    maxUnavailable: 0    # Может быть числом или процентом (25%)
```

**Как работает с `maxSurge: 1`, `maxUnavailable: 0`, `replicas: 3`:**

| Шаг | Старый RS | Новый RS | Всего Pod | Доступно |
|-----|-----------|----------|-----------|----------|
| 0 | 3 | 0 | 3 | 3 |
| 1 | 3 | 1 | 4 | 3 (новый ещё не ready) |
| 2 | 2 | 2 | 4 | 4 |
| 3 | 1 | 3 | 4 | 4 |
| 4 | 0 | 3 | 3 | 3 |

> [!tip]
> `maxUnavailable: 0` гарантирует, что во время обновления всегда доступны все `replicas` Pod. Это важно для production.

#### Recreate

Все старые Pod удаляются, затем создаются новые. **Простой** между удалением и созданием.

```yaml
strategy:
  type: Recreate
```

**Когда использовать:** когда два экземпляра приложения не могут работать одновременно (например, миграции БД, singleton).

### Практика: работа с Deployment

```bash
# Создать
kubectl apply -f deployment.yaml

# Посмотреть
kubectl get deployments
kubectl get deploy
kubectl describe deploy my-deployment

# Посмотреть ReplicaSet
kubectl get rs

# Посмотреть Pod
kubectl get pods -l app=nginx

# Масштабировать
kubectl scale deploy my-deployment --replicas=5

# Посмотреть статус обновления
kubectl rollout status deploy my-deployment
```

### Обновление образа

```bash
# Способ 1: set image (императивно)
kubectl set image deploy/my-deployment nginx=nginx:1.26

# Способ 2: отредактировать YAML и применить (декларативно)
kubectl edit deploy my-deployment
# или
vim deployment.yaml  # изменить image на nginx:1.26
kubectl apply -f deployment.yaml
```

**Что произойдёт:**

1. Deployment создаст новый ReplicaSet с новым образом.
2. Новый RS начнёт создавать Pod.
3. Когда новые Pod станут ready — старый RS начнёт удалять Pod.
4. Процесс повторяется до полной замены.

**Наблюдение:**

```bash
kubectl get rs -w
kubectl get pods -l app=nginx -w
kubectl rollout status deploy my-deployment
```

### Откат (Rollback)

```bash
# История ревизий
kubectl rollout history deploy my-deployment

# Детали конкретной ревизии
kubectl rollout history deploy my-deployment --revision=2

# Откатить к предыдущей версии
kubectl rollout undo deploy my-deployment

# Откатить к конкретной ревизии
kubectl rollout undo deploy my-deployment --to-revision=1

# Пауза обновления (для canary)
kubectl rollout pause deploy my-deployment

# Возобновить
kubectl rollout resume deploy my-deployment
```

**Как работает откат:** Deployment просто переключается на старый ReplicaSet. Это мгновенно, потому что старый RS уже существует (с `replicas: 0`).

### Пауза и canary-деплой

Можно приостановить обновление, чтобы протестировать новую версию на части Pod.

```bash
# Создать Deployment
kubectl apply -f deployment.yaml

# Приостановить
kubectl rollout pause deploy my-deployment

# Обновить образ (создастся новый RS, но не будет масштабироваться)
kubectl set image deploy/my-deployment nginx=nginx:1.26

# Проверить, что новый RS создан с 0 реплик
kubectl get rs

# Вручную масштабировать новый RS для canary
kubectl scale rs my-deployment-<new-hash> --replicas=1

# Если всё хорошо — возобновить
kubectl rollout resume deploy my-deployment
```

## Deployment vs ReplicaSet: что выбрать

| Возможность | ReplicaSet | Deployment |
|-------------|------------|------------|
| Гарантия количества Pod | ✅ | ✅ |
| Rolling update | ❌ | ✅ |
| Rollback | ❌ | ✅ |
| История версий | ❌ | ✅ |
| Пауза обновления | ❌ | ✅ |
| Canary-деплой | ❌ | ✅ (с ручным вмешательством) |

**Вывод:** всегда используйте Deployment. ReplicaSet — это внутренний механизм Deployment.

> [!note]
> В старых версиях Kubernetes (до 1.16) был объект `ReplicationController` — предшественник ReplicaSet. Он не поддерживал set-based selectors. Не используйте его.

## Практический пример: полный цикл

### Шаг 1: Создать Deployment

**Файл `deployment.yaml`:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests:
              memory: "64Mi"
              cpu: "100m"
            limits:
              memory: "128Mi"
              cpu: "200m"
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 5
```

```bash
kubectl apply -f deployment.yaml
```

### Шаг 2: Проверить

```bash
kubectl get deploy web-app
kubectl get rs
kubectl get pods -l app=web
kubectl rollout status deploy web-app
```

### Шаг 3: Обновить образ

```bash
kubectl set image deploy/web-app web=nginx:1.26
kubectl rollout status deploy web-app
kubectl get rs
kubectl get pods -l app=web
```

### Шаг 4: Посмотреть историю

```bash
kubectl rollout history deploy web-app
```

**Пример вывода:**

```
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
```

`CHANGE-CAUSE` пустой, потому что мы не указали `kubernetes.io/change-cause` annotation. Добавим:

```bash
kubectl annotate deploy/web-app kubernetes.io/change-cause="Update nginx to 1.26"
```

### Шаг 5: Откатить

```bash
kubectl rollout undo deploy web-app
kubectl rollout status deploy web-app
kubectl get rs
```

### Шаг 6: Масштабировать

```bash
kubectl scale deploy web-app --replicas=5
kubectl get pods -l app=web
```

### Шаг 7: Удалить

```bash
kubectl delete -f deployment.yaml
```

## Продвинутые возможности

### Probes в Deployment

Probes определяются в `template.spec.containers[].livenessProbe` и т.д.

```yaml
template:
  spec:
    containers:
      - name: web
        image: nginx:1.25
        readinessProbe:
          httpGet:
            path: /ready
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 5
        livenessProbe:
          httpGet:
            path: /healthz
            port: 80
          initialDelaySeconds: 15
          periodSeconds: 10
```

### Resource requests и limits

```yaml
resources:
  requests:
    memory: "64Mi"
    cpu: "100m"
  limits:
    memory: "128Mi"
    cpu: "200m"
```

> [!important]
> Всегда указывайте requests. Без них scheduler не сможет корректно распределить Pod. Лимиты защищают узел от «прожорливых» Pod.

### Lifecycle hooks

```yaml
lifecycle:
  postStart:
    exec:
      command: ["/bin/sh", "-c", "echo 'Container started' >> /var/log/lifecycle.log"]
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]
```

- `postStart` — выполняется сразу после запуска контейнера.
- `preStop` — выполняется перед остановкой контейнера (важно для graceful shutdown).

### Termination grace period

```yaml
spec:
  terminationGracePeriodSeconds: 30
```

При удалении Pod kubelet:
1. Отправляет SIGTERM в контейнер.
2. Ждёт `terminationGracePeriodSeconds`.
3. Если контейнер не завершился — отправляет SIGKILL.

### Pod anti-affinity для HA

Чтобы Pod одного Deployment не оказались на одном узле:

```yaml
template:
  spec:
    affinity:
      podAntiAffinity:
        preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: web
              topologyKey: kubernetes.io/hostname
```

## Типичные ошибки

### Selector не совпадает с template labels

```yaml
spec:
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: nginx    # ← не совпадает!
```

**Результат:** Deployment создаст ReplicaSet, но RS не найдёт Pod и будет создавать бесконечно новые.

**Решение:** `selector.matchLabels` должен быть **подмножеством** `template.metadata.labels`.

### Обновление selector

**Selector в Deployment immutable.** Если вы попытаетесь изменить его — получите ошибку:

```
The Deployment "my-deployment" is invalid: spec.selector: Invalid value: ...: field is immutable
```

**Решение:** удалить и пересоздать Deployment (или использовать `kubectl replace --force`).

### maxUnavailable: 100% при replicas: 1

Если у вас `replicas: 1` и `maxUnavailable: 100%` — при обновлении Pod будет полностью удалён, и будет простой.

**Решение:** использовать `maxUnavailable: 0` и `maxSurge: 1`.

## Шпаргалка: основные команды

```bash
# Создание
kubectl apply -f deployment.yaml
kubectl create deployment my-deploy --image=nginx --replicas=3

# Просмотр
kubectl get deployments
kubectl get deploy -o wide

# Масштабирование
kubectl scale deploy my-deploy --replicas=5
kubectl autoscale deploy my-deploy --min=2 --max=10 --cpu-percent=80

kubectl set image deploy/my-deploy app=nginx:1.26
kubectl rollout status deploy/my-deploy
kubectl rollout history deploy/my-deploy
kubectl rollout undo deploy/my-deploy
kubectl rollout undo deploy/my-deploy --to-revision=1
kubectl rollout pause deploy/my-deploy
kubectl rollout resume deploy/my-deploy
kubectl rollout restart deploy/my-deploy

# Удаление
kubectl delete deploy my-deploy
kubectl delete -f deployment.yaml
```

## Итог

1. **ReplicaSet** гарантирует количество Pod. Не умеет обновлять.
2. **Deployment** управляет ReplicaSet и добавляет rolling update, rollback, историю.
3. **RollingUpdate** — стратегия по умолчанию. `maxSurge` и `maxUnavailable` контролируют процесс.
4. **Selector immutable.** Планируйте labels заранее.
5. **Selector должен совпадать с template labels.**
6. **Откат** — мгновенный, потому что старый ReplicaSet уже существует.
7. **Пауза** позволяет делать canary-деплой вручную.
8. **Всегда используйте Deployment** для stateless-приложений. ReplicaSet — внутренний механизм.

> [!tip]
> Для stateful-приложений (БД, очереди) используйте **StatefulSet**. Для запуска на каждом узле — **DaemonSet**. Для одноразовых задач — **Job**. Для периодических — **CronJob**. Deployment — для stateless-сервисов.
