# 01. Хранение данных: Volume, PV, PVC

Мы разобрались с сетью. Но есть ещё одна фундаментальная проблема: **данные**. Контейнеры эфемерны — при пересоздании Pod всё, что было записано в файловую систему контейнера, **исчезает**. Для stateless-приложений это нормально. Но для баз данных, очередей, файловых хранилищ — катастрофа.

В этой лекции разберём, как в Kubernetes организовано хранение данных: **Volume**, **PersistentVolume (PV)**, **PersistentVolumeClaim (PVC)**.

> **Главный принцип:** данные должны переживать пересоздание Pod. Хранилище должно быть **декларативным** и **абстрагированным** от конкретного Pod.

---

## Проблема: эфемерность контейнеров

Представьте Pod с PostgreSQL:

```
Pod postgres-abc123
  └── /var/lib/postgresql/data  ← данные БД
```

Что произойдёт, если:
- Pod упадёт и пересоздастся → **данные потеряны**.
- Вы обновите образ → **данные потеряны**.
- Узел упадёт → **данные потеряны**.

**Решение:** вынести данные **за пределы** жизненного цикла Pod. Для этого в Kubernetes есть **Volume**.

---

## Volume: базовое понятие

> **Volume** — это директория, доступная контейнерам в Pod. В отличие от файловой системы контейнера, Volume **переживает** перезапуск контейнера (но не всегда — пересоздание Pod).

### Типы Volume

| Тип | Жизненный цикл | Использование |
|-----|----------------|---------------|
| `emptyDir` | Живёт, пока жив Pod | Временные данные, кэш, обмен между контейнерами |
| `hostPath` | Живёт на узле | Доступ к файлам узла (опасно) |
| `configMap` | Из ConfigMap | Конфигурация |
| `secret` | Из Secret | Секреты |
| `persistentVolumeClaim` | Независим от Pod | Постоянные данные |
| `nfs` | Внешний NFS | Сетевое хранилище |
| `csi` | Через CSI-драйвер | Любое хранилище |

### emptyDir

> **emptyDir** — пустая директория, создаваемая при старте Pod. Удаляется при удалении Pod.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-cache
spec:
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: cache
          mountPath: /var/cache/app
    - name: sidecar
      image: busybox:1.36
      command: ["sh", "-c", "while true; do echo $(date) >> /var/log/app.log; sleep 5; done"]
      volumeMounts:
        - name: cache
          mountPath: /var/log
  volumes:
    - name: cache
      emptyDir: {}
```

**Когда использовать:**
- Кэш, временные файлы.
- Обмен данными между контейнерами в Pod.
- Scratch space для вычислений.

**Когда НЕ использовать:**
- Данные, которые должны пережить Pod.
- Базы данных.

**Вариант с памятью:**

```yaml
volumes:
  - name: cache
    emptyDir:
      medium: Memory      # tmpfs (RAM)
      sizeLimit: 100Mi
```

### hostPath

> **hostPath** — монтирует директорию с узла в Pod.

```yaml
volumes:
  - name: host-logs
    hostPath:
      path: /var/log
      type: Directory
```

**Типы:**

| type | Описание |
|------|----------|
| `DirectoryOrCreate` | Создать, если нет |
| `Directory` | Должна существовать |
| `FileOrCreate` | Создать файл |
| `File` | Файл должен существовать |
| `Socket` | Unix-сокет |
| `CharDevice` | Символьное устройство |
| `BlockDevice` | Блочное устройство |

> [!warning]
> **hostPath опасен.** Pod получает доступ к файловой системе узла. При компрометации Pod — компрометация узла. Используйте только для системных DaemonSet (логи, метрики).

### configMap и secret

Мы уже разбирали их в лекции про ConfigMap и Secret.

```yaml
volumes:
  - name: config
    configMap:
      name: app-config
  - name: secret
    secret:
      secretName: db-secret
```

## PersistentVolume (PV) и PersistentVolumeClaim (PVC)

> **PV** — это ресурс кластера, представляющий **физическое хранилище** (диск, NFS-шара, облачный том). **PVC** — это **запрос** на хранилище от Pod.

**Аналогия:**
- **PV** — это как сервер в дата-центре (физический ресурс).
- **PVC** — это как заявка «дайте мне 10 ГБ SSD».
- Pod использует PVC, а Kubernetes связывает PVC с подходящим PV.

### Архитектура

```
┌─────────────┐
│     Pod     │
│  ┌───────┐  │
│  │  PVC  │  │  ← Запрос: "10Gi, ReadWriteOnce"
│  └───┬───┘  │
└──────┼──────┘
       │
       ▼
┌─────────────┐
│     PV      │  ← Ресурс: 10Gi на SSD
│  (storage)  │
└─────────────┘
```

### Жизненный цикл PV

| Фаза | Описание |
|------|----------|
| `Available` | PV свободен, готов к связыванию |
| `Bound` | PV связан с PVC |
| `Released` | PVC удалён, PV ждёт очистки |
| `Failed` | Ошибка при связывании |

### PersistentVolume

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-manual
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/data
```

**Разбор:**

| Поле | Назначение |
|------|------------|
| `capacity.storage` | Размер |
| `accessModes` | Режим доступа |
| `persistentVolumeReclaimPolicy` | Что делать после удаления PVC |
| `storageClassName` | Класс хранилища |
| `hostPath` / `nfs` / `csi` | Тип хранилища |

### AccessModes

| Режим | Сокращение | Описание |
|-------|------------|----------|
| `ReadWriteOnce` | RWO | Один узел, чтение/запись |
| `ReadOnlyMany` | ROX | Много узлов, только чтение |
| `ReadWriteMany` | RWX | Много узлов, чтение/запись |
| `ReadWriteOncePod` | RWOP | Один Pod, чтение/запись (с v1.22) |

> [!important]
> AccessModes — это **не** права доступа. Это режим **монтирования**. RWO — не значит, что только один Pod может читать. Это значит, что том может быть смонтирован на **одном узле** для записи.

**Примеры:**

| Хранилище | Поддерживаемые режимы |
|-----------|----------------------|
| AWS EBS | RWO |
| AWS EFS | RWX |
| GCP PD | RWO |
| NFS | RWX, ROX |
| CephFS | RWX |
| Local SSD | RWO |

### persistentVolumeReclaimPolicy

| Политика | Поведение |
|----------|-----------|
| `Retain` | PV остаётся после удаления PVC, данные сохраняются. Требует ручной очистки |
| `Delete` | PV и хранилище удаляются автоматически |
| `Recycle` | Устаревшая, не рекомендуется |

> [!tip]
> Для production используйте **Retain** для критичных данных. Для временных — **Delete**.

### PersistentVolumeClaim

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-manual
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 10Gi
```

**Разбор:**

| Поле | Назначение |
|------|------------|
| `accessModes` | Запрашиваемый режим |
| `storageClassName` | Класс хранилища |
| `resources.requests.storage` | Запрашиваемый размер |
| `selector` | Селектор для выбора PV (опционально) |

### Связывание PV и PVC

Kubernetes связывает PVC с PV, если:
1. `storageClassName` совпадает.
2. `accessModes` совпадают.
3. `capacity >= requests.storage`.

**Пример:**

- PV: 10Gi, RWO, `storageClassName: manual`
- PVC: 5Gi, RWO, `storageClassName: manual`
- Результат: **Bound**. PVC получит 10Gi (весь PV).

> [!note]
> PVC и PV связываются **один к одному**. Нельзя связать один PV с несколькими PVC.

## Использование PVC в Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: postgres
spec:
  containers:
    - name: postgres
      image: postgres:16
      env:
        - name: POSTGRES_PASSWORD
          value: "secret"
        - name: PGDATA
          value: /var/lib/postgresql/data/pgdata
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: pvc-manual
```

**Что произойдёт:**
1. Pod монтирует PVC `pvc-manual`.
2. PVC связан с PV `pv-manual` (hostPath `/mnt/data`).
3. Данные в `/var/lib/postgresql/data` сохраняются на узле.
4. При пересоздании Pod — данные на месте.

## Практический пример: полный цикл

### Шаг 1: Создать PV вручную

**Файл `pv.yaml`:**

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-manual
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/data
```

```bash
kubectl apply -f pv.yaml
kubectl get pv
# NAME        CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM
# pv-manual   1Gi        RWO            Retain           Available
```

### Шаг 2: Создать PVC

**Файл `pvc.yaml`:**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-manual
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 1Gi
```

```bash
kubectl apply -f pvc.yaml
kubectl get pvc
# NAME         STATUS   VOLUME      CAPACITY   ACCESS MODES
# pvc-manual   Bound    pv-manual   1Gi        RWO
```

### Шаг 3: Создать Pod с PVC

**Файл `pod.yaml`:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "while true; do echo $(date) >> /data/log.txt; sleep 5; done"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: pvc-manual
```

```bash
kubectl apply -f pod.yaml
kubectl exec app -- cat /data/log.txt
```

### Шаг 4: Проверить персистентность

```bash
# Удалить Pod
kubectl delete pod app

# Создать снова
kubectl apply -f pod.yaml

# Данные на месте
kubectl exec app -- cat /data/log.txt
```

### Шаг 5: Удалить

```bash
kubectl delete pod app
kubectl delete pvc pvc-manual
kubectl delete pv pv-manual
```

**Обратите внимание:** после удаления PVC PV перешёл в фазу `Released`. Данные на hostPath остались. Для повторного использования нужно вручную очистить PV.

## StorageClass: динамическое выделение

Ручное создание PV — неудобно. Для каждого PVC нужно создавать PV. В production используют **StorageClass**.

> **StorageClass** — объект, описывающий **класс** хранилища и **provisioner**, который автоматически создаёт PV при создании PVC.

### Манифест StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

### Разбор

| Поле | Назначение |
|------|------------|
| `provisioner` | Драйвер, создающий PV (CSI, cloud, local) |
| `parameters` | Параметры для provisioner (тип диска, IOPS) |
| `reclaimPolicy` | Политика после удаления PVC |
| `allowVolumeExpansion` | Разрешить увеличение размера |
| `volumeBindingMode` | `Immediate` или `WaitForFirstConsumer` |
| `mountOptions` | Опции монтирования |

### volumeBindingMode

| Режим | Поведение |
|-------|----------|
| `Immediate` | PV создаётся сразу при создании PVC |
| `WaitForFirstConsumer` | PV создаётся, когда Pod запланирован на узел |

**`WaitForFirstConsumer`** важен для local-хранилищ: PV должен быть создан на том же узле, где будет Pod.

### Проверка StorageClass

```bash
kubectl get storageclass
kubectl get sc
# NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE
# fast-ssd             ebs.csi.aws.com         Delete          WaitForFirstConsumer
# standard (default)   kubernetes.io/gce-pd    Delete          Immediate
```

**Default StorageClass:** если PVC не указывает `storageClassName`, используется default.

```bash
kubectl patch storageclass fast-ssd -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
```

### PVC с динамическим выделением

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-dynamic
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi
```

**Что произойдёт:**
1. PVC создан.
2. StorageClass `fast-ssd` вызывает provisioner.
3. Provisioner создаёт диск в облаке (или локально).
4. Создаётся PV, связывается с PVC.
5. PVC в фазе `Bound`.

```bash
kubectl get pvc
# NAME          STATUS   VOLUME                                     CAPACITY
# pvc-dynamic   Bound    pvc-abc123-def456-ghi789                   10Gi
```

## CSI: Container Storage Interface

> **CSI** — стандартный интерфейс для подключения хранилищ к Kubernetes. Заменяет in-tree плагины.

### Как работает CSI

```
PVC → StorageClass → CSI Provisioner → CSI Driver → Хранилище
```

**Компоненты:**

| Компонент | Роль |
|-----------|------|
| **CSI Driver** | Реализация для конкретного хранилища (AWS EBS, Ceph, NFS) |
| **CSI Provisioner** | Создаёт/удаляет тома |
| **CSI Attacher** | Прикрепляет том к узлу |
| **CSI Resizer** | Изменяет размер тома |
| **CSI Snapshotter** | Создаёт снапшоты |

### Популярные CSI-драйверы

| Драйвер | Хранилище |
|---------|-----------|
| `ebs.csi.aws.com` | AWS EBS |
| `pd.csi.storage.gke.io` | GCP Persistent Disk |
| `disk.csi.azure.com` | Azure Disk |
| `rbd.csi.ceph.com` | Ceph RBD |
| `cephfs.csi.ceph.com` | CephFS |
| `nfs.csi.k8s.io` | NFS |
| `driver.longhorn.io` | Longhorn |
| `rook-ceph.rbd.csi.ceph.com` | Rook Ceph |

### Пример: установка AWS EBS CSI

```bash
# Создать IAM role (для EKS)
eksctl create iamserviceaccount \
  --name ebs-csi-controller-sa \
  --namespace kube-system \
  --cluster my-cluster \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve

# Установить addon
eksctl create addon --name aws-ebs-csi-driver --cluster my-cluster

# Или через Helm
helm repo add aws-ebs-csi-driver https://kubernetes-sigs.github.io/aws-ebs-csi-driver
helm install aws-ebs-csi-driver aws-ebs-csi-driver/aws-ebs-csi-driver -n kube-system
```

### Пример: Longhorn (для bare-metal)

```bash
helm repo add longhorn https://charts.longhorn.io
helm install longhorn longhorn/longhorn -n longhorn-system --create-namespace
```

**Longhorn** — распределённое блочное хранилище. Работает на любом Kubernetes.

## StatefulSet и volumeClaimTemplates

Мы уже разбирали StatefulSet. Каждый Pod получает **свой** PVC через `volumeClaimTemplates`.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: fast-ssd
        resources:
          requests:
            storage: 10Gi
```

**Что произойдёт:**
- `postgres-0` → PVC `data-postgres-0`
- `postgres-1` → PVC `data-postgres-1`
- `postgres-2` → PVC `data-postgres-2`

Каждый Pod получает **свой** PV.

## Volume Snapshots

> **VolumeSnapshot** — снапшот PV. Позволяет создавать резервные копии и клонировать тома.

### Компоненты

| Ресурс | Роль |
|--------|------|
| `VolumeSnapshotClass` | Класс снапшотов (provisioner, параметры) |
| `VolumeSnapshot` | Снапшот конкретного PVC |
| `VolumeSnapshotContent` | Созданный снапшот (аналог PV) |

### Пример

**VolumeSnapshotClass:**

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-snapclass
driver: ebs.csi.aws.com
deletionPolicy: Delete
```

**VolumeSnapshot:**

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: pvc-snapshot
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: pvc-dynamic
```

**Восстановление из снапшота:**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-restored
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi
  dataSource:
    name: pvc-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
```

## Расширение PVC

Если StorageClass имеет `allowVolumeExpansion: true`, можно увеличить размер PVC:

```bash
kubectl patch pvc pvc-dynamic -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

**Что произойдёт:**
1. PVC обновится.
2. Provisioner увеличит том.
3. Файловая система расширится (если поддерживается).

> [!warning]
> **Уменьшить PVC нельзя.** Только увеличить. Планируйте размер заранее.

## Типичные ошибки

### PVC в Pending

**Причины:**
- Нет подходящего PV.
- Нет StorageClass.
- `WaitForFirstConsumer`, но Pod не создан.

**Решение:**

```bash
kubectl describe pvc my-pvc
kubectl get pv
kubectl get storageclass
kubectl get events
```

### Pod не монтирует PVC

```
error: Unable to attach or mount volumes: unmounted volumes=[data]
```

**Причины:**
- PVC в другом namespace.
- PVC не Bound.
- Проблема с CSI-драйвером.

**Решение:**

```bash
kubectl describe pod my-pod
kubectl get pvc
kubectl logs -n kube-system <csi-driver-pod>
```

### Данные потеряны после удаления Pod

**Причина:** использовался `emptyDir`, а не PVC.

**Решение:** использовать PVC.

### PV не очищается

**Причина:** `persistentVolumeReclaimPolicy: Retain`.

**Решение:** вручную очистить PV:

```bash
kubectl delete pv pv-manual
# Очистить данные на хранилище
```

### AccessModes не совпадают

```
cannot bind to pv: accessModes mismatch
```

**Решение:** PVC и PV должны иметь совместимые `accessModes`.

## Итог

1. **Volume** — директория, доступная контейнерам. `emptyDir` — временный, `hostPath` — с узла.
2. **PV** — физическое хранилище. **PVC** — запрос на хранилище.
3. **PVC и PV связываются один к одному.**
4. **StorageClass** — динамическое выделение PV.
5. **CSI** — стандарт для подключения хранилищ.
6. **AccessModes:** RWO, ROX, RWX, RWOP.
7. **ReclaimPolicy:** Retain, Delete, Recycle.
8. **StatefulSet** использует `volumeClaimTemplates` для своих PVC.
9. **VolumeSnapshot** — снапшоты PV.
10. **PVC можно увеличить, но нельзя уменьшить.**

> [!tip]
> **Правило выбора:**
> - Временные данные → `emptyDir`
> - Доступ к узлу → `hostPath` (осторожно!)
> - Постоянные данные → PVC + StorageClass
> - БД в StatefulSet → `volumeClaimTemplates`
> - Bare-metal → Longhorn, Rook Ceph
> - Облако → managed CSI (EBS, PD, Azure Disk)

> [!warning]
> Никогда не используйте `hostPath` для данных БД в production. При падении узла данные потеряны. Используйте PVC с репликацией или внешнее хранилище.
