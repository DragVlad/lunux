# 02. Хранилище глубже: StorageClass, CSI, динамический provisioning

В прошлой лекции мы разобрались с базовой триадой: **Volume → PV → PVC**. Но ручное создание PV для каждого PVC — это боль. В production используют **динамическое выделение** через **StorageClass** и **CSI**. В этой лекции разберём их глубже.

> **Динамическое выделение (dynamic provisioning)** — это автоматическое создание PV при создании PVC. Вам не нужно вручную создавать PV — StorageClass и CSI-драйвер сделают это за вас.

---

## От статического к динамическому

### Статическое выделение (manual)

```
Администратор создаёт PV → Пользователь создаёт PVC → Kubernetes связывает
```

**Проблемы:**
- Администратор должен заранее создать PV.
- Если PV закончились — PVC в `Pending`.
- Нет автоматизации.
- Нет гибкости по размеру.

### Динамическое выделение (StorageClass)

```
Пользователь создаёт PVC → StorageClass вызывает provisioner → PV создаётся автоматически → PVC Bound
```

**Преимущества:**
- Автоматизация.
- Гибкость по размеру.
- Меньше ручной работы.
- Стандарт в production.

## StorageClass: подробно

> **StorageClass** — объект, описывающий **класс** хранилища и **provisioner**, который создаёт PV.

### Полный манифест StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  kmsKeyId: "arn:aws:kms:us-east-1:123456789012:key/abc-123"
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
mountOptions:
  - discard
  - noatime
allowedTopologies:
  - matchLabelExpressions:
      - key: topology.kubernetes.io/zone
        values:
          - us-east-1a
          - us-east-1b
```

### Разбор полей

| Поле | Назначение |
|------|------------|
| `provisioner` | Драйвер, создающий PV. **Обязательно** |
| `parameters` | Параметры для provisioner (зависят от драйвера) |
| `reclaimPolicy` | `Delete` (по умолчанию) или `Retain` |
| `allowVolumeExpansion` | Разрешить увеличение размера PVC |
| `volumeBindingMode` | `Immediate` или `WaitForFirstConsumer` |
| `mountOptions` | Опции монтирования (noatime, discard) |
| `allowedTopologies` | Ограничение зон/регионов |

### provisioner

| Provisioner | Хранилище |
|-------------|-----------|
| `kubernetes.io/aws-ebs` | AWS EBS (устаревший) |
| `ebs.csi.aws.com` | AWS EBS CSI |
| `pd.csi.storage.gke.io` | GCP Persistent Disk |
| `disk.csi.azure.com` | Azure Disk |
| `file.csi.azure.com` | Azure Files |
| `rbd.csi.ceph.com` | Ceph RBD |
| `cephfs.csi.ceph.com` | CephFS |
| `nfs.csi.k8s.io` | NFS |
| `driver.longhorn.io` | Longhorn |
| `rook-ceph.rbd.csi.ceph.com` | Rook Ceph |
| `kubernetes.io/no-provisioner` | Локальные PV (без динамики) |

> [!note]
> `kubernetes.io/no-provisioner` используется для **local** PV — когда PV создаются вручную, но связываются через StorageClass.

### parameters (зависят от драйвера)

**AWS EBS:**

```yaml
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  fsType: ext4
```

**GCP PD:**

```yaml
parameters:
  type: pd-ssd
  replication-type: regional-pd
  zones: us-central1-a,us-central1-b
```

**Azure Disk:**

```yaml
parameters:
  skuName: Premium_LRS
  kind: Managed
  cachingmode: ReadOnly
```

**Ceph RBD:**

```yaml
parameters:
  clusterID: <cluster-id>
  pool: rbd
  imageFormat: "2"
  imageFeatures: layering
  csi.storage.k8s.io/provisioner-secret-name: ceph-secret
  csi.storage.k8s.io/provisioner-secret-namespace: default
```

**Longhorn:**

```yaml
parameters:
  numberOfReplicas: "3"
  staleReplicaTimeout: "30"
  fromBackup: ""
  fsType: ext4
```

### reclaimPolicy

| Политика | Поведение | Когда использовать |
|----------|-----------|-------------------|
| `Delete` | PV и хранилище удаляются при удалении PVC | Временные данные |
| `Retain` | PV остаётся, данные сохраняются | Критичные данные |

> [!important]
> **`Retain` — не значит «безопасно».** После удаления PVC PV переходит в фазу `Released`. Его нельзя переиспользовать, пока не очистите вручную. Данные на хранилище остаются, но PV нужно пересоздать.

### volumeBindingMode

| Режим | Поведение | Когда использовать |
|-------|-----------|-------------------|
| `Immediate` | PV создаётся сразу при создании PVC | Облачные хранилища (EBS, PD) |
| `WaitForFirstConsumer` | PV создаётся, когда Pod запланирован на узел | Local-хранилища, multi-zone |

**`WaitForFirstConsumer`** решает проблему: если PV создан в зоне `us-east-1a`, а Pod запланирован в `us-east-1b` — том не смонтируется. С `WaitForFirstConsumer` PV создаётся в той же зоне, что и Pod.

### allowedTopologies

Ограничивает, в каких зонах можно создавать PV:

```yaml
allowedTopologies:
  - matchLabelExpressions:
      - key: topology.kubernetes.io/zone
        values:
          - us-east-1a
          - us-east-1b
```

### Default StorageClass

Если PVC не указывает `storageClassName`, используется default. Пометить StorageClass как default:

```bash
kubectl patch storageclass fast-ssd -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
```

**Проверка:**

```bash
kubectl get sc
# NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE
# fast-ssd (default)   ebs.csi.aws.com         Delete          WaitForFirstConsumer
```

> [!warning]
> В кластере может быть **только один** default StorageClass. Если два — поведение непредсказуемо.

## CSI: Container Storage Interface

> **CSI** — стандартный интерфейс для подключения хранилищ к Kubernetes. Заменяет in-tree плагины.

### Зачем CSI

До CSI каждый драйвер хранилища был **встроен** в Kubernetes (in-tree). Это означало:
- Обновление драйвера = обновление Kubernetes.
- Баги в драйвере = баги в Kubernetes.
- Медленный релизный цикл.

**CSI** вынес драйверы из ядра Kubernetes. Теперь драйверы:
- Разрабатываются независимо.
- Обновляются отдельно.
- Устанавливаются как обычные Pod.

### Архитектура CSI

```
┌──────────────────────────────────────────────────────────────┐
│                       Kubernetes                              │
│                                                               │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐        │
│  │   kube-      │  │   kube-      │  │   kube-      │        │
│  │  apiserver   │  │  controller  │  │  scheduler   │        │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘        │
│         │                 │                 │                │
│         └─────────────────┼─────────────────┘                │
│                           │                                  │
│                    ┌──────▼───────┐                          │
│                    │  CSI Driver  │                          │
│                    │              │                          │
│                    │ ┌──────────┐ │                          │
│                    │ │Controller│ │  ← Deployment            │
│                    │ │  Plugin  │ │                          │
│                    │ └──────────┘ │                          │
│                    │ ┌──────────┐ │                          │
│                    │ │  Node    │ │  ← DaemonSet             │
│                    │ │  Plugin  │ │                          │
│                    │ └──────────┘ │                          │
│                    └──────┬───────┘                          │
│                           │                                  │
│                    ┌──────▼───────┐                          │

│                    │  (EBS, Ceph) │                          │
│                    └──────────────┘                          │
└──────────────────────────────────────────────────────────────┘
```

### Компоненты CSI

| Компонент | Роль | Запуск |
|-----------|------|--------|
| **CSI Driver** | Реализация для конкретного хранилища | DaemonSet + Deployment |
| **CSI Provisioner** | Создаёт/удаляет тома | Sidecar в controller |
| **CSI Attacher** | Прикрепляет том к узлу | Sidecar в controller |
| **CSI Resizer** | Изменяет размер тома | Sidecar в controller |
| **CSI Snapshotter** | Создаёт снапшоты | Sidecar в controller |
| **CSI Node Driver Registrar** | Регистрирует драйвер на узле | Sidecar в node |

**Controller Plugin** (Deployment):
- `csi-provisioner` — создаёт тома.
- `csi-attacher` — attach/detach.
- `csi-resizer` — resize.
- `csi-snapshotter` — snapshots.
- `csi-driver` — сам драйвер.

**Node Plugin** (DaemonSet):
- `csi-driver` — монтирует том на узел.
- `node-driver-registrar` — регистрирует драйвер.

## Динамический provisioning: полный цикл

### Шаг 1: StorageClass создан

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

### Шаг 2: PVC создан

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi
```

### Шаг 3: Что происходит

1. PVC создан, статус `Pending`.
2. `volumeBindingMode: WaitForFirstConsumer` — PV не создаётся сразу.
3. Pod создан и запланирован на узел в зоне `us-east-1a`.
4. CSI Provisioner создаёт EBS volume в `us-east-1a`.
5. Создаётся PV, связывается с PVC.
6. PVC → `Bound`.
7. CSI Attacher прикрепляет том к узлу.
8. kubelet монтирует том в Pod.

### Шаг 4: Проверка

```bash
kubectl get pvc my-pvc
# NAME     STATUS   VOLUME                                     CAPACITY
# my-pvc   Bound    pvc-abc123-def456-ghi789                   10Gi

kubectl get pv
# NAME                                       CAPACITY   STATUS   CLAIM
# pvc-abc123-def456-ghi789                   10Gi       Bound    default/my-pvc

kubectl get volumeattachments
# NAME                          ATTACHER          PV                       NODE
# csi-abc123...                 ebs.csi.aws.com   pvc-abc123-def456-ghi789  node-1
```

### Шаг 5: Удаление

```bash
kubectl delete pvc my-pvc
# PV удаляется (reclaimPolicy: Delete)
# EBS volume удаляется в AWS
```

## Расширение PVC

Если StorageClass имеет `allowVolumeExpansion: true`, можно увеличить размер PVC:

```bash
kubectl patch pvc my-pvc -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
```

**Что произойдёт:**
1. PVC обновится.
2. CSI Resizer увеличит том.
3. Файловая система расширится (если поддерживается).

**Проверка:**

```bash
kubectl get pvc my-pvc
# NAME     STATUS   VOLUME    CAPACITY   ACCESS MODES
# my-pvc   Bound    pvc-...   20Gi       RWO

kubectl describe pvc my-pvc | grep -A5 "Conditions"
```

**Ограничения:**
- **Уменьшить PVC нельзя.**
- Не все CSI-драйверы поддерживают expansion.
- Для некоторых ФС (ext4) нужно расширить ФС внутри Pod.

## Volume Snapshots

> **VolumeSnapshot** — снапшот PV. Позволяет создавать резервные копии и клонировать тома.

### Компоненты

| Ресурс | Роль |
|--------|------|
| `VolumeSnapshotClass` | Класс снапшотов (provisioner, параметры) |
| `VolumeSnapshot` | Снапшот конкретного PVC |
| `VolumeSnapshotContent` | Созданный снапшот (аналог PV) |

### Установка CSI Snapshotter

```bash
# CRDs
kubectl apply -f https://raw.githubusercontent.com/kubernetes-csi/external-snapshotter/master/client/config/crd/snapshot.storage.k8s.io_volumesnapshotclasses.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes-csi/external-snapshotter/master/client/config/crd/snapshot.storage.k8s.io_volumesnapshotcontents.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes-csi/external-snapshotter/master/client/config/crd/snapshot.storage.k8s.io_volumesnapshots.yaml

# Controller
kubectl apply -f https://raw.githubusercontent.com/kubernetes-csi/external-snapshotter/master/deploy/kubernetes/snapshot-controller/rbac-snapshot-controller.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes-csi/external-snapshotter/master/deploy/kubernetes/snapshot-controller/setup-snapshot-controller.yaml
```

### VolumeSnapshotClass

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-snapclass
driver: ebs.csi.aws.com
deletionPolicy: Delete
parameters:
  tagSpecification_1: "Name=snapshot-test"
```

### VolumeSnapshot

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: pvc-snapshot
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: my-pvc
```

**Проверка:**

```bash
kubectl get volumesnapshot
# NAME           READYTOUSE   SOURCEPVC   SOURCESNAPSHOTCONTENT   RESTORESIZE
# pvc-snapshot   true         my-pvc                              10Gi

kubectl get volumesnapshotcontent
```

### Восстановление из снапшота

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-restored
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi
  dataSource:
    name: pvc-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
```

### Клонирование PVC

Можно клонировать PVC без снапшота:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-clone
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi
  dataSource:
    name: my-pvc
    kind: PersistentVolumeClaim
```

## Локальные хранилища (Local PV)

> **Local PV** — PV, привязанный к конкретному узлу. Использует локальные диски (SSD, NVMe).

### Когда использовать

- Высокая производительность (нет сети).
- БД, требующие низкой latency.
- Когда нет сетевого хранилища.

### Проблемы

- **Нет репликации.** Узел упал — данные недоступны.
- **Pod привязан к узлу.** Нельзя перепланировать.
- **Ручное управление.** Нет динамического provisioning (кроме local-path-provisioner).

### Local PV манифест

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-pv-1
spec:
  capacity:
    storage: 100Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-storage
  local:
    path: /mnt/disks/ssd1
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - node-1
```

**StorageClass:**

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-storage
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
```

**PVC:**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: local-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: local-storage
  resources:
    requests:
      storage: 100Gi
```

**Pod:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: local-pvc
```

### Local Path Provisioner

Для динамического создания Local PV:

```bash
kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/master/deploy/local-path-storage.yaml
```

**StorageClass:**

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-path
provisioner: rancher.io/local-path
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
```

## Сравнение хранилищ

| Хранилище | Тип | AccessModes | Производительность | Репликация | Использование |
|-----------|-----|-------------|-------------------|------------|---------------|
| **AWS EBS** | Блочное | RWO | Высокая | Нет | Облако AWS |
| **AWS EFS** | Файловое | RWX | Средняя | Да | Облако AWS |
| **GCP PD** | Блочное | RWO | Высокая | Нет | Облако GCP |
| **Azure Disk** | Блочное | RWO | Высокая | Нет | Облако Azure |
| **Ceph RBD** | Блочное | RWO | Высокая | Да | On-prem |
| **CephFS** | Файловое | RWX | Средняя | Да | On-prem |
| **Longhorn** | Блочное | RWO | Средняя | Да | Bare-metal |
| **NFS** | Файловое | RWX | Низкая | Зависит | On-prem |
| **Local PV** | Блочное | RWO | Очень высокая | Нет | Bare-metal |
| **hostPath** | Локальное | RWO | Очень высокая | Нет | Не для production |

### Когда что выбирать

| Сценарий | Хранилище |
|----------|-----------|
| БД в облаке | EBS, PD, Azure Disk |
| БД on-prem | Ceph RBD, Local PV |
| Shared files (RWX) | EFS, CephFS, NFS |
| Bare-metal без Ceph | Longhorn |
| Максимальная производительность | Local PV (NVMe) |
| Простой кластер | Longhorn, local-path |
| Multi-zone | `WaitForFirstConsumer` + облачный CSI |

## Troubleshooting

### PVC в Pending

**Причины:**
- Нет StorageClass.
- Нет provisioner.
- `WaitForFirstConsumer`, но Pod не создан.
- Недостаточно capacity в хранилище.

**Решение:**

```bash
kubectl describe pvc my-pvc
kubectl get storageclass
kubectl get pods -n kube-system | grep csi
kubectl logs -n kube-system <csi-provisioner-pod>
kubectl get events --sort-by=.metadata.creationTimestamp
```

### Pod не монтирует PVC

```
error: Unable to attach or mount volumes: unmounted volumes=[data]
```

**Причины:**
- PVC в другом namespace.
- PVC не Bound.
- CSI-драйвер не работает на узле.
- Том в другой зоне.

**Решение:**

```bash
kubectl describe pod my-pod
kubectl get pvc
kubectl get volumeattachments
kubectl logs -n kube-system <csi-node-pod>
```

### VolumeAttachment застрял

```
kubectl get volumeattachments
# NAME          ATTACHER         PV          NODE     ATTACHED
# csi-abc123    ebs.csi.aws.com  pvc-...     node-1   false
```

**Решение:**

```bash
kubectl describe volumeattachment csi-abc123
# Если узел удалён — удалить вручную
kubectl delete volumeattachment csi-abc123
```

### Расширение PVC не работает

**Причины:**
- `allowVolumeExpansion: false` в StorageClass.
- CSI-драйвер не поддерживает expansion.
- ФС не поддерживает online expansion.

**Решение:**

```bash
kubectl describe pvc my-pvc | grep -A5 "Conditions"
kubectl get storageclass fast-ssd -o yaml | grep allowVolumeExpansion
```

### Snapshot не создаётся

**Причины:**
- CRDs не установлены.
- Snapshot Controller не запущен.
- CSI-драйвер не поддерживает snapshots.

**Решение:**

```bash
kubectl get crd | grep snapshot
kubectl get pods -n kube-system | grep snapshot
kubectl describe volumesnapshot my-snapshot
```

## Best practices

| Практика | Почему |
|----------|--------|
| Использовать `WaitForFirstConsumer` | Избежать создания PV в неправильной зоне |
| `reclaimPolicy: Retain` для критичных данных | Защита от случайного удаления |
| `allowVolumeExpansion: true` | Возможность увеличить размер |
| Не использовать `hostPath` в production | Опасно, привязка к узлу |
| Мониторить capacity | Предотвратить исчерпание |
| Использовать snapshots | Резервное копирование |
| Проверять CSI-драйвер | Совместимость с Kubernetes |
| Не использовать default StorageClass без нужды | Явность лучше неявности |
| Планировать размер PVC | Нельзя уменьшить |
| Использовать `volumeBindingMode: WaitForFirstConsumer` | Для multi-zone кластеров |

# StorageClass

## Итог

1. **StorageClass** — динамическое выделение PV.
2. **provisioner** — драйвер, создающий PV (CSI).
3. **volumeBindingMode:** `Immediate` vs `WaitForFirstConsumer`.
4. **reclaimPolicy:** `Delete` vs `Retain`.
5. **allowVolumeExpansion** — увеличение PVC.
6. **CSI** — стандарт для подключения хранилищ.
7. **VolumeSnapshot** — снапшоты PV.
8. **Local PV** — высокая производительность, но нет репликации.
9. **Longhorn, Rook Ceph** — для bare-metal.
10. **PVC можно увеличить, но нельзя уменьшить.**

> [!tip]
> **Правило выбора хранилища:**
> - Облако → managed CSI (EBS, PD, Azure Disk)
> - Bare-metal с репликацией → Longhorn, Rook Ceph
> - Максимальная производительность → Local PV (NVMe)
> - Shared files (RWX) → EFS, CephFS, NFS
> - Простой кластер → Longhorn, local-path

> [!warning]
> Никогда не используйте `hostPath` для данных в production. Это опасно и непортируемо.
