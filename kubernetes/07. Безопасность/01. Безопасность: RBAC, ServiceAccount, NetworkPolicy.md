# 01. Безопасность: RBAC, ServiceAccount, NetworkPolicy

Мы научились запускать приложения, управлять ресурсами, настраивать сеть и хранилища. Но кто имеет доступ к кластеру? Кто может создавать Pod? Кто может читать Secret? Кто может общаться с какими Pod?

В этой лекции разберём **три столпа безопасности Kubernetes**: **RBAC**, **ServiceAccount** и **NetworkPolicy**.

> **Безопасность в Kubernetes** строится на принципе **наименьших привилегий**: каждый компонент и пользователь должны иметь только те права, которые необходимы для выполнения задач.

---

## Часть 1: Аутентификация, авторизация, admission

Прежде чем говорить о RBAC, важно понять **три этапа** обработки запроса в Kubernetes.

### Этап 1: Аутентификация (Authentication)

**Кто вы?** API-сервер проверяет вашу личность.

| Метод | Описание |
|-------|----------|
| **Client Certificates** | X.509 сертификаты (kubectl, kubelet) |
| **Bearer Tokens** | ServiceAccount tokens |
| **Basic Auth** | Устаревший, не рекомендуется |
| **OIDC** | OpenID Connect (Google, Azure AD, Okta) |
| **Webhook** | Внешний сервис аутентификации |
| **Authenticating Proxy** | Прокси с сертификатом |

**Результат:** API-сервер знает **кто** вы (username, groups).

### Этап 2: Авторизация (Authorization)

**Что вам можно?** API-сервер проверяет права.

| Режим | Описание |
|-------|----------|
| **RBAC** | Role-Based Access Control (стандарт) |
| **ABAC** | Attribute-Based Access Control (устаревший) |
| **Node** | Для kubelet |
| **Webhook** | Внешний сервис авторизации |
| **AlwaysAllow** | Разрешить всё (не для production) |
| **AlwaysDeny** | Запретить всё |

**Результат:** API-сервер знает, **можно ли** выполнить запрос.

### Этап 3: Admission Control

**Можно ли это сделать?** Admission-контроллеры проверяют и модифицируют запрос.

| Контроллер | Роль |
|------------|------|
| **PodSecurity** | Проверяет security context Pod |
| **ResourceQuota** | Проверяет квоты |
| **LimitRanger** | Применяет дефолтные limits |
| **ValidatingAdmissionWebhook** | Внешняя валидация |
| **MutatingAdmissionWebhook** | Внешняя модификация |
| **NodeRestriction** | Ограничивает kubelet |

**Результат:** запрос либо принят, либо отклонён.

## Часть 2: ServiceAccount

> **ServiceAccount** — идентичность для **Pod** (не для человека). Используется для доступа Pod к API-серверу.

### Зачем нужен ServiceAccount

Когда Pod обращается к API-серверу (например, для чтения ConfigMap), он должен **аутентифицироваться**. ServiceAccount предоставляет токен для этого.

**Примеры использования:**
- Prometheus читает метрики Pod.
- Operator управляет CRD.
- CI/CD создаёт Deployment.
- Приложение читает Secret.

### Default ServiceAccount

В каждом namespace автоматически создаётся `default` ServiceAccount. Если Pod не указывает `serviceAccountName`, используется `default`.

```bash
kubectl get serviceaccounts
kubectl get sa
# NAME      SECRETS   AGE
# default   0         10d
```

> [!warning]
> **Default ServiceAccount имеет минимальные права.** Но если вы дадите ему права — все Pod в namespace получат их. Лучше создавать отдельные ServiceAccount для каждого приложения.

### Создание ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: prometheus
  namespace: monitoring
```

```bash
kubectl create serviceaccount prometheus -n monitoring
```

### Использование в Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  serviceAccountName: prometheus
  containers:
    - name: app
      image: myapp:1.0
```

### Токен ServiceAccount

**До Kubernetes 1.24:** токен хранился в Secret и монтировался в Pod.

**С 1.24:** используется **TokenRequest API** — токен создаётся динамически и монтируется через projected volume.

```bash
kubectl exec my-pod -- cat /var/run/secrets/kubernetes.io/serviceaccount/token
kubectl exec my-pod -- cat /var/run/secrets/kubernetes.io/serviceaccount/namespace
kubectl exec my-pod -- cat /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
```

### Автоматическое монтирование

По умолчанию ServiceAccount токен монтируется в Pod. Можно отключить:

```yaml
spec:
  automountServiceAccountToken: false
```

> [!tip]
> Если Pod не обращается к API-серверу — отключите автомонтирование токена. Это уменьшает поверхность атаки.

### imagePullSecrets

ServiceAccount может содержать `imagePullSecrets` для приватных registry:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app
imagePullSecrets:
  - name: regcred
```

Теперь все Pod с этим ServiceAccount смогут скачивать образы из приватного registry.

## Часть 3: RBAC (Role-Based Access Control)

> **RBAC** — механизм авторизации на основе ролей. Определяет, **кто** (subject) может **что** (verb) делать с **какими** ресурсами.

### Компоненты RBAC

| Компонент | Роль | Namespaced |
|-----------|------|------------|
| **Role** | Набор правил в namespace | ✅ |
| **ClusterRole** | Набор правил в кластере | ❌ |
| **RoleBinding** | Связывает Role с subject в namespace | ✅ |
| **ClusterRoleBinding** | Связывает ClusterRole с subject в кластере | ❌ |

### Subject (кто)

| Subject | Описание |
|---------|----------|
| **User** | Человек (по сертификату, OIDC) |
| **Group** | Группа пользователей |
| **ServiceAccount** | Идентичность Pod |

### Verb (что)

| Verb | Описание |
|------|----------|
| `get` | Читать объект |
| `list` | Список объектов |
| `watch` | Следить за изменениями |
| `create` | Создавать |
| `update` | Обновлять |
| `patch` | Частично обновлять |
| `delete` | Удалять |
| `deletecollection` | Удалять коллекцию |

### Resource (с чем)

| Resource | Описание |
|----------|----------|
| `pods` | Pod |
| `deployments` | Deployment |
| `services` | Service |
| `secrets` | Secret |
| `configmaps` | ConfigMap |
| `nodes` | Node |
| `*` | Все ресурсы |

### Role: пример

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
```

**Что разрешает:** читать Pod и их логи в namespace `default`.

### RoleBinding: пример

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
  - kind: User
    name: jane
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: prometheus
    namespace: monitoring
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**Что разрешает:** пользователь `jane` и ServiceAccount `prometheus` могут читать Pod в namespace `default`.

### ClusterRole: пример

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

**Что разрешает:** читать Node и Pod **во всех namespace**.

### ClusterRoleBinding: пример

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: read-nodes
subjects:
  - kind: User
    name: admin
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: node-reader
  apiGroup: rbac.authorization.k8s.io
```

**Что разрешает:** пользователь `admin` может читать Node и Pod во всём кластере.

### Role vs ClusterRole

| Role | ClusterRole |
|------|-------------|
| Только в namespace | Во всём кластере |
| Для namespaced ресурсов | Для cluster-scoped ресурсов |
| Создаётся в namespace | Глобальный |

**ClusterRole можно использовать с RoleBinding** — тогда права будут ограничены namespace.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
  - kind: ServiceAccount
    name: prometheus
    namespace: monitoring
roleRef:
  kind: ClusterRole      # ← ClusterRole
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**Что разрешает:** ServiceAccount `prometheus` может читать Pod **только в namespace `default`** (благодаря RoleBinding).

### Агрегированные ClusterRole

Можно объединять ClusterRole через `aggregationRule`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring
aggregationRule:
  clusterRoleSelectors:
    - matchLabels:
        rbac.example.com/aggregate-to-monitoring: "true"
rules: []   # заполняется автоматически
```

### Встроенные ClusterRole

Kubernetes имеет встроенные ClusterRole:

| ClusterRole | Права |
|-------------|-------|
| `cluster-admin` | Полный доступ |
| `admin` | Полный доступ в namespace |
| `edit` | Редактирование в namespace |
| `view` | Только чтение в namespace |

**Просмотр:**

```bash
kubectl get clusterroles
kubectl describe clusterrole cluster-admin
```

### Проверка прав

```bash
# Могу ли я?
kubectl auth can-i create pods
kubectl auth can-i create pods --as=jane
kubectl auth can-i create pods --as=system:serviceaccount:default:prometheus
kubectl auth can-i create pods -n monitoring

# Что я могу?
kubectl auth can-i --list
kubectl auth can-i --list --as=jane
```

### Практический пример: Prometheus ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: prometheus
  namespace: monitoring
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: prometheus
rules:
  - apiGroups: [""]
    resources: ["nodes", "nodes/metrics", "services", "endpoints", "pods"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get"]
  - nonResourceURLs: ["/metrics"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: prometheus
subjects:
  - kind: ServiceAccount
    name: prometheus
    namespace: monitoring
roleRef:
  kind: ClusterRole
  name: prometheus
  apiGroup: rbac.authorization.k8s.io
```

### Best practices RBAC

| Практика | Почему |
|----------|--------|
| Принцип наименьших привилегий | Минимизировать ущерб |
| Не использовать `cluster-admin` | Слишком много прав |
| Отдельный ServiceAccount на приложение | Изоляция |
| Не использовать `default` ServiceAccount | Все Pod получат права |
| `automountServiceAccountToken: false` | Если не нужен API |
| Регулярный аудит RBAC | Найти избыточные права |
| Использовать Groups | Упростить управление |
| Не давать `create pods` без нужды | Может привести к эскалации |

> [!warning]
> **`create pods` — опасно.** Pod может смонтировать `hostPath`, использовать `privileged: true`, украсть токены других ServiceAccount. Давайте это право только доверенным subject.

## Часть 4: NetworkPolicy

> **NetworkPolicy** — firewall на уровне Pod. По умолчанию весь трафик разрешён. С NetworkPolicy — запрещён, кроме явно разрешённого.

### Зачем нужна NetworkPolicy

По умолчанию в Kubernetes **все Pod могут общаться со всеми**. Это удобно, но небезопасно:
- Скомпрометированный Pod может сканировать сеть.
- Pod в dev может обращаться к prod.
- Нет изоляции между командами.

NetworkPolicy решает эти проблемы.

### Требования

NetworkPolicy **требует CNI с поддержкой**:
- ✅ Calico
- ✅ Cilium
- ✅ Weave Net
- ✅ Antrea
- ❌ Flannel (без дополнений)

### Default deny all

**Самый важный пример.** Запретить весь трафик в namespace.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

**Что произойдёт:**
- Все Pod в `production` не могут принимать трафик.
- Все Pod в `production` не могут отправлять трафик.

### Разрешить входящий трафик от frontend

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-frontend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

**Что разрешает:** Pod с `app: backend` принимают трафик от Pod с `app: frontend` на порт 8080.

### Разрешить исходящий трафик к БД

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-to-db
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Egress
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: database
      ports:
        - protocol: TCP
          port: 5432
```

**Что разрешает:** Pod с `app: backend` могут отправлять трафик к Pod с `app: database` на порт 5432.

### Разрешить DNS

**Важно:** если вы запрещаете egress, нужно разрешить DNS. Иначе Pod не сможет резолвить имена.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
```

### Разрешить трафик из namespace

```yaml
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            name: monitoring
```

**Что разрешает:** трафик из namespace `monitoring`.

### Комбинация podSelector и namespaceSelector

```yaml
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            name: production
        podSelector:
          matchLabels:
            app: frontend
```

**Что разрешает:** трафик от Pod с `app: frontend` **в** namespace `production`.

> [!note]
> `namespaceSelector` и `podSelector` в одном элементе — **AND**. В разных элементах — **OR**.

### Разрешить трафик из IP-блока

```yaml
ingress:
  - from:
      - ipBlock:
          cidr: 10.0.0.0/8
          except:
            - 10.0.1.0/24
```

**Что разрешает:** трафик из `10.0.0.0/8`, кроме `10.0.1.0/24`.

### Практический пример: полная изоляция

```yaml

  name: default-deny-all

    - Egress
---

# 3. Разрешить frontend → backend

  name: allow-frontend-to-backend
  namespace: production

  podSelector:
    matchLabels:
      app: backend

    - Ingress

    - from:
        - podSelector:

        - protocol: TCP
          port: 8080
---
# 4. Разрешить backend → database
apiVersion: networking.k8s.io/v1

  name: allow-backend-to-db
  namespace: production

  podSelector:
    matchLabels:
      app: backend
```

**Результат:**
- Весь трафик запрещён.
- DNS разрешён.
- Frontend → backend разрешён.
- Backend → database разрешён.
- Всё остальное — запрещено.

### Best practices NetworkPolicy

| Практика | Почему |
|----------|--------|
| Default deny all | Начать с запрета всего |
| Разрешать только нужное | Принцип наименьших привилегий |
| Не забывать DNS | Иначе Pod не резолвят имена |
| Тестировать политики | Можно заблокировать себя |
| Использовать namespaceSelector | Изоляция между командами |
| Мониторить blocked трафик | Cilium Hubble, Calico logs |
| Версионировать политики | GitOps |

> [!warning]
> NetworkPolicy **не шифрует** трафик. Для шифрования используйте service mesh (Istio, Linkerd) или WireGuard (Cilium).

## Часть 5: Pod Security

> **Pod Security** — контроль security context Pod. Реализуется через **Pod Security Standards (PSS)** и **Pod Security Admission (PSA)**.

### Pod Security Standards

| Уровень | Описание |
|---------|----------|
| **Privileged** | Без ограничений |
| **Baseline** | Минимальные ограничения (нет privileged, hostNetwork) |
| **Restricted** | Строгие ограничения (non-root, read-only FS) |

### Pod Security Admission

**Namespace labels:**

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

**Что произойдёт:** Pod, не соответствующие `restricted`, будут отклонены.

### Security Context

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: myapp:1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop:
            - ALL
          add:
            - NET_BIND_SERVICE
```

### Best practices Security Context

| Практика | Почему |
|----------|--------|
| `runAsNonRoot: true` | Не запускать от root |
| `readOnlyRootFilesystem: true` | Защита от модификации |
| `allowPrivilegeEscalation: false` | Запрет эскалации |
| `capabilities.drop: [ALL]` | Убрать все capabilities |
| `seccompProfile: RuntimeDefault` | Ограничить syscalls |

## Troubleshooting

### Pod не может обратиться к API

```
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:default:my-sa" cannot list resource "pods"
```

**Причина:** нет RBAC.

**Решение:**

```bash
kubectl auth can-i list pods --as=system:serviceaccount:default:my-sa
# Создать Role/ClusterRole и Binding
```

### ServiceAccount не найден

```
Error: serviceaccount "my-sa" not found
```

**Решение:** создать ServiceAccount в том же namespace, что и Pod.

### NetworkPolicy блокирует трафик

**Причина:** default deny, но не разрешён нужный трафик.

**Решение:**

```bash
kubectl get networkpolicies -n production
kubectl describe networkpolicy default-deny-all -n production
# Добавить разрешающую политику
```

### DNS не работает после NetworkPolicy

**Причина:** egress запрещён, DNS не разрешён.

**Решение:** добавить NetworkPolicy для DNS.

### Pod Security отклоняет Pod

```
Error: pods "my-pod" is forbidden: violates PodSecurity "restricted:latest"
```

**Решение:**

```bash
kubectl describe namespace production
# Проверить labels
# Исправить securityContext
```

## Шпаргалка: основные команды

```bash
# ServiceAccount
kubectl get serviceaccounts
kubectl get sa -A
kubectl create serviceaccount my-sa -n default
kubectl describe sa my-sa

# RBAC
kubectl get roles
kubectl get rolebindings
kubectl get clusterroles
kubectl get clusterrolebindings
kubectl describe role pod-reader
kubectl describe clusterrole cluster-admin

# Проверка прав
kubectl auth can-i create pods
kubectl auth can-i create pods --as=jane
kubectl auth can-i create pods --as=system:serviceaccount:default:my-sa
kubectl auth can-i --list
kubectl auth can-i --list --as=jane

# NetworkPolicy
kubectl get networkpolicies
kubectl get netpol -A
kubectl describe networkpolicy default-deny-all

# Pod Security
kubectl get namespaces --show-labels
kubectl describe namespace production
kubectl label namespace production pod-security.kubernetes.io/enforce=baseline

# Отладка
kubectl logs -n kube-system kube-apiserver-<node> | grep -i "forbidden\|unauthorized"
kubectl get events --sort-by=.metadata.creationTimestamp
```

## Итог

1. **Аутентификация** — кто вы. **Авторизация** — что можно. **Admission** — можно ли это сделать.
2. **ServiceAccount** — идентичность Pod. Отдельный SA на приложение.
3. **RBAC:** Role, ClusterRole, RoleBinding, ClusterRoleBinding.
4. **Role** — в namespace. **ClusterRole** — во всём кластере.
5. **ClusterRole + RoleBinding** — права ограничены namespace.
6. **NetworkPolicy** — firewall на уровне Pod. Требует CNI с поддержкой.
7. **Default deny all** — начать с запрета всего.
8. **Не забывайте DNS** в egress-политиках.
9. **Pod Security Standards:** Privileged, Baseline, Restricted.
10. **Security Context:** non-root, read-only FS, drop capabilities.

> [!tip]
> **Правило выбора:**
> - Pod не обращается к API → `automountServiceAccountToken: false`
> - Pod обращается к API → отдельный ServiceAccount + минимальные RBAC
> - Изоляция трафика → NetworkPolicy с default deny
> - Защита Pod → Pod Security Standards + SecurityContext
> - Мониторинг → Prometheus SA с ClusterRole

> [!warning]
> **`create pods` — право, которое может привести к эскалации привилегий.** Pod может смонтировать `hostPath`, использовать `privileged: true`, украсть токены. Давайте это право только доверенным subject.
