# 03. API и объекты

В прошлых лекциях мы разобрались, из чего состоит кластер и как его компоненты взаимодействуют. Теперь пришло время понять, **как мы говорим с Kubernetes**. Всё общение происходит через API, а единицей этого общения является **объект**.

> **Kubernetes API** — это RESTful HTTP API, через который можно создавать, читать, обновлять и удалять объекты. Это единственный способ взаимодействия с кластером. `kubectl` — лишь удобная обёртка над этим API.

---

## Всё есть объект

В Kubernetes нет «команд» в привычном смысле. Вы не говорите «запусти контейнер». Вы создаёте **объект** `Pod`, в котором описано, какой контейнер запустить. Вы не говорите «открой порт». Вы создаёте объект `Service`, который описывает, как маршрутизировать трафик.

**Объект** — это запись в etcd, описывающая желаемое состояние (desired state) или текущее состояние (current state) какого-то ресурса.

| Категория | Примеры объектов |
|-----------|------------------|
| **Рабочие нагрузки** | Pod, Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJob |
| **Сеть** | Service, Ingress, NetworkPolicy, EndpointSlice |
| **Конфигурация** | ConfigMap, Secret |
| **Хранение** | PersistentVolume, PersistentVolumeClaim, StorageClass |
| **Управление доступом** | ServiceAccount, Role, RoleBinding, ClusterRole, ClusterRoleBinding |
| **Метаданные** | Namespace, Event, LimitRange, ResourceQuota |
| **Расширения** | CustomResourceDefinition (CRD) и любые кастомные объекты |

## Структура объекта

Каждый объект Kubernetes имеет **четыре обязательных поля верхнего уровня**:

```yaml
apiVersion: apps/v1        # 1. Версия API
kind: Deployment           # 2. Тип объекта
metadata:                  # 3. Метаданные
  name: my-deployment
  namespace: default
  labels:
    app: myapp
spec:                      # 4. Спецификация (желаемое состояние)
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: app
          image: nginx:1.25
          ports:
            - containerPort: 80
# status:                  # 5. Статус (текущее состояние) — заполняется Kubernetes
```

### 1. apiVersion — версия API

Определяет, к какой группе и версии API относится объект.

**Формат:** `<group>/<version>` или `<version>` для core-группы.

| apiVersion | Группа | Пример объектов |
|------------|--------|-----------------|
| `v1` | core (без группы) | Pod, Service, ConfigMap, Secret, Namespace |
| `apps/v1` | apps | Deployment, ReplicaSet, StatefulSet, DaemonSet |
| `batch/v1` | batch | Job, CronJob |
| `networking.k8s.io/v1` | networking | Ingress, NetworkPolicy |
| `rbac.authorization.k8s.io/v1` | rbac | Role, ClusterRole, RoleBinding |
| `storage.k8s.io/v1` | storage | StorageClass, CSIDriver |

> [!note]
> `v1` без группы — это исторически первая (core) группа API. Все остальные имеют префикс группы.

**Зачем это нужно:** Kubernetes развивается, API меняется. Версия позволяет поддерживать несколько версий одновременно и плавно мигрировать.

**Проверка доступных API:**

```bash
kubectl api-versions
kubectl api-resources
```

### 2. kind — тип объекта

Определяет, **что** это за объект. Kind — это всегда строка в CamelCase.

```yaml
kind: Pod
kind: Deployment
kind: Service
```

**Важно:** `kind` — это тип объекта, а не его имя. Имя задаётся в `metadata.name`.

### 3. metadata — метаданные

Метаданные идентифицируют объект и управляют его поведением.

```yaml
metadata:
  name: my-pod                    # Имя объекта (обязательно)
  namespace: default              # Пространство имён (по умолчанию default)
  labels:                         # Метки (key-value) для селекторов
    app: myapp
    env: production
  annotations:                    # Аннотации (key-value) для метаданных
    description: "My first pod"
    prometheus.io/scrape: "true"
  uid: abc-123-def                # Уникальный ID (генерируется Kubernetes)
  resourceVersion: "12345"        # Версия для оптимистичных блокировок
  creationTimestamp: "2024-01-15T10:00:00Z"
  ownerReferences:                # Ссылка на родительский объект
    - apiVersion: apps/v1
      kind: ReplicaSet
      name: my-deployment-abc123
      uid: def-456-ghi
  finalizers:                     # Хуки для удаления
    - kubernetes.io/pv-protection
```

**Ключевые поля:**

| Поле | Назначение |
|------|------------|
| `name` | Имя объекта. Уникально в рамках namespace и kind |
| `namespace` | Логическая изоляция. Для cluster-scoped объектов отсутствует |
| `labels` | Метки для селекторов (Service, ReplicaSet ищут Pod по labels) |
| `annotations` | Произвольные метаданные. Не участвуют в селекторах |
| `uid` | Уникальный идентификатор, генерируется Kubernetes |
| `resourceVersion` | Используется для оптимистичной блокировки при обновлении |
| `ownerReferences` | Кто «владеет» объектом. При удалении владельца — каскадное удаление |

**Labels vs Annotations:**

| Labels | Annotations |
|--------|-------------|
| Используются для селекции | Используются для метаданных |
| Влияют на работу контроллеров | Не влияют на работу |
| Ограничены по длине и символам | Могут быть большими |
| Пример: `app: nginx` | Пример: `kubectl.kubernetes.io/last-applied-configuration` |

### 4. spec — желаемое состояние

**Spec** — это сердце объекта. Здесь вы описываете, **что вы хотите**.

```yaml
spec:
  replicas: 3                    # Сколько копий Pod нужно
  selector:
    matchLabels:
      app: myapp
  template:                      # Шаблон для создания Pod
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: app
          image: nginx:1.25
          resources:
            requests:
              memory: "64Mi"
              cpu: "250m"
            limits:
              memory: "128Mi"
              cpu: "500m"
```

**Содержимое spec зависит от kind:**
- Для Deployment — `replicas`, `selector`, `template`.
- Для Service — `selector`, `ports`, `type`.
- Для ConfigMap — `data`, `binaryData`.
- Для Pod — `containers`, `volumes`, `nodeSelector`.

### 5. status — текущее состояние

**Status** — это то, что Kubernetes **наблюдает** в реальности. Вы **не пишете** status сами. Его заполняют контроллеры и kubelet.

```yaml
status:
  replicas: 3                    # Сколько реплик сейчас
  readyReplicas: 2               # Сколько готовы
  availableReplicas: 2           # Сколько доступны
  conditions:                    # Условия
    - type: Available
      status: "True"
      lastUpdateTime: "2024-01-15T10:05:00Z"
    - type: Progressing
      status: "True"
      reason: ReplicaSetUpdated
```

**Как посмотреть status:**

```bash
kubectl get deployment my-deployment -o yaml
kubectl describe deployment my-deployment
```

## Декларативный vs императивный подход

### Императивный подход

Вы говорите **что делать**:

```bash
kubectl run my-pod --image=nginx
kubectl create deployment my-deploy --image=nginx --replicas=3
kubectl expose deployment my-deploy --port=80
```

**Плюсы:** быстро для одноразовых задач.
**Минусы:** не воспроизводимо, не версионируется, сложно поддерживать.

### Декларативный подход

Вы описываете **что хотите**:

```bash
kubectl apply -f deployment.yaml
```

**Плюсы:**
- Воспроизводимость: один и тот же YAML даёт один и тот же результат.
- Версионирование: YAML хранится в Git.
- Идемпотентность: `apply` можно запускать многократно.
- GitOps: ArgoCD, Flux автоматически применяют YAML из Git.

**Это рекомендуемый подход.**

> [!tip]
> `kubectl apply` — это **declarative**. `kubectl create` и `kubectl run` — **imperative**. В production используйте `apply` и храните манифесты в Git.

## Генерация манифестов

### --dry-run — генерация без применения

```bash
# Сгенерировать YAML для Pod
kubectl run my-pod --image=nginx --dry-run=client -o yaml > pod.yaml

# Сгенерировать YAML для Deployment
kubectl create deployment my-deploy --image=nginx --replicas=3 --dry-run=client -o yaml > deploy.yaml

# Сгенерировать YAML для Service
kubectl expose deployment my-deploy --port=80 --dry-run=client -o yaml > svc.yaml
```

### Генерация из существующих объектов

```bash
# Сохранить текущий объект в YAML
kubectl get deployment my-deploy -o yaml > deploy-backup.yaml

# Убрать лишние поля (status, metadata.uid и т.д.)
kubectl get deployment my-deploy -o yaml --export > deploy-clean.yaml
```

> [!note]
> Флаг `--export` удалён в новых версиях kubectl. Используйте `kubectl neat` (плагин) или вручную чистите YAML.

### Валидация без применения

```bash
# Проверить синтаксис
kubectl apply -f deploy.yaml --dry-run=server

# Проверить с валидацией схемы
kubectl apply -f deploy.yaml --validate=true --dry-run=server
```

## Namespaces — логическая изоляция

> **Namespace** — это виртуальный кластер внутри физического. Объекты в разных namespace изолированы по именам.

**Зачем нужны:**
- Разделение команд (`team-a`, `team-b`).
- Разделение сред (`dev`, `staging`, `prod`).
- Квоты и лимиты на группу объектов.
- RBAC на уровне namespace.

**Стандартные namespace:**

| Namespace | Назначение |
|-----------|------------|
| `default` | Для объектов без явного namespace |
| `kube-system` | Компоненты Control Plane (kube-apiserver, etcd, kube-proxy) |
| `kube-public` | Публичные данные (ConfigMap для bootstrap) |
| `kube-node-lease` | Lease-объекты для отслеживания heartbeat узлов |

**Работа с namespace:**

```bash
# Список namespace
kubectl get namespaces

# Создать namespace
kubectl create namespace my-app

# Переключить namespace по умолчанию
kubectl config set-context --current --namespace=my-app

# Создать объект в конкретном namespace
kubectl apply -f deploy.yaml -n my-app

# Посмотреть объекты во всех namespace
kubectl get pods --all-namespaces
```

**Важно:** Не все объекты находятся в namespace. Некоторые **cluster-scoped**:

| Cluster-scoped | Namespaced |
|----------------|------------|
| Node | Pod |
| PersistentVolume | PersistentVolumeClaim |
| StorageClass | Service |
| ClusterRole | Role |
| ClusterRoleBinding | RoleBinding |
| CustomResourceDefinition | ConfigMap, Secret |

## Работа с API через kubectl

### Просмотр объектов

```bash
# Список Pod
kubectl get pods

# Список Pod с дополнительной информацией
kubectl get pods -o wide

# Список Pod в формате YAML
kubectl get pod my-pod -o yaml

# Список Pod в формате JSON
kubectl get pod my-pod -o json

# Кастомные колонки
kubectl get pods -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName
```

### Описание объекта

```bash
# Человекочитаемое описание с событиями
kubectl describe pod my-pod

# События (важно для troubleshooting)
kubectl get events --sort-by=.metadata.creationTimestamp
```

### Создание и обновление

```bash
# Создать из файла
kubectl apply -f deploy.yaml

# Создать из stdin
cat deploy.yaml | kubectl apply -f -

# Создать из директории (все YAML)
kubectl apply -f ./manifests/

# Создать рекурсивно
kubectl apply -R -f ./manifests/

# Обновить образ в Deployment
kubectl set image deployment/my-deploy app=nginx:1.26

# Масштабировать
kubectl scale deployment/my-deploy --replicas=5
```

### Редактирование

```bash
# Редактировать в редакторе (откроется vim/nano)
kubectl edit deployment my-deploy

# Это откроет YAML, вы правите, сохраняете — изменения применяются
```

> [!warning]
> `kubectl edit` — императивный подход. В production используйте Git и `apply`. `edit` удобен для отладки, но изменения не версионируются.

### Удаление

```bash
# Удалить по имени
kubectl delete pod my-pod

# Удалить из файла
kubectl delete -f deploy.yaml

# Удалить все Pod с меткой
kubectl delete pods -l app=myapp

# Удалить namespace (и всё внутри)
kubectl delete namespace my-app
```

## API Resources — что доступно в кластере

```bash
# Список всех ресурсов
kubectl api-resources

# С фильтрацией
kubectl api-resources --namespaced=true
kubectl api-resources --namespaced=false

# С указанием группы
kubectl api-resources --api-group=apps
```

**Пример вывода:**

```
NAME          SHORTNAMES   APIVERSION   NAMESPACED   KIND
pods          po           v1           true         Pod
services      svc          v1           true         Service
deployments   deploy       apps/v1      true         Deployment
nodes         no           v1           false        Node
```

**Короткие имена (shortnames):**

```bash
kubectl get po          # pods
kubectl get svc         # services
kubectl get deploy      # deployments
kubectl get ns          # namespaces
kubectl get no          # nodes
```

## Практический пример: полный цикл

### Шаг 1: Создать namespace

```bash
kubectl create namespace demo
```

### Шаг 2: Написать Deployment

**Файл `deployment.yaml`:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  namespace: demo
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests:
              memory: "64Mi"
              cpu: "100m"
            limits:
              memory: "128Mi"
              cpu: "200m"
```

### Шаг 3: Применить

```bash
kubectl apply -f deployment.yaml
```

### Шаг 4: Проверить

```bash
kubectl get deployments -n demo
kubectl get pods -n demo
kubectl describe deployment nginx-deployment -n demo
```

### Шаг 5: Посмотреть status

```bash
kubectl get deployment nginx-deployment -n demo -o yaml
```

Обратите внимание на поля `status`:
- `replicas: 3`
- `readyReplicas: 3`
- `availableReplicas: 3`

### Шаг 6: Обновить образ

```bash
kubectl set image deployment/nginx-deployment nginx=nginx:1.26 -n demo
```

Или отредактировать YAML и снова применить:

```bash
kubectl apply -f deployment.yaml
```

### Шаг 7: Откатить

```bash
kubectl rollout history deployment/nginx-deployment -n demo
kubectl rollout undo deployment/nginx-deployment -n demo
```

### Шаг 8: Удалить

```bash
kubectl delete -f deployment.yaml
kubectl delete namespace demo
```

## Шпаргалка: основные команды

```bash
# Просмотр
kubectl get <resource>                    # Список
kubectl get <resource> -o wide            # С доп. информацией
kubectl get <resource> -o yaml            # YAML
kubectl get <resource> -o json            # JSON
kubectl describe <resource> <name>        # Детально + события
kubectl explain <resource>                # Документация по полям

# Создание и обновление
kubectl apply -f file.yaml                # Декларативно
kubectl create -f file.yaml               # Императивно (падает, если есть)
kubectl replace -f file.yaml              # Заменить
kubectl patch <resource> <name> -p '...'  # Частичное обновление
kubectl edit <resource> <name>            # Редактировать в редакторе

# Удаление
kubectl delete <resource> <name>
kubectl delete -f file.yaml
kubectl delete <resource> -l key=value    # По метке

# Генерация
kubectl run my-pod --image=nginx --dry-run=client -o yaml
kubectl create deployment my-deploy --image=nginx --dry-run=client -o yaml

# Namespace
kubectl get namespaces
kubectl create namespace my-ns
kubectl config set-context --current --namespace=my-ns

# API
kubectl api-versions
kubectl api-resources
kubectl explain pod.spec.containers
```

## Итог

1. **Всё есть объект.** Kubernetes управляет объектами, описанными в YAML/JSON.
2. **Объект имеет 4 обязательных поля:** `apiVersion`, `kind`, `metadata`, `spec`. `status` заполняется Kubernetes.
3. **Декларативный подход** — рекомендуемый. Описывайте желаемое состояние, а Kubernetes приведёт к нему.
4. **Namespace** — логическая изоляция. Не все объекты namespaced.
5. **kubectl** — обёртка над REST API. Любое действие можно сделать через API-сервер.
6. **`kubectl apply`** — идемпотентен. Можно запускать многократно.

> [!tip]
> Изучите `kubectl explain`. Это встроенная документация по любому полю любого объекта. Например, `kubectl explain pod.spec.containers.resources` покажет, что можно указать в ресурсах.
