# 02. Устройство кластера

В прошлой лекции мы познакомились с философией Kubernetes и высокоуровневым обзором компонентов. Теперь пришло время заглянуть внутрь и понять, как эти компоненты взаимодействуют, образуя единый организм — кластер.

> **Кластер Kubernetes** — это набор машин (физических или виртуальных), объединённых в единую систему управления приложениями. Эти машины делятся на две роли: **Control Plane** (управляющий слой) и **Worker Nodes** (рабочие узлы).

---

## Control Plane — мозг кластера

Control Plane принимает все решения о кластере: где запускать Pod, сколько реплик держать, что делать при отказе узла. Он состоит из четырёх ключевых компонентов.

### kube-apiserver — центральный узел связи

> **kube-apiserver** — это единственная точка входа для всех запросов к кластеру. Ни один компонент не обращается к etcd напрямую — только через API-сервер.

**Что делает:**
- Принимает REST-запросы от пользователей (`kubectl`), контроллеров и kubelet.
- **Валидирует** запросы: проверяет синтаксис, права доступа (через RBAC), admission-контроллеры.
- **Аутентифицирует** и **авторизует** каждый запрос.
- Сохраняет состояние объектов в **etcd**.
- Предоставляет **watch API** — механизм, позволяющий компонентам подписываться на изменения объектов в реальном времени.

**Как это работает на практике:**

```bash
kubectl apply -f deployment.yaml
```

1. `kubectl` отправляет HTTP-запрос (POST/PUT) на `kube-apiserver`.
2. API-сервер проверяет права пользователя, валидирует манифест, применяет admission-контроллеры.
3. Если всё в порядке — сохраняет объект в etcd.
4. Все, кто «слушает» (watch) изменения этого типа объектов, получают уведомление.

**Ключевая особенность:** API-сервер **stateless**. Он не хранит состояние у себя — всё уходит в etcd. Можно запустить несколько экземпляров API-сервера за балансировщиком для отказоустойчивости.

### etcd — единственный источник правды

> **etcd** — распределённое, надёжное key-value хранилище. В нём хранится **всё** состояние кластера: манифесты, статусы, конфигурации, секреты.

**Почему etcd критичен:**
- Если etcd потерян — кластер потерян. Все объекты исчезнут.
- etcd использует алгоритм **Raft** для консенсуса между узлами.
- Для production рекомендуется **3 или 5 узлов etcd** (нечётное число для кворума).

**Что хранится в etcd:**
- Все объекты Kubernetes (Pod, Service, Deployment, ConfigMap, Secret и т.д.).
- Метаданные: кто создал, когда, текущий статус.
- Состояние кластера: какие узлы живы, какие Pod запущены.

**Пример просмотра ключей etcd (осторожно, только для отладки):**

```bash
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/deployments --prefix --keys-only
```

> [!warning]
> Никогда не редактируйте etcd вручную. Все изменения — только через kube-apiserver. Прямое вмешательство может разрушить кластер.

### kube-scheduler — распределитель нагрузки

> **kube-scheduler** — компонент, который решает, на каком узле запустить новый Pod.

**Как работает scheduler:**

1. **Watch:** Scheduler подписан на API-сервер и получает уведомления о новых Pod, у которых ещё нет узла (`nodeName` пуст).
2. **Filtering (фильтрация):** Отбирает узлы, которые *могут* запустить Pod:
   - Достаточно ли CPU и RAM (requests)?
   - Соответствуют ли nodeSelector / nodeAffinity?
   - Есть ли tolerations для taints узла?
   - Не занят ли порт (hostPort)?
3. **Scoring (оценка):** Среди подходящих узлов выбирает лучший:
   - Балансировка нагрузки (меньше занятых Pod — выше приоритет).
   - Предпочтения affinity.
   - Распределение по зонам доступности.
4. **Binding:** Записывает в API-сервер решение: `Pod.spec.nodeName = выбранный_узел`.

**Важно:** Scheduler **не запускает** Pod. Он только *назначает* узел. Запуском занимается kubelet на этом узле.

**Пример просмотра решения scheduler:**

```bash
kubectl describe pod my-pod | grep -A5 "Events:"
```

В событиях будет видно: `Successfully assigned default/my-pod to node-1`.

### kube-controller-manager — хранитель желаемого состояния

> **kube-controller-manager** — это набор контроллеров, каждый из которых следит за своим типом объектов и приводит текущее состояние к желаемому.

**Что такое контроллер?**

Контроллер — это цикл (reconciliation loop):

```
for {
    desired_state := get_desired_state()
    current_state := get_current_state()
    if current_state != desired_state {
        take_action_to_fix()
    }
    sleep()
}
```

**Основные контроллеры:**

| Контроллер | За что отвечает |
|------------|-----------------|
| **Deployment Controller** | Управляет ReplicaSet, обеспечивает rolling update и rollback |
| **ReplicaSet Controller** | Следит, чтобы нужное количество Pod было запущено |
| **Node Controller** | Отслеживает состояние узлов, помечает упавшие как `NotReady` |
| **Endpoint Controller** | Обновляет Endpoints для Service, когда Pod появляются/исчезают |
| **Service Account Controller** | Создаёт ServiceAccount для новых namespace |
| **Namespace Controller** | Удаляет ресурсы при удалении namespace |

**Пример работы:**

Вы создали Deployment с `replicas: 3`. Deployment Controller создаёт ReplicaSet. ReplicaSet Controller создаёт 3 Pod. Если один Pod упал — ReplicaSet Controller создаст новый. Если вы обновили образ — Deployment Controller создаст новый ReplicaSet и постепенно переключит Pod.

**Все контроллеры работают параллельно в одном процессе** `kube-controller-manager`, но логически независимы.

## Worker Node — рабочая лошадка

Worker Nodes — это машины, на которых запускаются контейнеры приложений. Каждый узел управляется Control Plane, но выполняет свою работу автономно.

### kubelet — агент узла

> **kubelet** — главный агент на каждом узле. Он следит за тем, чтобы контейнеры в Pod были запущены и здоровы.

**Задачи kubelet:**

1. **Регистрация узла:** При старте kubelet регистрирует свой узел в API-сервере.
2. **Watch Pods:** Подписывается на Pod, у которых `nodeName` совпадает с его узлом.
3. **Запуск Pod:** Через Container Runtime Interface (CRI) запускает контейнеры.
4. **Health checks:** Выполняет liveness, readiness и startup probes.
5. **Отчёты:** Периодически отправляет статус Pod и узла в API-сервер.
6. **Управление ресурсами:** Следит за потреблением CPU/RAM, eviction при нехватке.

**Важно:** kubelet **не управляется** Control Plane напрямую. Control Plane только сообщает kubelet желаемое состояние (через API), а kubelet сам решает, как его достичь.

**Пример просмотра статуса kubelet:**

```bash
systemctl status kubelet
journalctl -u kubelet -f
```

### Container Runtime — среда выполнения

> **Container Runtime** — это то, что *реально* запускает и останавливает контейнеры.

Kubernetes взаимодействует с runtime через **CRI (Container Runtime Interface)** — стандартный API.

**Популярные runtime:**

| Runtime | Описание |
|---------|----------|
| **containerd** | Современный стандарт. Лёгкий, быстрый. Используется в большинстве managed Kubernetes |
| **CRI-O** | Оптимизирован для Kubernetes. Используется в OpenShift |
| **Docker (dockershim)** | Устаревший. Удалён из Kubernetes начиная с v1.24 |

**Ключевое:** kubelet не знает про Docker. Он говорит с runtime через CRI. Это позволяет менять runtime без изменения Kubernetes.

**Проверка runtime:**

```bash
kubectl get nodes -o wide
```

В колонке `CONTAINER-RUNTIME` будет видно: `containerd://1.6.20` или `cri-o://1.28.0`.

### kube-proxy — сетевое связывание

> **kube-proxy** — компонент, который реализует сетевые правила для **Service**.

**Что делает kube-proxy:**

1. Watch API на изменения Service и Endpoints.
2. Программирует правила в iptables (или IPVS) на узле.
3. Когда пакет идёт на ClusterIP Service — kube-proxy перенаправляет его на один из Pod.

**Режимы работы:**

| Режим | Описание |
|-------|----------|
| **iptables** | Классический. Работает через правила netfilter. Может тормозить при тысячах Service |
| **IPVS** | Современный. Использует LVS (Linux Virtual Server). Быстрее, лучше масштабируется |
| **userspace** | Устаревший. Проксирование через userspace. Медленно |

**Пример просмотра правил iptables (осторожно, очень много строк):**

```bash
sudo iptables -t nat -L KUBE-SERVICES -n | head -20
```

**Важно:** kube-proxy — не единственный способ реализации Service. В некоторых CNI (например, Cilium) kube-proxy заменяется на eBPF-программы.

### Container Network Interface (CNI)

> **CNI** — плагин, который отвечает за сеть между Pod на разных узлах.

**Задачи CNI:**
- Выделение IP-адресов Pod.
- Обеспечение связности между Pod на разных узлах.
- Реализация NetworkPolicy.

**Популярные CNI:**

| CNI | Особенности |
|-----|-------------|
| **Calico** | Гибкий, поддерживает NetworkPolicy, BGP |
| **Cilium** | eBPF-based, высокая производительность, замена kube-proxy |
| **Flannel** | Простой, но ограниченный функционал |
| **Weave Net** | Простой в установке, поддерживает шифрование |

**Проверка CNI:**

```bash
ls /etc/cni/net.d/
```

## Как всё взаимодействует: полный цикл

Рассмотрим, что происходит при создании Deployment.

### Шаг 1: Пользователь создаёт Deployment

```bash
kubectl apply -f deployment.yaml
```

1. `kubectl` отправляет запрос на `kube-apiserver`.
2. API-сервер валидирует, аутентифицирует, авторизует.
3. Сохраняет Deployment в etcd.

### Шаг 2: Deployment Controller создаёт ReplicaSet

1. `kube-controller-manager` (Deployment Controller) получает уведомление о новом Deployment.
2. Видит: `desired_replicas = 3`, `current_replicas = 0`.
3. Создаёт ReplicaSet с `replicas: 3`.

### Шаг 3: ReplicaSet Controller создаёт Pod

1. ReplicaSet Controller получает уведомление о новом ReplicaSet.
2. Видит: `desired_pods = 3`, `current_pods = 0`.
3. Создаёт 3 Pod (без `nodeName`).

### Шаг 4: Scheduler назначает узлы

1. `kube-scheduler` получает уведомление о новых Pod без `nodeName`.
2. Фильтрует узлы, оценивает, выбирает лучший.
3. Обновляет Pod: `nodeName = node-2`.

### Шаг 5: kubelet запускает Pod

1. `kubelet` на `node-2` получает уведомление о Pod с его `nodeName`.
2. Через CRI просит containerd запустить контейнер.
3. Containerd скачивает образ, создаёт контейнер, запускает.
4. kubelet отправляет статус Pod в API-сервер.

### Шаг 6: Service и kube-proxy

1. Если Pod соответствует Service selector — Endpoint Controller обновляет Endpoints.
2. `kube-proxy` на всех узлах обновляет iptables/IPVS правила.
3. Трафик на Service ClusterIP теперь идёт на новые Pod.

### Шаг 7: Reconciliation Loop продолжается

- Если Pod упал — ReplicaSet Controller создаст новый.
- Если узел упал — Node Controller пометит его `NotReady`, Pod будут пересозданы.
- Если вы обновили образ — Deployment Controller запустит rolling update.

## Различия managed и self-hosted кластеров

| Аспект | Managed (EKS, GKE, AKS) | Self-hosted (kubeadm, k3s) |
|--------|-------------------------|----------------------------|
| **Control Plane** | Управляется провайдером | Вы управляете сами |
| **etcd** | Провайдер отвечает за бэкапы | Вы отвечаете за бэкапы |
| **Обновления** | Автоматические | Ручные |
| **Стоимость** | Платите за Control Plane | Платите только за узлы |
| **Гибкость** | Ограничена | Полный контроль |

## Шпаргалка: основные команды

```bash
# Информация о кластере
kubectl cluster-info
kubectl get nodes -o wide
kubectl describe node <node-name>

# Компоненты Control Plane (если есть доступ)
kubectl get pods -n kube-system
kubectl logs -n kube-system kube-apiserver-<node>
kubectl logs -n kube-system kube-scheduler-<node>
kubectl logs -n kube-system kube-controller-manager-<node>

# etcd (только для self-hosted)
kubectl exec -n kube-system etcd-<node> -- etcdctl member list

# kubelet (на узле)
systemctl status kubelet
journalctl -u kubelet -f

# kube-proxy
kubectl logs -n kube-system kube-proxy-<pod>
```

## Итог

1. **Control Plane** — мозг кластера: API-сервер, etcd, scheduler, controller-manager.
2. **Worker Node** — рабочая лошадка: kubelet, container runtime, kube-proxy, CNI.
3. **API-сервер** — единственная точка входа. Все компоненты общаются через него.
4. **etcd** — единственный источник правды. Потеря etcd = потеря кластера.
5. **Контроллеры** — циклы согласования, которые приводят текущее состояние к желаемому.
6. **Scheduler** — решает, *где* запускать Pod, но не запускает их.
7. **kubelet** — запускает Pod через CRI и следит за их здоровьем.

> [!tip]
> Понимание того, как компоненты взаимодействуют, критически важно для troubleshooting. Если Pod не запускается — смотрите события (`kubectl describe pod`). Если узел NotReady — смотрите kubelet. Если Service не работает — смотрите kube-proxy и Endpoints.
