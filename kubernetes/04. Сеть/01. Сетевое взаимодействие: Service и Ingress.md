# 01. Сетевое взаимодействие: Service и Ingress

Мы научились запускать Pod. Но у Pod есть проблема: **IP-адреса меняются**. Pod создаётся, умирает, пересоздаётся — и каждый раз получает новый IP. Как обеспечить стабильный доступ к приложению? Как балансировать трафик между репликами? Как открыть приложение в интернет?

Ответ — **Service** и **Ingress**.

> **Service** — абстракция, которая предоставляет стабильный сетевой доступ к группе Pod. **Ingress** — точка входа для внешнего трафика, маршрутизирующая HTTP/HTTPS на Service.

---

## Проблема: Pod эфемерны

Представьте Deployment с 3 репликами:

```
web-app-abc123  →  10.244.1.5
web-app-def456  →  10.244.2.6
web-app-ghi789  →  10.244.3.7
```

Что произойдёт, если:
- Pod упадёт и пересоздастся → новый IP.
- Вы сделаете rolling update → все IP изменятся.
- Вы масштабируете → добавятся новые IP.

**Клиент не может знать IP заранее.** Нужна абстракция, которая:
- Имеет **стабильный IP** (ClusterIP).
- Имеет **стабильное DNS-имя**.
- **Балансирует** трафик между Pod.
- **Автоматически** обновляет список Pod.

Это и есть Service.

---

## Service: четыре типа

| Тип | Доступ | Использование |
|-----|--------|---------------|
| **ClusterIP** | Внутри кластера | Внутренние сервисы (по умолчанию) |
| **NodePort** | Снаружи через порт узла | Отладка, простые случаи |
| **LoadBalancer** | Снаружи через облачный LB | Production в облаке |
| **ExternalName** | DNS CNAME | Проксирование на внешний сервис |

### ClusterIP — внутренний сервис

> **ClusterIP** — тип по умолчанию. Выделяет виртуальный IP внутри кластера.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app
spec:
  type: ClusterIP          # по умолчанию
  selector:
    app: web
  ports:
    - name: http
      port: 80             # порт Service
      targetPort: 8080     # порт контейнера
      protocol: TCP
```

**Что получаем:**
- Виртуальный IP: `10.96.0.10` (ClusterIP).
- DNS: `web-app.default.svc.cluster.local`.
- Трафик на `web-app:80` идёт на Pod с меткой `app: web`, порт 8080.

**Проверка:**

```bash
kubectl get svc web-app
# NAME      TYPE        CLUSTER-IP    PORT(S)   AGE
# web-app   ClusterIP   10.96.0.10    80/TCP    10s

kubectl get endpoints web-app
# NAME      ENDPOINTS                                AGE
# web-app   10.244.1.5:8080,10.244.2.6:8080,...    10s
```

### NodePort — доступ через узел

> **NodePort** — открывает порт на **каждом** узле кластера. Трафик на `<NodeIP>:<NodePort>` идёт на Service.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app-nodeport
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080      # 30000-32767 (по умолчанию)
```

**Что получаем:**
- ClusterIP: `10.96.0.20`.
- NodePort: `30080` на **каждом** узле.
- Доступ: `http://<любой-узел>:30080`.

**Проверка:**

```bash
kubectl get svc web-app-nodeport
# NAME              TYPE       CLUSTER-IP    PORT(S)        AGE
# web-app-nodeport  NodePort   10.96.0.20    80:30080/TCP   10s

# С любой машины, у которой есть доступ к узлу
curl http://192.168.1.10:30080
```

> [!warning]
> NodePort **не** предназначен для production. Он открывает порт на всех узлах, что небезопасно и неудобно. Используйте LoadBalancer или Ingress.

### LoadBalancer — облачный балансировщик

> **LoadBalancer** — создаёт внешний балансировщик в облаке (AWS ELB, GCP LB, Azure LB).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app-lb
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
```

**Что получаем:**
- ClusterIP.
- NodePort (автоматически).
- Внешний IP от облачного провайдера.

**Проверка:**

```bash
kubectl get svc web-app-lb
# NAME          TYPE           CLUSTER-IP    EXTERNAL-IP     PORT(S)
# web-app-lb    LoadBalancer   10.96.0.30    203.0.113.10    80:31234/TCP
```

**В bare-metal кластерах** (без облака) LoadBalancer не работает «из коробки». Нужны:
- **MetalLB** — реализация LoadBalancer для bare-metal.
- **kube-vip** — VIP для control-plane и LoadBalancer.

### ExternalName — проксирование на внешний сервис

> **ExternalName** — создаёт DNS CNAME на внешний сервис. Не проксирует трафик.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: db.example.com
```

**Что получаем:** DNS `external-db.default.svc.cluster.local` → CNAME → `db.example.com`.

**Использование:** для миграции с внешних сервисов или для абстракции.

## Как работает Service: kube-proxy

Service — это **виртуальная абстракция**. Нет процесса, который слушает порт. Всё реализуется через **kube-proxy** на каждом узле.

### iptables-режим (по умолчанию)

kube-proxy создаёт правила iptables:

```
# Трафик на ClusterIP 10.96.0.10:80
-A KUBE-SERVICES -d 10.96.0.10/32 -p tcp --dport 80 -j KUBE-SVC-XXXXX

# Балансировка между Pod
-A KUBE-SVC-XXXXX -m statistic --mode random --probability 0.33 -j KUBE-SEP-POD1
-A KUBE-SVC-XXXXX -m statistic --mode random --probability 0.50 -j KUBE-SEP-POD2
-A KUBE-SVC-XXXXX -j KUBE-SEP-POD3

# DNAT на конкретный Pod
-A KUBE-SEP-POD1 -p tcp -j DNAT --to-destination 10.244.1.5:8080
```

**Как это работает:**
1. Пакет идёт на ClusterIP.
2. iptables перехватывает и делает DNAT на один из Pod.
3. Pod отвечает, обратный трафик идёт через conntrack.

### IPVS-режим

Для больших кластеров (тысячи Service) iptables становится медленным. IPVS (IP Virtual Server) быстрее:

```yaml
# В kube-proxy ConfigMap
mode: ipvs
```

IPVS использует хеш-таблицы, а не линейный список правил.

### eBPF-режим (Cilium)

Cilium заменяет kube-proxy на eBPF-программы. Быстрее, лучше масштабируется, сохраняет source IP.

## Service без selector

Service может работать без selector — тогда Endpoints создаются вручную.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-service
spec:
  ports:
    - port: 80
      targetPort: 80
---
apiVersion: v1
kind: Endpoints
metadata:
  name: external-service
subsets:
  - addresses:
      - ip: 192.168.1.100
      - ip: 192.168.1.101
    ports:
      - port: 80
```

**Использование:** для подключения к внешним БД, legacy-сервисам.

## Headless Service

> **Headless Service** — Service без ClusterIP (`clusterIP: None`). DNS возвращает IP всех Pod.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app-headless
spec:
  clusterIP: None
  selector:
    app: web
  ports:
    - port: 80
```

**DNS-записи:**

```
web-app-headless.default.svc.cluster.local  → 10.244.1.5, 10.244.2.6, 10.244.3.7
```

**Использование:**
- StatefulSet (для стабильных DNS-имён Pod).
- Клиентская балансировка (клиент сам выбирает Pod).
- Service discovery без проксирования.

## Ingress: вход в кластер

Service типа LoadBalancer создаёт **один** балансировщик на **один** сервис. Если у вас 10 сервисов — нужно 10 балансировщиков. Это дорого.

**Ingress** решает проблему: **один** вход, маршрутизация по хостам и путям.

> **Ingress** — объект, описывающий правила маршрутизации HTTP/HTTPS на Service. Требует **Ingress Controller** (nginx, Traefik, HAProxy).

### Архитектура

```
Интернет
   │
   ▼
┌──────────────────┐
│  LoadBalancer    │  ← один IP
└──────────────────┘
   │
   ▼
┌──────────────────┐
│ Ingress Controller│  ← nginx, Traefik
└──────────────────┘
   │
   ├── /api      → api-service:80
   ├── /web      → web-service:80
   └── /admin    → admin-service:80
```

### Установка Ingress Controller (nginx)

```bash
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --create-namespace
```

**Проверка:**

```bash
kubectl get pods -n ingress-nginx
kubectl get svc -n ingress-nginx
```

### Манифест Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app
                port:
                  number: 80
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
```

**Что получаем:**
- `http://app.example.com/` → `web-app:80`
- `http://app.example.com/api` → `api-service:8080`

### pathType

| pathType | Описание |
|----------|----------|
| `Prefix` | Префикс пути (`/api` матчит `/api`, `/api/v1`, `/api/users`) |
| `Exact` | Точное совпадение (`/api` матчит только `/api`) |
| `ImplementationSpecific` | Зависит от controller |

### Мультихостовый Ingress

```yaml
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app
                port:
                  number: 80
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
```

### TLS в Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress-tls
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: app-tls-secret
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app
                port:
                  number: 80
```

**Secret должен быть типа `kubernetes.io/tls`:**

```bash
kubectl create secret tls app-tls-secret \
  --cert=path/to/tls.crt \
  --key=path/to/tls.key
```

### Аннотации Ingress

Ingress Controller настраивается через аннотации:

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
    nginx.ingress.kubernetes.io/rate-limit: "100"
    cert-manager.io/cluster-issuer: letsencrypt-prod
```

### cert-manager для автоматического TLS

**cert-manager** автоматически получает сертификаты от Let's Encrypt.

```bash
helm repo add jetstack https://charts.jetstack.io
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set installCRDs=true
```

**ClusterIssuer:**

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@example.com
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
      - http01:
          ingress:
            class: nginx
```

**Ingress с автоматическим TLS:**

```yaml
metadata:
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  tls:
    - hosts:
        - app.example.com
      secretName: app-tls-secret   # cert-manager создаст автоматически
```

## Gateway API: следующий шаг

> **Gateway API** — новая стандартизированная замена Ingress. Более гибкая, поддерживает TCP/UDP/gRPC, роли.

| Ingress | Gateway API |
|---------|-------------|
| Только HTTP/HTTPS | HTTP, HTTPS, TCP, UDP, gRPC |
| Аннотации для всего | Явные ресурсы (GatewayClass, Gateway, HTTPRoute) |
| Один объект | Разделение ролей (infra, app) |
| Ограниченная маршрутизация | Header-based, weight-based, mirroring |

**Пример HTTPRoute:**

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web-route
spec:
  parentRefs:
    - name: my-gateway
  hostnames:
    - app.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: web-app
          port: 80
```

Gateway API — будущее, но Ingress всё ещё широко используется.

## DNS в кластере: CoreDNS

> **CoreDNS** — DNS-сервер кластера. Резолвит имена Service и Pod.

**Формат DNS-имён:**

| Ресурс | DNS |
|--------|-----|
| Service | `<service>.<namespace>.svc.cluster.local` |
| Pod | `<pod-ip-dashed>.<namespace>.pod.cluster.local` |
| StatefulSet Pod | `<pod-name>.<service>.<namespace>.svc.cluster.local` |

**Пример:**

```
web-app.default.svc.cluster.local       → ClusterIP
web-app-0.web-app.default.svc.cluster.local → IP Pod
```

**Проверка:**

```bash
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup web-app
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup kubernetes.default
```

## NetworkPolicy: ограничение трафика

> **NetworkPolicy** — firewall на уровне Pod. По умолчанию весь трафик разрешён. С NetworkPolicy — запрещён, кроме явно разрешённого.

**Пример: разрешить только трафик от frontend к backend:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-policy
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

**Требует CNI с поддержкой NetworkPolicy:** Calico, Cilium, Weave Net. Flannel — не поддерживает.

## Практический пример: полный стек

### 1. Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
```

### 2. ClusterIP Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
```

### 3. Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app
                port:
                  number: 80
```

### Проверка

```bash
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f ingress.yaml

kubectl get pods -l app=web
kubectl get svc web-app
kubectl get ingress
kubectl get endpoints web-app

# Проверка изнутри кластера
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- wget -qO- http://web-app

# Проверка снаружи
curl -H "Host: app.example.com" http://<ingress-ip>
```

## Итог

1. **Service** — стабильный доступ к Pod. Четыре типа: ClusterIP, NodePort, LoadBalancer, ExternalName.
2. **ClusterIP** — внутри кластера. **NodePort** — через порт узла. **LoadBalancer** — облачный LB.
3. **kube-proxy** реализует Service через iptables/IPVS/eBPF.
4. **Headless Service** — без ClusterIP, DNS возвращает IP всех Pod.
5. **Ingress** — HTTP/HTTPS маршрутизация. Требует Ingress Controller.
6. **cert-manager** — автоматический TLS от Let's Encrypt.
7. **Gateway API** — будущее, замена Ingress.
8. **CoreDNS** — DNS кластера.
9. **NetworkPolicy** — firewall на уровне Pod. Требует CNI с поддержкой.
10. **Service — L4, Ingress — L7.**

> [!tip]
> **Правило выбора:**
> - Внутренний сервис → **ClusterIP**
> - Внешний доступ в облаке → **LoadBalancer**
> - Много сервисов через один IP → **Ingress**
> - StatefulSet → **Headless Service**
> - Отладка → **port-forward**
