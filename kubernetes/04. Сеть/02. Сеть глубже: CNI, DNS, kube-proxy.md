# 02. Сеть глубже: CNI, DNS, kube-proxy

В прошлой лекции мы разобрались с Service и Ingress — абстракциями для доступа к приложениям. Но под ними скрывается целый мир: как Pod получают IP? Как они общаются между узлами? Как работает DNS? Как трафик попадает от Service к Pod?

В этой лекции разберём **три столпа сетевой подсистемы Kubernetes**: CNI, DNS и kube-proxy.

> **Сетевая модель Kubernetes** описывается четырьмя правилами:
> 1. Все Pod могут общаться друг с другом **без NAT**.
> 2. Все узлы могут общаться с Pod **без NAT**.
> 3. Pod видит свой IP таким же, каким его видят другие.
> 4. IP Pod уникален в пределах кластера.

Эти правила — фундамент. Реализацию обеспечивают CNI, CoreDNS и kube-proxy.

## Часть 1: CNI (Container Network Interface)

> **CNI** — это спецификация и набор плагинов для настройки сети контейнеров. Kubernetes не реализует сеть сам — он делегирует её CNI-плагину.

### Как это работает

Когда kubelet создаёт Pod:

1. kubelet вызывает CNI-плагин через **CRI**.
2. CNI-плагин:
   - Создаёт **veth pair** (виртуальный кабель) между сетевым namespace Pod и узлом.
   - Выделяет Pod **IP-адрес** из пула.
   - Настраивает **маршруты** между Pod на разных узлах.
   - Применяет **NetworkPolicy** (если поддерживает).

### Ключевые компоненты CNI

| Компонент | Роль |
|-----------|------|
| **CNI plugin** | Бинарник, который вызывается kubelet'ом |
| **IPAM** | Управление IP-адресами (выделение, освобождение) |
| **Overlay / Underlay** | Способ связности между узлами |
| **NetworkPolicy engine** | Реализация NetworkPolicy |

### Overlay vs Underlay

**Overlay-сеть:**
- Пакеты инкапсулируются в другие пакеты (VXLAN, Geneve, IP-in-IP).
- Работает поверх любой физической сети.
- Минус: overhead, сложнее отладка.

**Underlay-сеть:**
- Pod получают IP из физической сети.
- Пакеты идут напрямую, без инкапсуляции.
- Плюс: производительность, простота.
- Минус: требует настройки BGP, ограничения по IP.

### Популярные CNI

| CNI | Тип | NetworkPolicy | Особенности |
|-----|-----|---------------|-------------|
| **Calico** | Overlay / Underlay (BGP) | ✅ | Гибкий, поддержка BGP, eBPF-режим |
| **Cilium** | eBPF | ✅ | Заменяет kube-proxy, высокая производительность |
| **Flannel** | Overlay (VXLAN) | ❌ | Простой, но без NetworkPolicy |
| **Weave Net** | Overlay | ✅ | Простой в установке, шифрование |
| **Antrea** | Overlay / Underlay | ✅ | Разработка VMware, OVS-based |
| **Kube-router** | Underlay (BGP) | ✅ | Лёгкий, заменяет kube-proxy |

### Calico

**Самый популярный CNI.** Работает в двух режимах:

**1. IP-in-IP (overlay):**
- Пакеты инкапсулируются в IP-in-IP.
- Работает поверх любой сети.
- Простая настройка.

**2. BGP (underlay):**
- Pod IP анонсируются в физическую сеть через BGP.
- Нет инкапсуляции — выше производительность.
- Требует поддержки BGP в сети.

**Установка:**

```bash
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.27.0/manifests/calico.yaml
```

**Проверка:**

```bash
kubectl get pods -n kube-system -l k8s-app=calico-node
kubectl get ippools.crd.projectcalico.org
kubectl get felixconfiguration
```

**Пример IPPool:**

```yaml
apiVersion: crd.projectcalico.org/v1
kind: IPPool
metadata:
  name: default-ipv4-ippool
spec:
  cidr: 10.244.0.0/16
  blockSize: 26
  natOutgoing: true
  nodeSelector: all()
```

### Cilium

**Современный CNI на eBPF.** Заменяет kube-proxy, обеспечивает высокую производительность.

**Особенности:**
- eBPF-программы вместо iptables.
- L7-фильтрация (HTTP, gRPC).
- Прозрачное шифрование (WireGuard, IPsec).
- Hubble — observability.

**Установка:**

```bash
helm repo add cilium https://helm.cilium.io/
helm install cilium cilium/cilium \
  --namespace kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=<api-server-ip> \
  --set k8sServicePort=<api-server-port>
```

**Проверка:**

```bash
kubectl get pods -n kube-system -l k8s-app=cilium
cilium status
cilium connectivity test
```

### Flannel

**Простой overlay CNI.** Не поддерживает NetworkPolicy.

**Установка:**

```bash
kubectl apply -f https://raw.githubusercontent.com/flannel-io/flannel/master/Documentation/kube-flannel.yml
```

**Режимы:**
- VXLAN (по умолчанию).
- host-gw (для L2-сетей).
- WireGuard (шифрование).

> [!warning]
> Flannel **не поддерживает NetworkPolicy**. Если вам нужна изоляция трафика — используйте Calico или Cilium.

### Сравнение CNI

| Критерий | Calico | Cilium | Flannel | Weave |
|----------|--------|--------|---------|-------|
| **Производительность** | Высокая | Очень высокая | Средняя | Средняя |
| **NetworkPolicy** | ✅ | ✅ | ❌ | ✅ |
| **eBPF** | Опционально | ✅ | ❌ | ❌ |
| **BGP** | ✅ | ✅ | ❌ | ❌ |
| **Шифрование** | WireGuard | WireGuard, IPsec | WireGuard | ✅ |
| **L7-фильтрация** | ❌ | ✅ | ❌ | ❌ |
| **Сложность** | Средняя | Высокая | Низкая | Низкая |
| **Замена kube-proxy** | Опционально | ✅ | ❌ | ❌ |

### Как выбрать CNI

| Сценарий | CNI |
|----------|-----|
| Простой кластер | Flannel |
| Нужна NetworkPolicy | Calico, Cilium |
| Максимальная производительность | Cilium |
| L7-фильтрация | Cilium |
| BGP-интеграция | Calico |
| Managed Kubernetes | Зависит от провайдера (EKS — VPC CNI, GKE — Calico/Cilium) |

## Часть 2: DNS в Kubernetes

> **CoreDNS** — DNS-сервер кластера. Резолвит имена Service, Pod и внешних ресурсов.

### Архитектура CoreDNS

```
Pod (DNS-запрос) → kube-dns Service (ClusterIP) → CoreDNS Pod → ответ
```

**Компоненты:**

| Компонент | Роль |
|-----------|------|
| **CoreDNS** | DNS-сервер (заменяет kube-dns) |
| **kube-dns Service** | ClusterIP для DNS (обычно 10.96.0.10) |
| **Corefile** | Конфигурация CoreDNS (ConfigMap) |

**Проверка:**

```bash
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl get svc -n kube-system kube-dns
kubectl get configmap -n kube-system coredns -o yaml
```

### DNS-имена

| Ресурс | DNS-имя |
|--------|---------|
| Service (ClusterIP) | `<service>.<namespace>.svc.cluster.local` |
| Headless Service | `<pod-name>.<service>.<namespace>.svc.cluster.local` |
| Pod (по IP) | `<ip-dashed>.<namespace>.pod.cluster.local` |
| ExternalName | CNAME на `externalName` |

**Примеры:**

```
web-app.default.svc.cluster.local
web-app-0.web-app.default.svc.cluster.local
10-244-1-5.default.pod.cluster.local
```

**Короткие имена:**

Внутри namespace `default`:
- `web-app` → `web-app.default.svc.cluster.local`
- `web-app.default` → `web-app.default.svc.cluster.local`
- `web-app.default.svc` → `web-app.default.svc.cluster.local`

**Проверка:**

```bash
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup web-app
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup web-app.default.svc.cluster.local
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup kubernetes.default
```

### resolv.conf в Pod

Каждый Pod получает `/etc/resolv.conf`:

```
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

| Параметр | Значение |
|----------|----------|
| `nameserver` | IP CoreDNS (ClusterIP) |
| `search` | Домены для поиска коротких имён |
| `ndots:5` | Если в имени < 5 точек — сначала пробовать search-домены |

**ndots:5 — важно.** Если вы резолвите `api.example.com` (2 точки), Kubernetes сначала попробует:
1. `api.example.com.default.svc.cluster.local` — fail
2. `api.example.com.svc.cluster.local` — fail
3. `api.example.com.cluster.local` — fail
4. `api.example.com` — success

Это создаёт **лишние DNS-запросы**. Для внешних доменов используйте FQDN с точкой на конце: `api.example.com.`

### dnsPolicy

| dnsPolicy | Описание |
|-----------|----------|
| `ClusterFirst` (по умолчанию) | Сначала CoreDNS, потом внешние |
| `Default` | Наследует DNS узла |
| `ClusterFirstWithHostNet` | Для Pod с hostNetwork |
| `None` | Свои настройки DNS |

**Пример с `None`:**

```yaml
spec:
  dnsPolicy: None
  dnsConfig:
    nameservers:
      - 8.8.8.8
    searches:
      - example.com
    options:
      - name: ndots
        value: "2"
```

### NodeLocal DNSCache

> **NodeLocal DNSCache** — кэш DNS на каждом узле. Снижает нагрузку на CoreDNS.

**Установка:**

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/kubernetes/master/cluster/addons/dns/nodelocaldns/nodelocaldns.yaml
```

**Преимущества:**
- Меньше latency (localhost).
- Меньше нагрузка на CoreDNS.
- Устойчивость к сбоям CoreDNS.

### Кастомизация CoreDNS

**ConfigMap `coredns` в `kube-system`:**

```
.:53 {
    errors
    health {
       lameduck 5s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
}
```

**Добавление кастомной зоны:**

```
example.com:53 {
    forward . 8.8.8.8
}
```

**Rewriting:**

```
rewrite name regex (.*)\.example\.com {1}.example.org
```

## Часть 3: kube-proxy

> **kube-proxy** — компонент на каждом узле, реализующий Service. Он программирует правила iptables/IPVS для маршрутизации трафика на Pod.

### Что делает kube-proxy

1. Watch API на изменения Service и Endpoints.
2. Программирует правила в iptables/IPVS.
3. Когда пакет идёт на ClusterIP — перенаправляет на один из Pod.
4. Обеспечивает балансировку нагрузки.

### Режимы kube-proxy

| Режим | Описание | Плюсы | Минусы |
|-------|----------|-------|--------|
| **iptables** | По умолчанию. Правила netfilter | Простой, стабильный | Медленно при тысячах Service |
| **IPVS** | LVS (Linux Virtual Server) | Быстро, масштабируется | Сложнее настройка |
| **userspace** | Прокси в userspace | Устаревший | Очень медленно |
| **eBPF** | Cilium заменяет kube-proxy | Максимальная производительность | Требует Cilium |

### iptables-режим

**Как работает:**

1. Service `web-app` имеет ClusterIP `10.96.0.10`.
2. kube-proxy создаёт правила:

```
# Трафик на 10.96.0.10:80
-A KUBE-SERVICES -d 10.96.0.10/32 -p tcp --dport 80 -j KUBE-SVC-XXXXX

# Балансировка
-A KUBE-SVC-XXXXX -m statistic --mode random --probability 0.33 -j KUBE-SEP-POD1
-A KUBE-SVC-XXXXX -m statistic --mode random --probability 0.50 -j KUBE-SEP-POD2
-A KUBE-SVC-XXXXX -j KUBE-SEP-POD3

# DNAT
-A KUBE-SEP-POD1 -p tcp -j DNAT --to-destination 10.244.1.5:8080
```

3. Пакет на `10.96.0.10:80` перехватывается, DNAT на Pod.
4. conntrack запоминает соединение, обратный трафик идёт правильно.

**Просмотр правил:**

```bash
sudo iptables -t nat -L KUBE-SERVICES -n
sudo iptables -t nat -L KUBE-SVC-XXXXX -n
```

**Проблемы iptables:**
- Линейный поиск правил — O(n).
- При тысячах Service — медленно.
- Обновление правил блокирует трафик.

### IPVS-режим

> **IPVS (IP Virtual Server)** — встроенный в ядро Linux L4-балансировщик. Использует хеш-таблицы.

**Включение:**

```bash
kubectl edit configmap kube-proxy -n kube-system
# Изменить mode: "ipvs"

kubectl rollout restart daemonset kube-proxy -n kube-system
```

**Проверка:**

```bash
sudo ipvsadm -L -n
```

**Пример вывода:**

```
TCP  10.96.0.10:80 rr
  -> 10.244.1.5:8080              Masq    1      0          0
  -> 10.244.2.6:8080              Masq    1      0          0
  -> 10.244.3.7:8080              Masq    1      0          0
```

**Алгоритмы балансировки:**

| Алгоритм | Описание |
|----------|----------|
| `rr` | Round Robin |
| `wrr` | Weighted Round Robin |
| `lc` | Least Connections |
| `wlc` | Weighted Least Connections |
| `sh` | Source Hashing |
| `mh` | Maglev Hashing |

**Настройка в ConfigMap:**

```yaml
ipvs:
  scheduler: "rr"
  minSyncPeriod: 0s
  syncPeriod: 30s
```

### eBPF-режим (Cilium)

Cilium заменяет kube-proxy на eBPF-программы:

**Преимущества:**
- Нет iptables — быстрее.
- Сохраняет source IP.
- L7-фильтрация.
- Меньше latency.

**Установка Cilium с заменой kube-proxy:**

```bash
helm install cilium cilium/cilium \
  --namespace kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=<api-server-ip> \
  --set k8sServicePort=<api-server-port>
```

**Проверка:**

```bash
cilium status | grep KubeProxyReplacement
```

### sessionAffinity

По умолчанию Service балансирует каждый запрос. Можно включить **session affinity**:

```yaml
spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800
```

Теперь все запросы с одного IP идут на один Pod (в течение timeout).

### externalTrafficPolicy

Для NodePort и LoadBalancer:

| Значение | Поведение |
|----------|-----------|
| `Cluster` (по умолчанию) | Трафик может идти на Pod на другом узле |
| `Local` | Трафик идёт только на Pod на этом узле |

**`Local`** сохраняет source IP, но может привести к дисбалансу.

```yaml
spec:
  externalTrafficPolicy: Local
```

### internalTrafficPolicy

С v1.22:

| Значение | Поведение |
|----------|-----------|
| `Cluster` (по умолчанию) | Трафик может идти на любой Pod |
| `Local` | Трафик идёт только на Pod на этом узле |

```yaml
spec:
  internalTrafficPolicy: Local
```

## Как всё работает вместе: полный путь пакета

Рассмотрим, что происходит, когда Pod A обращается к Service B.

### Шаг 1: DNS-резолвинг

1. Pod A делает DNS-запрос на `web-app.default.svc.cluster.local`.
2. Запрос идёт на CoreDNS (ClusterIP `10.96.0.10`).
3. CoreDNS возвращает ClusterIP Service `10.96.0.20`.

### Шаг 2: Отправка пакета

1. Pod A отправляет пакет на `10.96.0.20:80`.
2. Пакет идёт через veth pair на узел.
3. На узле срабатывают правила kube-proxy (iptables/IPVS).
4. DNAT: `10.96.0.20:80` → `10.244.2.6:8080` (Pod B).
5. Если Pod B на другом узле — пакет идёт через CNI (VXLAN, IP-in-IP, BGP).

### Шаг 3: Ответ

1. Pod B отвечает.
2. conntrack на узле A помнит соединение.
3. Обратный трафик идёт через DNAT обратно.
4. Pod A получает ответ.

### Шаг 4: NetworkPolicy

Если есть NetworkPolicy — CNI проверяет, разрешён ли трафик между Pod A и Pod B. Если нет — пакет дропается.

## Диагностика сетевых проблем

### Проверка CNI

```bash
kubectl get pods -n kube-system | grep -E "calico|cilium|flannel"
kubectl logs -n kube-system <cni-pod>
ls /etc/cni/net.d/
```

### Проверка DNS

```bash
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup web-app
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- cat /etc/resolv.conf
kubectl logs -n kube-system -l k8s-app=kube-dns
```

### Проверка Service

```bash
kubectl get svc web-app
kubectl get endpoints web-app
kubectl describe svc web-app
```

**Если Endpoints пуст:** selector Service не совпадает с labels Pod.

### Проверка kube-proxy

```bash
kubectl get pods -n kube-system -l k8s-app=kube-proxy
kubectl logs -n kube-system -l k8s-app=kube-proxy
sudo iptables -t nat -L KUBE-SERVICES -n | head
sudo ipvsadm -L -n
```

### Проверка связности

```bash
# Из Pod A в Pod B
kubectl exec -it pod-a -- ping <pod-b-ip>
kubectl exec -it pod-a -- wget -qO- http://web-app

# Из узла в Pod
ping <pod-ip>
```

### Типичные проблемы

| Симптом | Причина | Решение |
|---------|---------|---------|
| Pod не получает IP | CNI не установлен | Установить CNI |
| Service не резолвится | CoreDNS не работает | Проверить CoreDNS Pod |
| Service не доступен | Endpoints пуст | Проверить selector |
| Трафик не идёт между узлами | CNI не настроен | Проверить маршруты |
| NetworkPolicy блокирует | Политика слишком строгая | Проверить NetworkPolicy |
| DNS-запросы медленные | ndots:5 | Использовать FQDN с точкой |

## Итог

1. **CNI** — реализация сети Pod. Calico, Cilium, Flannel — основные.
2. **Overlay** (VXLAN, IP-in-IP) vs **Underlay** (BGP).
3. **Cilium** — eBPF, заменяет kube-proxy, L7-фильтрация.
4. **Calico** — BGP, NetworkPolicy, гибкость.
5. **Flannel** — просто, но без NetworkPolicy.
6. **CoreDNS** — DNS кластера. `ndots:5` — важно.
7. **kube-proxy** — iptables, IPVS, eBPF.
8. **IPVS** быстрее iptables при тысячах Service.
9. **NetworkPolicy** — firewall на уровне Pod. Требует CNI с поддержкой.
10. **NodeLocal DNSCache** — кэш DNS на узле.

> [!tip]
> **Правило выбора CNI:**
> - Простой кластер → **Flannel**
> - Нужна NetworkPolicy → **Calico**
> - Максимальная производительность, L7 → **Cilium**
> - Managed Kubernetes → используйте то, что даёт провайдер

> [!warning]
> Не устанавливайте несколько CNI одновременно. Это приведёт к конфликтам маршрутов и непредсказуемому поведению.
