# 02. Ресурсы и автомасштабирование: requests, limits, HPA, VPA

Мы разобрались, как scheduler выбирает узел. Но scheduler принимает решения на основе **ресурсов**, которые запрашивает Pod. Что такое requests и limits? Как они влияют на планирование? Как автоматически масштабировать приложение при росте нагрузки?

В этой лекции разберём **управление ресурсами** и **автомасштабирование**.

> **Requests** — сколько ресурсов гарантированно нужно Pod. **Limits** — максимум, который Pod может потребить. **HPA** — автомасштабирование по метрикам. **VPA** — автомасштабирование requests/limits.

---

## Часть 1: Requests и Limits

### Что такое requests и limits

Каждый контейнер может указать:

```yaml
resources:
  requests:
    memory: "128Mi"
    cpu: "250m"
  limits:
    memory: "256Mi"
    cpu: "500m"
```

| | Requests | Limits |
|---|----------|--------|
| **Назначение** | Гарантия ресурсов | Максимум потребления |
| **Влияет на** | Scheduler (выбор узла) | Cgroups (ограничение) |
| **Что если превышен** | Ничего (это гарантия) | CPU throttling / OOMKill |
| **Кто использует** | Scheduler | kubelet, cgroups |

### CPU: единицы измерения

| Значение | Описание |
|----------|----------|
| `1` | 1 CPU (1 ядро) |
| `0.5` | Половина ядра |
| `500m` | 500 millicpu = 0.5 CPU |
| `100m` | 0.1 CPU |
| `1000m` | 1 CPU |

**Пример:** `cpu: "250m"` = 0.25 ядра = 25% одного ядра.

### Memory: единицы измерения

| Значение | Описание |
|----------|----------|
| `128Mi` | 128 мебибайт (1024²) |
| `1Gi` | 1 гибибайт |
| `128M` | 128 мегабайт (1000²) |
| `1G` | 1 гигабайт |

> [!note]
> `Mi` (мебибайт) = 1024² = 1,048,576 байт. `M` (мегабайт) = 1000² = 1,000,000 байт. В Kubernetes обычно используют `Mi` и `Gi`.

### Как requests влияют на scheduling

Scheduler суммирует requests всех Pod на узле и сравнивает с capacity узла.

**Пример:**

```
Узел: 4 CPU, 16Gi RAM
Уже запланировано:
  Pod A: requests 1 CPU, 2Gi
  Pod B: requests 2 CPU, 4Gi
  Итого: 3 CPU, 6Gi

Новый Pod: requests 2 CPU, 4Gi
Свободно: 1 CPU, 10Gi
→ Не хватает CPU → Pod в Pending
```

**Проверка:**

```bash
kubectl describe node node-1 | grep -A10 "Allocated resources"
```

**Пример вывода:**

```
Allocated resources:
  Resource           Requests    Limits
  --------           --------    ------
  cpu                1500m (37%) 3000m (75%)
  memory             2Gi (12%)   4Gi (25%)
```

### Как limits влияют на runtime

**CPU limits:**
- Если контейнер превышает CPU limit — **throttling** (замедление).
- Контейнер не убивается, но получает меньше CPU.
- Проверка: `container_cpu_cfs_throttled_seconds_total`.

**Memory limits:**
- Если контейнер превышает memory limit — **OOMKilled**.
- Контейнер убивается, Pod перезапускается.
- Проверка: `kubectl describe pod` → `OOMKilled`.

### QoS классы

Kubernetes присваивает Pod **QoS-класс** на основе requests/limits:

| QoS | Условие | Приоритет при eviction |
|-----|---------|------------------------|
| **Guaranteed** | requests == limits для всех контейнеров | Высший |
| **Burstable** | requests < limits | Средний |
| **BestEffort** | Нет requests и limits | Низший |

**Guaranteed:**

```yaml
resources:
  requests:
    memory: "128Mi"
    cpu: "250m"
  limits:
    memory: "128Mi"
    cpu: "250m"
```

**Burstable:**

```yaml
resources:
  requests:
    memory: "128Mi"
    cpu: "250m"
  limits:
    memory: "256Mi"
    cpu: "500m"
```

**BestEffort:**

```yaml
# Нет resources вообще
```

> [!important]
> **Guaranteed Pod** — последние, кого выселяют при нехватке ресурсов. **BestEffort** — первые. Для критичных сервисов используйте Guaranteed.

### Eviction: вытеснение при нехватке

Когда узел испытывает нехватку ресурсов (MemoryPressure, DiskPressure), kubelet **вытесняет** Pod:

1. BestEffort — первыми.
2. Burstable — следующими (по превышению requests).
3. Guaranteed — последними.

**Проверка:**

```bash
kubectl get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
```

### LimitRange: дефолтные requests/limits

> **LimitRange** — устанавливает дефолтные requests/limits для namespace.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: default
spec:
  limits:
    - default:
        memory: "256Mi"
        cpu: "500m"
      defaultRequest:
        memory: "128Mi"
        cpu: "250m"
      max:
        memory: "1Gi"
        cpu: "2"
      min:
        memory: "64Mi"
        cpu: "100m"
      type: Container
```

**Что произойдёт:**
- Pod без requests получит `defaultRequest`.
- Pod без limits получит `default`.
- Pod с requests > `max` — отклонён.
- Pod с requests < `min` — отклонён.

### ResourceQuota: квоты на namespace

> **ResourceQuota** — ограничивает общее потребление ресурсов в namespace.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: default
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"
    pods: "50"
    services: "10"
    persistentvolumeclaims: "5"
```

**Что произойдёт:** если namespace превысит квоту — новые Pod будут отклонены.

**Проверка:**

```bash
kubectl describe resourcequota compute-quota -n default
```

### Best practices для requests/limits

| Практика | Почему |
|----------|--------|
| **Всегда указывайте requests** | Scheduler не сможет корректно распределить Pod |
| **Memory limits = requests** | Guaranteed QoS, защита от OOM |
| **CPU limits — опционально** | CPU throttling может замедлить приложение |
| **Не ставьте слишком маленькие limits** | OOMKilled, throttling |
| **Не ставьте слишком большие limits** | Неэффективное использование ресурсов |
| **Используйте VPA для подбора** | Автоматическая оптимизация |
| **Мониторьте actual usage** | Prometheus + Grafana |

> [!tip]
> **Правило:** requests = типичное потребление. limits = пиковое потребление. Memory limits = memory requests (Guaranteed). CPU limits — можно не ставить (Burstable).

## Часть 2: HPA (Horizontal Pod Autoscaler)

> **HPA** — автомасштабирование **количества** Pod на основе метрик.

### Как работает HPA

```
┌─────────────────────────────────────────────────────────────┐
│                       HPA Controller                         │
│                                                              │
│  1. Читает метрики (Metrics Server, Prometheus)             │
│  2. Сравнивает с target                                      │
│  3. Вычисляет desired replicas                               │
│  4. Обновляет Deployment/ReplicaSet                          │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│                    Deployment (replicas: 3)                  │
│                                                              │
│  HPA: min=2, max=10, target CPU=70%                         │
│  Current CPU: 90% → desired = 3 * (90/70) = 4              │
│  → scale to 4                                                │
└─────────────────────────────────────────────────────────────┘
```

### Формула

```
desiredReplicas = ceil(currentReplicas × (currentMetric / targetMetric))
```

**Пример:**
- `currentReplicas = 3`
- `currentCPU = 90%`
- `targetCPU = 70%`
- `desired = ceil(3 × 90/70) = ceil(3.86) = 4`

### Манифест HPA (v2)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 100
          periodSeconds: 15
        - type: Pods
          value: 4
          periodSeconds: 15
      selectPolicy: Max
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `scaleTargetRef` | Что масштабировать (Deployment, StatefulSet) |
| `minReplicas` | Минимум Pod |
| `maxReplicas` | Максимум Pod |
| `metrics` | Метрики для масштабирования |
| `behavior` | Как быстро масштабировать |

### Типы метрик

| Тип | Описание | Пример |
|-----|----------|--------|
| `Resource` | CPU, memory | `averageUtilization: 70` |
| `Pods` | Метрика на Pod | `averageValue: 100` |
| `Object` | Метрика на объект | `value: 1000` |
| `External` | Внешняя метрика | Prometheus, Kafka lag |
| `ContainerResource` | Метрика на контейнер | Для sidecar |

### Требования

1. **Metrics Server** — для CPU/memory.
2. **Requests** — обязательно указаны в Pod.
3. **Prometheus Adapter** — для кастомных метрик.

**Установка Metrics Server:**

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

**Проверка:**

```bash
kubectl top nodes
kubectl top pods
kubectl get hpa
```

### Поведение (behavior)

**scaleDown:**
- `stabilizationWindowSeconds: 300` — 5 минут. HPA смотрит на метрики за последние 5 минут и берёт **максимум**. Это предотвращает «дёргание».

**scaleUp:**
- `stabilizationWindowSeconds: 0` — реагирует сразу.
- `policies` — не более 100% или 4 Pod за 15 секунд.

**selectPolicy:**
- `Max` — выбирает политику с максимальным изменением.
- `Min` — минимальное.
- `Disabled` — отключено.

### Практический пример

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "500m"
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

```bash
kubectl apply -f deployment.yaml
kubectl apply -f hpa.yaml
kubectl get hpa -w
```

**Нагрузка:**

```bash
kubectl run -it --rm load --image=busybox:1.36 --restart=Never -- sh -c "while true; do wget -qO- http://web-app; done"
```

**Наблюдение:**

```bash
kubectl get hpa -w
# NAME          REFERENCE            TARGETS   MINPODS   MAXPODS   REPLICAS
# web-app-hpa   Deployment/web-app   5%/70%    2         10        3
# web-app-hpa   Deployment/web-app   85%/70%   2         10        3
# web-app-hpa   Deployment/web-app   85%/70%   2         10        4
```

### HPA с кастомными метриками (Prometheus)

**Prometheus Adapter:**

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install prometheus-adapter prometheus-community/prometheus-adapter -n monitoring
```

**HPA с кастомной метрикой:**

```yaml
metrics:
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "100"
```

### HPA с внешними метриками (Kafka lag)

```yaml
metrics:
  - type: External
    external:
      metric:
        name: kafka_consumer_lag
        selector:
          matchLabels:
            topic: orders
      target:
        type: AverageValue
        averageValue: "1000"
```

### Ограничения HPA

| Ограничение | Решение |
|-------------|---------|
| Не работает без requests | Указать requests |
| Не работает без Metrics Server | Установить Metrics Server |
| Не масштабирует по кастомным метрикам без адаптера | Установить Prometheus Adapter |
| Не подходит для stateful | Использовать VPA или ручное |
| Не работает с DaemonSet | DaemonSet не масштабируется |

## Часть 3: VPA (Vertical Pod Autoscaler)

> **VPA** — автомасштабирование **requests/limits** Pod.

### Как работает VPA

```
┌─────────────────────────────────────────────────────────────┐
│                       VPA Controller                         │
│                                                              │
│  1. Читает actual usage (Metrics Server)                    │
│  2. Вычисляет recommended requests/limits                   │
│  3. Обновляет Pod (пересоздаёт)                             │
└─────────────────────────────────────────────────────────────┘
```

### Компоненты VPA

| Компонент | Роль |
|-----------|------|
| **VPA Recommender** | Вычисляет recommendations |
| **VPA Updater** | Обновляет Pod (evict) |
| **VPA Admission Controller** | Применяет recommendations при создании Pod |

### Манифест VPA

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-app-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  updatePolicy:
    updateMode: "Auto"
  resourcePolicy:
    containerPolicies:
      - containerName: "*"
        minAllowed:
          cpu: "100m"
          memory: "128Mi"
        maxAllowed:
          cpu: "2"
          memory: "2Gi"
        controlledResources: ["cpu", "memory"]
```

### UpdateMode

| Режим | Поведение |
|-------|-----------|
| `Off` | Только recommendations, не применяет |
| `Initial` | Применяет при создании Pod |
| `Recreate` | Пересоздаёт Pod при изменении |
| `Auto` | Как Recreate |

> [!warning]
> VPA **пересоздаёт Pod** при изменении requests. Это может привести к downtime. Используйте с осторожностью.

### Просмотр recommendations

```bash
kubectl get vpa web-app-vpa -o yaml
```

**Пример:**

```yaml
status:
  recommendation:
    containerRecommendations:
      - containerName: web
        lowerBound:
          cpu: "100m"
          memory: "128Mi"
        target:
          cpu: "250m"
          memory: "256Mi"
        upperBound:
          cpu: "500m"
          memory: "512Mi"
```

### VPA vs HPA

| HPA | VPA |
|-----|-----|
| Масштабирует количество Pod | Масштабирует requests/limits |
| Не пересоздаёт Pod | Пересоздаёт Pod |
| Для stateless | Для stateless и stateful |
| Быстро | Медленно |
| Требует Metrics Server | Требует Metrics Server |

> [!important]
> **HPA и VPA несовместимы** для одной и той же метрики (CPU/memory). Если HPA масштабирует по CPU, VPA не должен управлять CPU. Можно использовать VPA для memory и HPA для CPU.

## Часть 4: Cluster Autoscaler

> **Cluster Autoscaler** — добавление/удаление **узлов** при нехватке/избытке ресурсов.

### Как работает

```
┌─────────────────────────────────────────────────────────────┐
│                    Cluster Autoscaler                        │
│                                                              │
│  1. Видит Pod в Pending (нет ресурсов)                      │
│  2. Добавляет узел в node group                             │
│  3. Pod запускается                                         │
│                                                              │
│  1. Видит пустые узлы                                       │
│  2. Удаляет их                                              │
└─────────────────────────────────────────────────────────────┘
```

### Установка (AWS EKS)

```bash
eksctl create cluster --name my-cluster --nodes-min=2 --nodes-max=10
# Cluster Autoscaler устанавливается автоматически
```

**Или вручную:**

```bash
helm repo add autoscaler https://kubernetes.github.io/autoscaler
helm install cluster-autoscaler autoscaler/cluster-autoscaler \
  --namespace kube-system \
  --set autoDiscovery.clusterName=my-cluster \
  --set awsRegion=us-east-1
```

### Аннотации для autoscaling

```yaml
metadata:
  annotations:
    cluster-autoscaler.kubernetes.io/safe-to-evict: "true"
```

### Когда Cluster Autoscaler добавляет узел

- Pod в Pending из-за нехватки ресурсов.
- Нет подходящего узла (affinity, taints).

### Когда Cluster Autoscaler удаляет узел

- Узел недозагружен (< 50%).
- Все Pod на узле можно переместить.
- Нет Pod с `safe-to-evict: false`.

### Проверка

```bash
kubectl get nodes
kubectl logs -n kube-system cluster-autoscaler-<pod>
kubectl get pods -n kube-system | grep autoscaler
```

## Практический пример: полный стек

### Deployment + HPA + VPA

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "500m"
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
---
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-app-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  updatePolicy:
    updateMode: "Off"    # только recommendations
```

**Использование:**
- HPA масштабирует по CPU.
- VPA даёт рекомендации по memory (не применяет).
- Cluster Autoscaler добавляет узлы при необходимости.

## Troubleshooting

### HPA: TARGETS unknown

```
NAME          REFERENCE            TARGETS         MINPODS   MAXPODS
web-app-hpa   Deployment/web-app   <unknown>/70%   2         10
```

**Причины:**
- Metrics Server не установлен.
- Pod не имеет requests.
- Pod не Ready.

**Решение:**

```bash
kubectl top pods
kubectl get pods
kubectl describe hpa web-app-hpa
```

### HPA не масштабирует

**Причины:**
- Метрики не достигают target.
- `minReplicas == maxReplicas`.
- Pod не имеет requests.

**Решение:**

```bash
kubectl describe hpa web-app-hpa
kubectl get hpa -w
```

### OOMKilled

**Причины:**
- Memory limit слишком маленький.
- Утечка памяти.

**Решение:**

```bash
kubectl describe pod my-pod | grep -i oom
# Увеличить limits.memory
# Использовать VPA для рекомендаций
```

### CPU throttling

**Причины:**
- CPU limit слишком маленький.
- Приложение требует больше CPU.

**Решение:**

```bash
# Проверить throttling
kubectl top pods
# Увеличить limits.cpu или убрать CPU limits
```

### Pod в Pending из-за ресурсов

```
0/5 nodes are available: 5 Insufficient cpu.
```

**Решение:**
- Уменьшить requests.
- Добавить узлы (Cluster Autoscaler).
- Удалить ненужные Pod.

### VPA не применяет recommendations

**Причины:**
- `updateMode: Off`.
- VPA Updater не запущен.
- Pod не управляется Deployment.

**Решение:**

```bash
kubectl get vpa web-app-vpa -o yaml
kubectl logs -n kube-system vpa-updater-<pod>
```

## Итог

1. **Requests** — гарантия ресурсов. Влияет на scheduling.
2. **Limits** — максимум. CPU — throttling, memory — OOMKilled.
3. **QoS:** Guaranteed, Burstable, BestEffort.
4. **LimitRange** — дефолтные requests/limits.
5. **ResourceQuota** — квоты на namespace.
6. **HPA** — масштабирование количества Pod по метрикам.
7. **VPA** — масштабирование requests/limits.
8. **Cluster Autoscaler** — добавление/удаление узлов.
9. **HPA и VPA несовместимы** для одной метрики.
10. **Всегда указывайте requests.**

> [!tip]
> **Правило выбора:**
> - Stateless с переменной нагрузкой → **HPA**
> - Нужна оптимизация requests → **VPA**
> - Не хватает узлов → **Cluster Autoscaler**
> - Критичные сервисы → **Guaranteed QoS**
> - Batch-задачи → **BestEffort** (если можно)

> [!warning]
> Не ставьте `limits.memory` меньше, чем реальное потребление. OOMKilled — частая причина падений.
