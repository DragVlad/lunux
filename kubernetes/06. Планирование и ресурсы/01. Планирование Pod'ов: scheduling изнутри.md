# 01. Планирование Pod'ов: scheduling изнутри

Мы научились создавать Pod, Deployment, StatefulSet. Но кто решает, **на каком узле** запустить Pod? Как Kubernetes выбирает узел, если их десятки? Что делать, если Pod должен быть на конкретном узле? Что если узел перегружен?

Ответ — **kube-scheduler**. В этой лекции разберём, как работает планирование изнутри.

> **Scheduling** — процесс выбора узла для Pod. Выполняется компонентом **kube-scheduler** в Control Plane.

---

## Зачем нужен scheduler

Представьте кластер из 100 узлов. Вы создаёте Pod. Вопросы:

- На каком узле есть свободные ресурсы?
- На каком узле есть нужный GPU?
- Как распределить Pod равномерно?
- Как избежать, чтобы все реплики БД оказались на одном узле?
- Что делать, если узел имеет taint, а Pod — toleration?

Scheduler отвечает на все эти вопросы. Он **не запускает** Pod — он только **назначает** узел. Запуском занимается kubelet.

---

## Как работает scheduler

### Два этапа: Filtering и Scoring

```
┌─────────────────────────────────────────────────────────────┐
│                    Все узлы кластера                         │
│  node-1  node-2  node-3  node-4  node-5  ...  node-100     │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  1. Filtering         │  ← Отсеиваем неподходящие
              │  (Predicates)         │
              └───────────┬───────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  Подходящие узлы      │
              │  node-2, node-5, ...  │
              └───────────┬───────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  2. Scoring           │  ← Оцениваем каждый
              │  (Priorities)         │
              └───────────┬───────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  Лучший узел          │
              │  node-5               │
              └───────────────────────┘
```

### Этап 1: Filtering (Predicates)

Scheduler отсеивает узлы, которые **не могут** запустить Pod:

| Фильтр | Что проверяет |
|--------|---------------|
| **NodeResourcesFit** | Хватает ли CPU/RAM (requests) |
| **NodeName** | Совпадает ли `nodeName` |
| **NodeSelector** | Совпадают ли labels узла |
| **NodeAffinity** | Соответствует ли affinity |
| **TaintsTolerations** | Есть ли tolerations для taints |
| **PodAffinity/AntiAffinity** | Соответствует ли affinity к другим Pod |
| **VolumeBinding** | Можно ли смонтировать PVC на этом узле |
| **VolumeZone** | Совпадает ли зона PV с зоной узла |
| **PodTopologySpread** | Соответствует ли spread constraints |
| **NodeUnschedulable** | Не cordoned ли узел |
| **NodePorts** | Свободны ли hostPorts |
| **NodeConditions** | Не в состоянии ли узел `NotReady`, `MemoryPressure` |

**Пример:** Pod запрашивает 2 CPU. Узел имеет 1 CPU свободный → **отсеян**.

### Этап 2: Scoring (Priorities)

Среди подходящих узлов scheduler выбирает **лучший** по сумме весов:

| Приоритет | Вес | Что учитывает |
|-----------|-----|---------------|
| **NodeResourcesBalancedAllocation** | 1 | Баланс CPU/RAM |
| **NodeResourcesLeastAllocated** | 1 | Меньше занятых ресурсов — выше |
| **InterPodAffinity** | 2 | Соответствие pod affinity |
| **NodeAffinity** | 2 | Соответствие node affinity |
| **PodTopologySpread** | 2 | Равномерность распределения |
| **ImageLocality** | 1 | Есть ли образ на узле |
| **TaintToleration** | 3 | Меньше taints — выше |
| **NodePreferAvoidPods** | 10000 | Приоритет узла |

**Формула:**

```
finalScore = Σ (weight_i × score_i)
```

Узел с наивысшим score выбирается.

### Этап 3: Binding

Scheduler записывает решение в API-сервер:

```yaml
apiVersion: v1
kind: Binding
metadata:
  name: my-pod
target:
  apiVersion: v1
  kind: Node
  name: node-5
```

API-сервер обновляет Pod: `spec.nodeName = node-5`. Kubelet на `node-5` видит Pod и запускает его.

## NodeSelector: простейший способ

> **nodeSelector** — привязка Pod к узлам по labels.

### Шаг 1: Пометить узел

```bash
kubectl label nodes node-1 disktype=ssd
kubectl label nodes node-2 disktype=hdd
```

### Шаг 2: Использовать в Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  nodeSelector:
    disktype: ssd
  containers:
    - name: app
      image: myapp:1.0
```

**Что произойдёт:** Pod запустится только на `node-1` (у которого `disktype=ssd`).

**Ограничения:**
- Только точное совпадение.
- Нет выражений (AND, OR, NOT).
- Нет "предпочтений" (только жёсткое требование).

Для более сложных сценариев — **nodeAffinity**.

---

## NodeAffinity: гибкая привязка

> **nodeAffinity** — более мощный механизм привязки Pod к узлам. Поддерживает выражения, `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`.

### requiredDuringSchedulingIgnoredDuringExecution

**Жёсткое требование.** Pod не запустится, если нет подходящего узла.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd
                  - nvme
              - key: zone
                operator: In
                values:
                  - us-east-1a
  containers:
    - name: app
      image: myapp:1.0
```

**Что произойдёт:** Pod запустится только на узле с `disktype=ssd` или `nvme` **И** `zone=us-east-1a`.

### preferredDuringSchedulingIgnoredDuringExecution

**Мягкое предпочтение.** Scheduler попытается, но если нет — запустит на любом.

```yaml
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd
        - weight: 50
          preference:
            matchExpressions:
              - key: zone
                operator: In
                values:
                  - us-east-1a
```

**Вес:** от 1 до 100. Чем выше — тем важнее.

### Операторы

| Оператор | Описание | Пример |
|----------|----------|--------|
| `In` | Значение в списке | `disktype In [ssd, nvme]` |
| `NotIn` | Значение не в списке | `disktype NotIn [hdd]` |
| `Exists` | Ключ существует | `gpu Exists` |
| `DoesNotExist` | Ключ не существует | `gpu DoesNotExist` |
| `Gt` | Больше | `cores Gt 8` |
| `Lt` | Меньше | `cores Lt 4` |

### required vs preferred

| | required | preferred |
|---|----------|-----------|
| **Поведение** | Жёсткое | Мягкое |
| **Если нет подходящего узла** | Pod в `Pending` | Запустится на любом |
| **Использование** | GPU, SSD, зона | Оптимизация |

> [!tip]
> Используйте `required` для критичных требований (GPU, архитектура). `preferred` — для оптимизации (SSD предпочтительнее HDD, но не обязательно).

## Taints и Tolerations

> **Taint** — метка на узле, которая **отталкивает** Pod. **Toleration** — метка на Pod, которая **разрешает** запуск на узле с taint.

**Аналогия:** taint — это «злая собака» на узле. Toleration — «косточка» для собаки.

### Taint на узле

```bash
kubectl taint nodes node-1 dedicated=gpu:NoSchedule
```

**Формат:** `key=value:effect`

| Effect | Описание |
|--------|----------|
| `NoSchedule` | Новые Pod не запускаются (существующие остаются) |
| `PreferNoSchedule` | Scheduler старается не запускать |
| `NoExecute` | Существующие Pod **выселяются** |

### Toleration на Pod

```yaml
spec:
  tolerations:
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule
```

**Что произойдёт:** Pod сможет запуститься на `node-1`.

### Операторы в tolerations

| Оператор | Описание |
|----------|----------|
| `Equal` | Точное совпадение key и value |
| `Exists` | Совпадение только по key |

**Пример с Exists:**

```yaml
tolerations:
  - key: dedicated
    operator: Exists
    effect: NoSchedule
```

Pod терпит любой taint с ключом `dedicated`.

### Пример: control-plane узлы

Control-plane узлы имеют taint:

```
node-role.kubernetes.io/control-plane:NoSchedule
```

DaemonSet для сбора логов должен иметь toleration:

```yaml
tolerations:
  - key: node-role.kubernetes.io/control-plane
    operator: Exists
    effect: NoSchedule
```

### NoExecute: выселение

`NoExecute` не только блокирует новые Pod, но и **выселяет существующие**.

```bash
kubectl taint nodes node-1 maintenance=true:NoExecute
```

**Что произойдёт:** все Pod без toleration будут **удалены** с узла.

**tolerationSeconds:** сколько ждать перед выселением:

```yaml
tolerations:
  - key: maintenance
    operator: Equal
    value: "true"
    effect: NoExecute
    tolerationSeconds: 300    # 5 минут
```

### Удаление taint

```bash
kubectl taint nodes node-1 dedicated=gpu:NoSchedule-
```

Дефис в конце — удаление.

### Просмотр taints

```bash
kubectl describe node node-1 | grep Taints
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

## PodAffinity и PodAntiAffinity

> **PodAffinity** — привязка Pod к другим Pod. **PodAntiAffinity** — отталкивание от других Pod.

**Использование:**
- **PodAffinity:** разместить кэш рядом с БД.
- **PodAntiAffinity:** не размещать реплики на одном узле.

### PodAffinity

```yaml
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: database
          topologyKey: kubernetes.io/hostname
```

**Что произойдёт:** Pod запустится только на узле, где уже есть Pod с `app: database`.

### PodAntiAffinity

```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: web
          topologyKey: kubernetes.io/hostname
```

**Что произойдёт:** Pod не запустится на узле, где уже есть Pod с `app: web`.

### topologyKey

| topologyKey | Описание |
|-------------|----------|
| `kubernetes.io/hostname` | Узел |
| `topology.kubernetes.io/zone` | Зона доступности |
| `topology.kubernetes.io/region` | Регион |

### preferred vs required

Как и в nodeAffinity:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: web
        topologyKey: kubernetes.io/hostname
```

> [!important]
> **PodAntiAffinity с `required` может привести к Pending.** Если у вас 3 реплики и 3 узла, а anti-affinity требует, чтобы реплики были на разных узлах — всё хорошо. Но если узлов 2 — третий Pod будет в `Pending`.

### Пример: HA для веб-приложения

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: web
                topologyKey: kubernetes.io/hostname
      containers:
        - name: web
          image: nginx:1.25
```

**Что произойдёт:** scheduler постарается разместить реплики на разных узлах. Если узлов меньше — некоторые окажутся на одном.

## TopologySpreadConstraints

> **TopologySpreadConstraints** — более гибкий способ равномерного распределения Pod по зонам/узлам.

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels:
          app: web
```

### Разбор

| Поле | Описание |
|------|----------|
| `maxSkew` | Максимальная разница в количестве Pod между зонами |
| `topologyKey` | Домен (zone, hostname, region) |
| `whenUnsatisfiable` | `DoNotSchedule` или `ScheduleAnyway` |
| `labelSelector` | Какие Pod считать |

**Пример:** `maxSkew: 1`, 3 зоны, 6 реплик → по 2 в каждой зоне.

### whenUnsatisfiable

| Значение | Поведение |
|----------|-----------|
| `DoNotSchedule` | Жёсткое требование (Pod в Pending) |
| `ScheduleAnyway` | Мягкое предпочтение |

### Отличие от PodAntiAffinity

| PodAntiAffinity | TopologySpreadConstraints |
|-----------------|---------------------------|
| Не допускает co-location | Равномерно распределяет |
| Жёсткое или мягкое | `maxSkew` — гибкость |
| Только anti-affinity | И spread, и skew |

## PriorityClass: приоритет Pod

> **PriorityClass** — приоритет Pod. Scheduler сначала планирует Pod с высоким приоритетом.

### Создание PriorityClass

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "For critical services"
```

| value | Приоритет |
|-------|-----------|
| 2000000000 | Максимальный (system) |
| 1000000 | Высокий |
| 0 | Default |
| -10 | Низкий |

### Использование

```yaml
spec:
  priorityClassName: high-priority
  containers:
    - name: critical-app
      image: myapp:1.0
```

### Preemption

Если Pod с высоким приоритетом не может быть запланирован — scheduler **выселяет** Pod с низким приоритетом.

> [!warning]
> Preemption может привести к неожиданному удалению Pod. Используйте осторожно.

---

## Preemption: вытеснение

> **Preemption** — scheduler может **вытеснить** Pod с низким приоритетом, чтобы запустить Pod с высоким.

**Как работает:**

1. Pod с высоким приоритетом не может быть запланирован (нет ресурсов).
2. Scheduler ищет узел, где можно вытеснить Pod с низким приоритетом.
3. Вытесняет их, освобождая ресурсы.
4. Запускает Pod с высоким приоритетом.

**Проверка:**

```bash
kubectl describe pod my-pod | grep -A5 "Events:"
# Normal  Preempted  ...  Preempted by default/high-priority-pod on node node-1
```

## Descheduler: перебалансировка

> **Descheduler** — компонент, который **перемещает** Pod для оптимизации.

**Зачем:**
- Узел перегружен, другой — пустой.
- Pod с anti-affinity оказались на одном узле после сбоя.
- Узел был добавлен, но Pod не переехали.

**Установка:**

```bash
helm repo add descheduler https://kubernetes-sigs.github.io/descheduler/
helm install descheduler descheduler/descheduler -n kube-system
```

**Стратегии:**

| Стратегия | Описание |
|-----------|----------|
| `RemoveDuplicates` | Убирает дубликаты Pod на одном узле |
| `LowNodeUtilization` | Перемещает с перегруженных на свободные |
| `HighNodeUtilization` | Консолидирует Pod на меньшее число узлов |
| `RemovePodsViolatingNodeAffinity` | Убирает Pod, нарушающие affinity |
| `RemovePodsViolatingInterPodAntiAffinity` | Убирает Pod, нарушающие anti-affinity |

## Практический пример: HA-приложение

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: node-type
                    operator: In
                    values:
                      - worker
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              preference:
                matchExpressions:
                  - key: disktype
                    operator: In
                    values:
                      - ssd
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: web
                topologyKey: kubernetes.io/hostname
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: web
      containers:
        - name: web
          image: nginx:1.25
          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "500m"
```

**Что получим:**
- Pod только на worker-узлах.
- Предпочтение SSD.
- Реплики на разных узлах.
- Равномерно по зонам.

## Troubleshooting

### Pod в Pending

**Причины:**
- Недостаточно ресурсов.
- Нет узлов с нужными labels.
- Taints без tolerations.
- PVC не Bound.
- PodAntiAffinity слишком строгий.

**Решение:**

```bash
kubectl describe pod my-pod | grep -A10 "Events:"
# Warning  FailedScheduling  ...  0/5 nodes are available: 2 Insufficient cpu
```

### FailedScheduling: Insufficient cpu

**Решение:**
- Уменьшить requests.
- Добавить узлы.
- Удалить ненужные Pod.

### FailedScheduling: taint

```
0/5 nodes are available: 3 node(s) had taint {dedicated: gpu}, that the pod didn't tolerate.
```

**Решение:** добавить toleration.

### FailedScheduling: node affinity

```
0/5 nodes are available: 5 node(s) didn't match node selector.
```

**Решение:** проверить labels узлов.

### PodAntiAffinity Pending

```
0/3 nodes are available: 3 node(s) didn't match pod anti-affinity rules.
```

**Решение:** использовать `preferred` вместо `required` или добавить узлы.

## Итог

1. **Scheduler** выбирает узел для Pod. Два этапа: **Filtering** и **Scoring**.
2. **nodeSelector** — простейшая привязка по labels.
3. **nodeAffinity** — гибкая привязка (`required` / `preferred`).
4. **Taints** отталкивают Pod, **tolerations** разрешают.
5. **PodAffinity** — привязка к другим Pod. **PodAntiAffinity** — отталкивание.
6. **TopologySpreadConstraints** — равномерное распределение.
7. **PriorityClass** — приоритет Pod.
8. **Preemption** — вытеснение низкоприоритетных Pod.
9. **Descheduler** — перебалансировка.
10. **Scheduler не запускает Pod** — только назначает узел.

> [!tip]
> **Правило выбора:**
> - Простая привязка → **nodeSelector**
> - Сложная привязка → **nodeAffinity**
> - Выделенный узел → **taints + tolerations**
> - HA → **PodAntiAffinity + TopologySpreadConstraints**
> - Критичные Pod → **PriorityClass**

> [!warning]
> Не используйте `required` в PodAntiAffinity без понимания. Это частая причина Pending.
