# 01. StatefulSet и Stateful-нагрузки

До сих пор мы работали со **stateless**-приложениями: веб-серверы, API, которые не хранят состояние между запросами. Для них идеально подходит Deployment: Pod взаимозаменяемы, имена случайны, данные не сохраняются.

Но что делать с **stateful**-нагрузками: базы данных, очереди сообщений, кластеры Elasticsearch, Zookeeper, Kafka? Здесь каждый экземпляр **уникален**, хранит **свои данные** и должен **знать своих соседей**. Для этого в Kubernetes есть **StatefulSet**.

> **StatefulSet** — контроллер для управления stateful-приложениями. Гарантирует:
> - **Стабильные имена** Pod (`pod-0`, `pod-1`, `pod-2`).
> - **Стабильные сетевые идентификаторы** (через Headless Service).
> - **Стабильное хранилище** (каждый Pod получает свой PVC).
> - **Упорядоченное развёртывание и масштабирование**.

---

## Deployment vs StatefulSet

| Характеристика | Deployment | StatefulSet |
|----------------|------------|-------------|
| **Имена Pod** | Случайные (`web-app-abc123`) | Предсказуемые (`web-app-0`, `web-app-1`) |
| **Сетевая идентичность** | Нет стабильного DNS | Стабильный DNS: `pod-0.service.ns.svc.cluster.local` |
| **Хранилище** | Общее или эфемерное | Свой PVC на каждый Pod |
| **Порядок запуска** | Параллельно | Последовательно (0 → 1 → 2) |
| **Порядок удаления** | Параллельно | Обратный (2 → 1 → 0) |
| **Масштабирование** | Параллельно | Последовательно |
| **Обновление** | Rolling update (любой порядок) | Rolling update (обратный порядок) |
| **Использование** | Stateless | Stateful (БД, очереди) |

> [!important]
> **Deployment — для stateless. StatefulSet — для stateful.** Не используйте Deployment для БД: потеряете данные и идентичность.

---

## Когда использовать StatefulSet

| Сценарий | Почему StatefulSet |
|----------|-------------------|
| **PostgreSQL / MySQL** | Master-replica, репликация, свой PVC на каждый узел |
| **MongoDB** | Replica set, каждый узел знает соседей |
| **Elasticsearch** | Кластер с уникальными именами нод, свои данные |
| **Kafka** | Каждый брокер — уникальный ID, свои топики |
| **Zookeeper** | Quorum, уникальные ID |
| **Redis (cluster)** | Каждый узел — свой слот данных |
| **Cassandra** | Кольцевая топология, свои данные |

**Когда НЕ использовать StatefulSet:**
- Stateless-приложения (веб, API) — Deployment.
- Одноразовые задачи — Job.
- Периодические задачи — CronJob.
- Демоны на каждом узле — DaemonSet.

## Ключевые особенности StatefulSet

### 1. Стабильные имена Pod

Pod в StatefulSet получают имена вида `<statefulset-name>-<ordinal>`:

```
web-app-0
web-app-1
web-app-2
```

Ordinal — это **порядковый номер** от 0 до `replicas - 1`. Он **не меняется** при пересоздании Pod.

**Преимущества:**
- Каждый Pod знает своё место в кластере.
- Можно настроить репликацию: `pod-0` — master, `pod-1..N` — replicas.
- DNS-имена предсказуемы.

### 2. Стабильный DNS через Headless Service

> **Headless Service** — Service без ClusterIP (`clusterIP: None`). Возвращает DNS-записи для каждого Pod.

**Обычный Service:**
- DNS: `my-service.default.svc.cluster.local` → один ClusterIP.
- Балансирует трафик между Pod.

**Headless Service:**
- DNS: `my-service.default.svc.cluster.local` → список IP всех Pod.
- DNS для каждого Pod: `pod-0.my-service.default.svc.cluster.local`.

**Пример Headless Service:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app
  labels:
    app: web
spec:
  clusterIP: None          # ← Headless
  selector:
    app: web
  ports:
    - port: 80
      name: http
```

**DNS-записи:**

```
web-app.default.svc.cluster.local          → 10.244.1.5, 10.244.2.6, 10.244.3.7
web-app-0.web-app.default.svc.cluster.local → 10.244.1.5
web-app-1.web-app.default.svc.cluster.local → 10.244.2.6
web-app-2.web-app.default.svc.cluster.local → 10.244.3.7
```

**Зачем:** Pod могут находить друг друга по именам. Например, `pod-1` подключается к `pod-0` для репликации.

### 3. Стабильное хранилище

Каждый Pod в StatefulSet получает **свой PersistentVolumeClaim (PVC)** через `volumeClaimTemplates`.

```yaml
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 10Gi
```

**Что произойдёт:**
- Для `web-app-0` создастся PVC `data-web-app-0`.
- Для `web-app-1` создастся PVC `data-web-app-1`.
- Для `web-app-2` создастся PVC `data-web-app-2`.

**Важно:** при удалении Pod PVC **не удаляется**. При пересоздании Pod он подцепит свой PVC. Данные сохранятся.

> [!warning]
> При удалении StatefulSet PVC **тоже не удаляются** автоматически. Удаляйте их вручную, иначе останутся «сироты».

### 4. Упорядоченное развёртывание

StatefulSet создаёт Pod **последовательно**:

1. Создаётся `web-app-0`. Ждём, пока он станет `Running` и `Ready`.
2. Создаётся `web-app-1`. Ждём.
3. Создаётся `web-app-2`. Ждём.

**Зачем:** `pod-0` может быть master, `pod-1` подключается к нему. Если запустить `pod-1` первым — он не найдёт master.

**При масштабировании вниз** — обратный порядок: `pod-2` → `pod-1` → `pod-0`.

### 5. Упорядоченное обновление

При обновлении `template` StatefulSet обновляет Pod в **обратном порядке**:

1. Удаляется `web-app-2`, создаётся новый с новым образом.
2. Ждём `Ready`.
3. Удаляется `web-app-1`, создаётся новый.
4. И так далее.

**Стратегии обновления:**

| Стратегия | Описание |
|-----------|----------|
| `RollingUpdate` (по умолчанию) | Обратный порядок, по одному |
| `OnDelete` | Pod обновляются только при ручном удалении |

### 6. Partition (для canary-обновлений)

```yaml
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    partition: 2
```

При `partition: 2` обновляются только Pod с ordinal **>= 2**. Pod `0` и `1` остаются на старой версии. Это позволяет делать canary.

## Манифест StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web-app
spec:
  serviceName: web-app           # ← Имя Headless Service
  replicas: 3
  selector:
    matchLabels:
      app: web
  updateStrategy:
    type: RollingUpdate
  podManagementPolicy: OrderedReady   # или Parallel
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
              name: http
          volumeMounts:
            - name: data
              mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: standard
        resources:
          requests:
            storage: 1Gi
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `serviceName` | **Обязательно.** Имя Headless Service для сетевой идентичности |
| `replicas` | Количество Pod |
| `selector` | Как StatefulSet находит свои Pod |
| `template` | Шаблон Pod |
| `volumeClaimTemplates` | Шаблон PVC для каждого Pod |
| `podManagementPolicy` | `OrderedReady` (по умолчанию) или `Parallel` |
| `updateStrategy` | `RollingUpdate` или `OnDelete` |

### podManagementPolicy

| Значение | Поведение |
|----------|-----------|
| `OrderedReady` | Последовательно: ждём Ready перед созданием следующего |
| `Parallel` | Параллельно: все Pod создаются одновременно |

`Parallel` используется, когда порядок не важен (например, для некоторых распределённых систем).

## Headless Service + StatefulSet

**Обязательная пара.** StatefulSet требует Headless Service для DNS.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app
  labels:
    app: web
spec:
  clusterIP: None
  selector:
    app: web
  ports:
    - port: 80
      name: http
```

**Что получаем:**

```bash
# DNS-записи
nslookup web-app.default.svc.cluster.local
# Address 1: 10.244.1.5 web-app-0.web-app.default.svc.cluster.local
# Address 2: 10.244.2.6 web-app-1.web-app.default.svc.cluster.local
# Address 3: 10.244.3.7 web-app-2.web-app.default.svc.cluster.local

# Каждый Pod имеет свой DNS
nslookup web-app-0.web-app.default.svc.cluster.local
# Address: 10.244.1.5
```

## Практический пример: StatefulSet с Nginx

### Шаг 1: Headless Service

**Файл `service.yaml`:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-app
  labels:
    app: web
spec:
  clusterIP: None
  selector:
    app: web
  ports:
    - port: 80
      name: http
```

```bash
kubectl apply -f service.yaml
```

### Шаг 2: StatefulSet

**Файл `statefulset.yaml`:**

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web-app
spec:
  serviceName: web-app
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
              name: http
          volumeMounts:
            - name: data
              mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi
```

```bash
kubectl apply -f statefulset.yaml
```

### Шаг 3: Наблюдение за созданием

```bash
# Смотрим, как Pod создаются последовательно
kubectl get pods -l app=web -w
```

**Что увидим:**

```
NAME        READY   STATUS    RESTARTS   AGE
web-app-0   0/1     Pending   0          0s
web-app-0   1/1     Running   0          10s
web-app-1   0/1     Pending   0          0s
web-app-1   1/1     Running   0          10s
web-app-2   0/1     Pending   0          0s
web-app-2   1/1     Running   0          10s
```

### Шаг 4: Проверка PVC

```bash
kubectl get pvc
```

**Вывод:**

```
NAME              STATUS   VOLUME                                     CAPACITY   ACCESS MODES
data-web-app-0    Bound    pvc-abc123...                              1Gi        RWO
data-web-app-1    Bound    pvc-def456...                              1Gi        RWO
data-web-app-2    Bound    pvc-ghi789...                              1Gi        RWO
```

Каждый Pod получил **свой** PVC.

### Шаг 5: Проверка DNS

```bash
# Запустить тестовый Pod
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- sh

# Внутри Pod
nslookup web-app
nslookup web-app-0.web-app
nslookup web-app-1.web-app
nslookup web-app-2.web-app
```

### Шаг 6: Проверка стабильности данных

```bash
# Записать данные в web-app-0
kubectl exec web-app-0 -- sh -c "echo 'Hello from pod-0' > /usr/share/nginx/html/index.html"

# Проверить
kubectl exec web-app-0 -- cat /usr/share/nginx/html/index.html

# Удалить Pod
kubectl delete pod web-app-0

# Дождаться пересоздания
kubectl get pods -l app=web -w

# Проверить данные
kubectl exec web-app-0 -- cat /usr/share/nginx/html/index.html
# Hello from pod-0  ← данные сохранились!
```

### Шаг 7: Масштабирование

```bash
# Увеличить
kubectl scale statefulset web-app --replicas=5
# Создадутся web-app-3, web-app-4

# Уменьшить
kubectl scale statefulset web-app --replicas=2
# Удалятся web-app-4, web-app-3 (в обратном порядке)
# PVC останутся!
```

### Шаг 8: Обновление

```bash
kubectl set image statefulset/web-app nginx=nginx:1.26

# Наблюдаем обратный порядок
kubectl get pods -l app=web -w
```

### Шаг 9: Удаление

```bash
kubectl delete statefulset web-app
kubectl delete service web-app

# PVC остались — удаляем вручную
kubectl delete pvc -l app=web
```

## StatefulSet и PersistentVolume

### Динамическое выделение

Если в кластере есть StorageClass с `provisioner`, PVC создаются автоматически.

```yaml
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 10Gi
```

### Статическое выделение

Можно создать PV заранее и связать с PVC по `volumeName`:

```yaml
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      volumeName: my-pv-0
      resources:
        requests:
          storage: 10Gi
```

### Retain policy

При удалении StatefulSet PVC **не удаляются**. Это защита от потери данных.

**Чтобы удалить:**

```bash
kubectl delete pvc -l app=web
```

**Чтобы PV тоже удалились** — настройте `persistentVolumeReclaimPolicy: Delete` в StorageClass.

## Особенности работы с БД в StatefulSet

### PostgreSQL: master-replica

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-secret
                  key: password
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

**Инициализация master/replica** — через init-контейнеры или entrypoint скрипты. Например, `pod-0` — master, остальные — replicas.

### Kafka

Kafka требует, чтобы каждый брокер имел **уникальный ID** и **свои данные**. StatefulSet идеально подходит:

```yaml
env:
  - name: KAFKA_BROKER_ID
    valueFrom:
      fieldRef:
        fieldPath: metadata.name   # web-app-0, web-app-1, ...
```

### Elasticsearch

Каждая нода Elasticsearch имеет уникальное имя и свои данные. StatefulSet + Headless Service — стандарт для развёртывания Elasticsearch в Kubernetes.

> [!important]
> **Развёртывание БД в Kubernetes — сложная задача.** Для production рассмотрите:
> - **Operators** (Postgres Operator, MySQL Operator, Elastic Cloud on Kubernetes).
> - **Managed-сервисы** (RDS, Cloud SQL, Atlas).
> - **Внешние БД** вне кластера.

---

## Operators: следующий уровень

> **Operator** — это контроллер, который управляет сложным приложением (БД, очередь) через CRD. Он знает, как развернуть, масштабировать, обновлять и восстанавливать приложение.

**Примеры:**

| Operator | Управляет |
|----------|-----------|
| **Zalando Postgres Operator** | PostgreSQL кластерами |
| **Percona Operators** | MySQL, PostgreSQL, MongoDB |
| **Elastic Cloud on Kubernetes (ECK)** | Elasticsearch, Kibana |
| **Strimzi** | Kafka |
| **Redis Operator** | Redis кластерами |
| **MongoDB Community Operator** | MongoDB |

**Operator vs StatefulSet:**

| StatefulSet | Operator |
|-------------|----------|
| Управляет Pod и PVC | Управляет всем жизненным циклом БД |
| Не знает про репликацию | Настраивает репликацию |
| Не делает бэкапы | Автоматические бэкапы |
| Не делает failover | Автоматический failover |
| Ручное обновление | Автоматическое обновление |

**Вывод:** для production БД используйте Operators, а не голые StatefulSet.

## Типичные ошибки

### Забыли Headless Service

```
error: StatefulSet.apps "web-app" is invalid: spec.serviceName: Required value
```

**Решение:** создать Headless Service и указать его в `serviceName`.

### PVC не удаляются

StatefulSet не удаляет PVC при удалении. Это by design. Удаляйте вручную:

```bash
kubectl delete pvc -l app=web
```

### Pod завис в Pending

**Причины:**
- Нет StorageClass.
- Нет PV для PVC.
- Недостаточно ресурсов.

**Решение:**

```bash
kubectl describe pod web-app-0
kubectl get pvc
kubectl get storageclass
```

### OrderedReady тормозит развёртывание

Если `pod-0` не становится Ready — остальные не создаются.

**Решение:** использовать `podManagementPolicy: Parallel` (если порядок не важен).

### Обновление застряло

Если `pod-2` не обновляется — `pod-1` и `pod-0` не будут обновлены.

**Решение:** проверить `kubectl describe pod web-app-2`, исправить проблему.

## Шпаргалка: основные команды

```bash
# Создание
kubectl apply -f service.yaml
kubectl apply -f statefulset.yaml

# Просмотр
kubectl get statefulsets
kubectl get sts
kubectl describe sts web-app
kubectl get pods -l app=web
kubectl get pvc

# Масштабирование
kubectl scale statefulset web-app --replicas=5

# Обновление
kubectl set image statefulset/web-app nginx=nginx:1.26
kubectl rollout status statefulset/web-app
kubectl rollout history statefulset/web-app
kubectl rollout undo statefulset/web-app

# Partition (canary)
kubectl patch statefulset web-app -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'

# Удаление
kubectl delete statefulset web-app
kubectl delete service web-app
kubectl delete pvc -l app=web

# DNS
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup web-app-0.web-app
```

## Итог

1. **StatefulSet** — для stateful-приложений: БД, очереди, кластеры.
2. **Стабильные имена:** `pod-0`, `pod-1`, `pod-2`.
3. **Headless Service** — обязателен для DNS-идентичности.
4. **volumeClaimTemplates** — свой PVC на каждый Pod.
5. **Упорядоченное развёртывание:** 0 → 1 → 2. Удаление: 2 → 1 → 0.
6. **PVC не удаляются** при удалении StatefulSet.
7. **Partition** — для canary-обновлений.
8. **Для production БД используйте Operators**, а не голые StatefulSet.
9. **Deployment — для stateless. StatefulSet — для stateful.** Не путайте.

> [!tip]
> Если вы разворачиваете БД в Kubernetes впервые — начните с managed-сервиса (RDS, Cloud SQL). StatefulSet и Operators — для тех, кто готов нести ответственность за данные.
