# 02. DaemonSet, Job и CronJob

Мы разобрали Deployment (для stateless), StatefulSet (для stateful). Но есть ещё три сценария, которые не покрываются ими:

- **DaemonSet** — запустить Pod на **каждом** узле (или на подмножестве).
- **Job** — выполнить задачу **один раз** до успешного завершения.
- **CronJob** — выполнять задачу **по расписанию**.

В этой лекции разберём все три контроллера.

---

## Часть 1: DaemonSet

> **DaemonSet** — контроллер, который гарантирует, что на **каждом** узле кластера (или на подмножестве, определённом через nodeSelector/affinity) запущена **одна копия** Pod.

### Зачем нужен DaemonSet

Некоторые задачи нужно выполнять **на каждом узле**:

| Задача | Пример |
|--------|--------|
| **Сбор логов** | Fluent Bit, Promtail, Filebeat |
| **Сбор метрик** | node-exporter |
| **Сетевая подсистема** | CNI-плагины (Calico, Cilium), kube-proxy |
| **Хранилище** | CSI-драйверы, GlusterFS, Ceph |
| **Безопасность** | Falco, Sysdig, аудит |
| **Утилиты** | Управление питанием, обновление ядра |

**Ключевое отличие от Deployment:** Deployment создаёт N Pod **где угодно**. DaemonSet создаёт **по одному Pod на каждом узле**. Если узел добавлен — DaemonSet создаст Pod на нём. Если узел удалён — Pod удалится.

### Манифест DaemonSet

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
  labels:
    app: node-exporter
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      hostNetwork: true
      hostPID: true
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.7.0
          ports:
            - containerPort: 9100
              hostPort: 9100
              name: metrics
          resources:
            requests:
              memory: "32Mi"
              cpu: "50m"
            limits:
              memory: "64Mi"
              cpu: "100m"
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `selector` | Как DaemonSet находит свои Pod |
| `template` | Шаблон Pod |
| `hostNetwork` | Использовать сеть узла (для сетевых демонов) |
| `hostPID` | Использовать PID namespace узла |
| `hostPort` | Порт на узле (для сетевых демонов) |
| `tolerations` | Для запуска на control-plane узлах |
| `nodeSelector` | Ограничить узлы |
| `affinity` | Более гибкие правила |
| `updateStrategy` | `RollingUpdate` (по умолчанию) или `OnDelete` |

### Как работает DaemonSet

1. **Watch узлов:** DaemonSet Controller следит за узлами кластера.
2. **Создание Pod:** Для каждого нового узла создаёт Pod.
3. **Scheduler:** DaemonSet использует scheduler для назначения Pod на узел (с v1.12). Но фактически Pod «привязан» к узлу.
4. **Удаление:** При удалении узла — Pod удаляется.

**Важно:** DaemonSet обходит некоторые ограничения scheduler. Он может запускать Pod на узлах, которые scheduler считает «неподходящими» (например, с taints), если у Pod есть соответствующие tolerations.

### DaemonSet и taints

Control-plane узлы обычно имеют taint:

```
node-role.kubernetes.io/control-plane:NoSchedule
```

Чтобы DaemonSet запускался и на них (например, для сбора логов), нужно добавить toleration:

```yaml
tolerations:
  - key: node-role.kubernetes.io/control-plane
    operator: Exists
    effect: NoSchedule
  - key: node-role.kubernetes.io/master      # для старых версий
    operator: Exists
    effect: NoSchedule
```

### Ограничение узлов через nodeSelector

```yaml
spec:
  template:
    spec:
      nodeSelector:
        node-type: worker
        disktype: ssd
```

Запустится только на узлах с этими метками.

### Обновление DaemonSet

```yaml
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1        # число или процент
    maxSurge: 0              # для DaemonSet обычно 0
```

- `RollingUpdate` — обновляет Pod по одному на каждом узле.
- `OnDelete` — Pod обновляются только при ручном удалении.

### Практика: DaemonSet

```bash
# Создать
kubectl apply -f daemonset.yaml

# Посмотреть
kubectl get daemonsets -n monitoring
kubectl get ds
kubectl describe ds node-exporter -n monitoring

# Pod на каждом узле
kubectl get pods -n monitoring -l app=node-exporter -o wide

# Проверить, что на каждом узле
kubectl get nodes
```

**Пример вывода:**

```
NAME                  READY   STATUS    NODE
node-exporter-abc12   1/1     Running   node-1
node-exporter-def34   1/1     Running   node-2
node-exporter-ghi56   1/1     Running   node-3
```

### Практический пример: Promtail для сбора логов

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: promtail
  namespace: logging
spec:
  selector:
    matchLabels:
      app: promtail
  template:
    metadata:
      labels:
        app: promtail
    spec:
      serviceAccountName: promtail
      containers:
        - name: promtail
          image: grafana/promtail:2.9.0
          args:
            - -config.file=/etc/promtail/config.yml
          volumeMounts:
            - name: config
              mountPath: /etc/promtail
            - name: varlog
              mountPath: /var/log
            - name: containers
              mountPath: /var/lib/docker/containers
              readOnly: true
      volumes:
        - name: config
          configMap:
            name: promtail-config
        - name: varlog
          hostPath:
            path: /var/log
        - name: containers
          hostPath:
            path: /var/lib/docker/containers
```

## Часть 2: Job

> **Job** — контроллер, который создаёт Pod и гарантирует, что они **успешно завершатся** (exit code 0). В отличие от Deployment, Pod в Job **не перезапускаются** бесконечно.

### Зачем нужен Job

| Задача | Пример |
|--------|--------|
| **Миграции БД** | Alembic, Flyway |
| **Одноразовые скрипты** | Импорт данных, экспорт отчёта |
| **Batch-обработка** | Обработка изображений, видео |
| **Тесты** | Integration tests в CI/CD |
| **Backup** | Резервное копирование |
| **Cleanup** | Очистка старых данных |

**Ключевое отличие от Deployment:**
- Deployment: Pod работает **постоянно**, перезапускается при падении.
- Job: Pod работает **до успешного завершения**, потом останавливается.

### Манифест Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  template:
    spec:
      containers:
        - name: migrate
          image: myapp:1.0
          command:
            - /bin/sh
            - -c
            - |
              echo "Running migrations..."
              python manage.py migrate
              echo "Done!"
      restartPolicy: OnFailure
  backoffLimit: 4
  completions: 1
  parallelism: 1
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `template` | Шаблон Pod |
| `restartPolicy` | **Обязательно** `OnFailure` или `Never` (не `Always`) |
| `backoffLimit` | Сколько раз перезапускать при падении (по умолчанию 6) |
| `completions` | Сколько Pod должны успешно завершиться (по умолчанию 1) |
| `parallelism` | Сколько Pod запускать параллельно (по умолчанию 1) |
| `activeDeadlineSeconds` | Максимальное время выполнения Job |
| `ttlSecondsAfterFinished` | Через сколько удалить Job после завершения |
| `completionMode` | `NonIndexed` (по умолчанию) или `Indexed` |

### restartPolicy для Job

| Значение | Поведение |
|----------|-----------|
| `OnFailure` | Контейнер перезапускается при падении, но Job не создаёт новый Pod |
| `Never` | При падении Pod Job создаёт новый Pod (с учётом `backoffLimit`) |

> [!important]
> `restartPolicy: Always` **нельзя** использовать в Job. Иначе Pod будет перезапускаться бесконечно, и Job никогда не завершится.

### Успешное завершение Job

Job считается завершённым, когда:
- Количество успешно завершённых Pod (exit code 0) >= `completions`.
- Все Pod завершились.

**Пример с `completions: 3`:**

Job создаст 3 Pod (последовательно или параллельно, зависит от `parallelism`). Когда все 3 успешно завершатся — Job готов.

### Параллелизм

```yaml
completions: 10
parallelism: 3
```

Job создаст 10 Pod, но одновременно будет работать не более 3. Как только один завершается — запускается следующий. Это полезно для batch-обработки больших данных.

### Индексированные Job (Indexed)

```yaml
completionMode: Indexed
completions: 10
parallelism: 3
```

Каждый Pod получает **индекс** от 0 до 9 через аннотацию:

```yaml
env:
  - name: JOB_COMPLETION_INDEX
    valueFrom:
      fieldRef:
        fieldPath: metadata.annotations['batch.kubernetes.io/job-completion-index']
```

**Использование:** обработка шардов данных. Pod с индексом 0 обрабатывает шард 0, и т.д.

### TTL для автоматической очистки

```yaml
spec:
  ttlSecondsAfterFinished: 3600   # удалить через час после завершения
```

Без TTL Job и его Pod остаются в кластере навсегда. Используйте TTL для очистки.

### Практика: Job

```bash
# Создать
kubectl apply -f job.yaml

# Посмотреть
kubectl get jobs
kubectl get pods
kubectl describe job db-migration

# Логи
kubectl logs job/db-migration

# Статус
kubectl get job db-migration -o jsonpath='{.status.succeeded}'

# Удалить
kubectl delete job db-migration
```

### Пример: Job с параллелизмом

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: parallel-job
spec:
  completions: 10
  parallelism: 3
  backoffLimit: 6
  ttlSecondsAfterFinished: 600
  template:
    spec:
      containers:
        - name: worker
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              echo "Processing item $JOB_COMPLETION_INDEX"
              sleep 5
              echo "Done with $JOB_COMPLETION_INDEX"
      restartPolicy: OnFailure
```

```bash
kubectl apply -f parallel-job.yaml
kubectl get pods -w
# Наблюдаем: 3 Pod одновременно, всего 10
```

Job можно создавать вручную или через CronJob. CronJob создаёт Job по расписанию.

## Часть 3: CronJob

> **CronJob** — контроллер, который создаёт Job по **расписанию** в формате cron.

### Формат расписания

```
┌───────────── минута (0-59)
│ ┌───────────── час (0-23)
│ │ ┌───────────── день месяца (1-31)
│ │ │ ┌───────────── месяц (1-12)
│ │ │ │ ┌───────────── день недели (0-6, 0 = воскресенье)
│ │ │ │ │
* * * * *
```

| Пример | Значение |
|--------|----------|
| `* * * * *` | Каждую минуту |
| `0 * * * *` | Каждый час |
| `0 0 * * *` | Каждый день в полночь |
| `0 3 * * *` | Каждый день в 3:00 |
| `0 3 * * 1` | Каждый понедельник в 3:00 |
| `*/5 * * * *` | Каждые 5 минут |
| `0 0 1 * *` | Первое число каждого месяца |
| `0 0 * * 0` | Каждое воскресенье в полночь |

### Манифест CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
spec:
  schedule: "0 3 * * *"          # каждый день в 3:00
  timeZone: "Europe/Moscow"      # опционально (с v1.27)
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  startingDeadlineSeconds: 300
  jobTemplate:
    spec:
      backoffLimit: 3
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          containers:
            - name: backup
              image: postgres:16
              command:
                - /bin/sh
                - -c
                - |
                  pg_dump -h postgres -U admin mydb > /backup/db-$(date +%Y%m%d).sql
                  echo "Backup done!"
              volumeMounts:
                - name: backup
                  mountPath: /backup
          restartPolicy: OnFailure
          volumes:
            - name: backup
              persistentVolumeClaim:
                claimName: backup-pvc
```

### Разбор spec

| Поле | Назначение |
|------|------------|
| `schedule` | Расписание в cron-формате |
| `timeZone` | Часовой пояс (с v1.27) |
| `concurrencyPolicy` | `Allow` (по умолчанию), `Forbid`, `Replace` |
| `successfulJobsHistoryLimit` | Сколько успешных Job хранить |
| `failedJobsHistoryLimit` | Сколько неудачных Job хранить |
| `startingDeadlineSeconds` | Дедлайн для запуска, если пропущен |
| `suspend` | Приостановить CronJob |
| `jobTemplate` | Шаблон Job |

### concurrencyPolicy

| Значение | Поведение |
|----------|-----------|
| `Allow` | Разрешить параллельные Job (по умолчанию) |
| `Forbid` | Запретить: если предыдущий Job ещё работает — пропустить |
| `Replace` | Заменить: удалить работающий Job и запустить новый |

> [!tip]
> Для бэкапов и миграций используйте `Forbid`, чтобы избежать параллельных запусков.

### История Job

```yaml
successfulJobsHistoryLimit: 3
failedJobsHistoryLimit: 1
```

CronJob хранит ссылки на завершённые Job. Без лимитов они накопятся и забьют etcd.

### Практика: CronJob

```bash
# Создать
kubectl apply -f cronjob.yaml

# Посмотреть
kubectl get cronjobs
kubectl get cj
kubectl describe cj db-backup

# Посмотреть Job, созданные CronJob
kubectl get jobs

# Посмотреть Pod
kubectl get pods

# Логи
kubectl logs job/db-backup-1234567890

# Вручную запустить Job из CronJob
kubectl create job --from=cronjob/db-backup manual-backup

# Приостановить
kubectl patch cronjob db-backup -p '{"spec":{"suspend":true}}'

# Возобновить
kubectl patch cronjob db-backup -p '{"spec":{"suspend":false}}'

# Удалить
kubectl delete cronjob db-backup
```

### Пример: CronJob для очистки

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: cleanup-logs
spec:
  schedule: "0 2 * * *"          # каждый день в 2:00
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      ttlSecondsAfterFinished: 3600
      template:
        spec:
          containers:
            - name: cleanup
              image: busybox:1.36
              command:
                - sh
                - -c
                - |
                  find /logs -name "*.log" -mtime +7 -delete
                  echo "Cleanup done"
              volumeMounts:
                - name: logs
                  mountPath: /logs
          restartPolicy: OnFailure
          volumes:
            - name: logs
              hostPath:
                path: /var/log/app
```

## Сравнение контроллеров

| Контроллер | Запускает Pod | Где | Когда | Завершение |
|------------|---------------|-----|-------|------------|
| **Deployment** | N копий | Где угодно | Постоянно | Никогда |
| **StatefulSet** | N копий | Где угодно | Постоянно | Никогда |
| **DaemonSet** | По 1 на узел | На каждом узле | Постоянно | Никогда |
| **Job** | N копий | Где угодно | Один раз | После успеха |
| **CronJob** | Job по расписанию | Где угодно | По расписанию | После успеха |

### Когда что использовать

| Задача | Контроллер |
|--------|------------|
| Веб-сервер, API | Deployment |
| База данных, очередь | StatefulSet |
| Сбор логов на каждом узле | DaemonSet |
| Миграция БД | Job |
| Резервное копирование по расписанию | CronJob |
| Batch-обработка | Job (с parallelism) |
| Одноразовый скрипт | Job |

## Продвинутые темы

### Init-контейнеры в Job

Job может использовать init-контейнеры для подготовки:

```yaml
spec:
  template:
    spec:
      initContainers:
        - name: wait-for-db
          image: busybox:1.36
          command:
            - sh
            - -c
            - until nc -z postgres 5432; do sleep 2; done
      containers:
        - name: migrate
          image: myapp:1.0
          command: ["python", "manage.py", "migrate"]
      restartPolicy: OnFailure
```

### Job с sidecar

Sidecar-контейнер может выполнять вспомогательные задачи (например, отправку логов). Но в Job sidecar должен уметь завершаться, иначе Job никогда не закончится.

### Indexed Job для шардирования

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: sharded-job
spec:
  completions: 10
  parallelism: 5
  completionMode: Indexed
  template:
    spec:
      containers:
        - name: worker
          image: myapp:1.0
          command:
            - sh
            - -c
            - |
              echo "Processing shard $JOB_COMPLETION_INDEX"
              process --shard=$JOB_COMPLETION_INDEX --total=10
      restartPolicy: OnFailure
```

### Pod failure policy (с v1.25)

```yaml
spec:
  podFailurePolicy:
    rules:
      - action: FailJob
        onExitCodes:
          operator: In
          values: [42]
      - action: Ignore
        onPodConditions:
          - type: DisruptionTarget
```

Позволяет гибко управлять поведением Job при разных типах сбоев.

### Suspend Job (с v1.21)

```yaml
spec:
  suspend: true
```

Job приостанавливается. Pod удаляются, но Job не считается завершённым. Можно возобновить:

```bash
kubectl patch job my-job -p '{"spec":{"suspend":false}}'
```

## Типичные ошибки

### Job с restartPolicy: Always

```
The Job "my-job" is invalid: spec.template.spec.restartPolicy: Unsupported value: "Always"
```

**Решение:** использовать `OnFailure` или `Never`.

### Job не завершается

**Причины:**
- Контейнер не завершается (бесконечный цикл).
- Sidecar не завершается.
- `backoffLimit` исчерпан, но Pod продолжает падать.

**Решение:**

```bash
kubectl describe job my-job
kubectl logs job/my-job
kubectl get pods
```

### CronJob пропускает запуски

**Причины:**
- `concurrencyPolicy: Forbid`, а предыдущий Job ещё работает.
- `startingDeadlineSeconds` слишком мал.
- CronJob был приостановлен (`suspend: true`).

**Решение:**

```bash
kubectl describe cronjob my-cronjob
kubectl get jobs
```

### DaemonSet не запускается на control-plane

**Причина:** taint на control-plane узлах.

**Решение:** добавить tolerations:

```yaml
tolerations:
  - key: node-role.kubernetes.io/control-plane
    operator: Exists
    effect: NoSchedule
```

### DaemonSet не запускается на всех узлах

**Причина:** nodeSelector или affinity ограничивают.

**Решение:**

```bash
kubectl describe ds my-daemonset
kubectl get nodes --show-labels
```

### 1. DaemonSet для node-exporter

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter

      hostNetwork: true

            - containerPort: 9100
```

### 2. Job для миграции БД

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  backoffLimit: 3
  ttlSecondsAfterFinished: 3600
  template:
    spec:
      initContainers:
        - name: wait-for-db
          image: busybox:1.36
          command:
            - sh
            - -c
            - until nc -z postgres 5432; do sleep 2; done
      containers:
        - name: migrate
          image: myapp:1.0
          command: ["python", "manage.py", "migrate"]
      restartPolicy: OnFailure
```

### 3. CronJob для бэкапа

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
spec:
  schedule: "0 3 * * *"
  timeZone: "Europe/Moscow"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 3
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          containers:
            - name: backup
              image: postgres:16
              command:
                - sh
                - -c
                - pg_dump -h postgres -U admin mydb > /backup/db-$(date +%Y%m%d).sql
              volumeMounts:
                - name: backup
                  mountPath: /backup
          restartPolicy: OnFailure
          volumes:
            - name: backup
              persistentVolumeClaim:
                claimName: backup-pvc
```

## Итог

1. **DaemonSet** — по одному Pod на каждом узле. Для сбора логов, метрик, сетевых плагинов.
2. **Job** — одноразовая задача до успешного завершения. Для миграций, batch-обработки.
3. **CronJob** — Job по расписанию. Для бэкапов, очистки, периодических задач.
4. **restartPolicy в Job** — только `OnFailure` или `Never`.
5. **concurrencyPolicy** — `Allow`, `Forbid`, `Replace`. Для бэкапов — `Forbid`.
6. **TTL** (`ttlSecondsAfterFinished`) — автоматическая очистка Job.
7. **Indexed Job** — для шардирования данных.
8. **DaemonSet и taints** — нужны tolerations для control-plane узлов.
9. **Не используйте Deployment** для одноразовых задач — используйте Job.

> [!tip]
> **Правило выбора контроллера:**
> - Постоянно, stateless → **Deployment**
> - Постоянно, stateful → **StatefulSet**
> - Постоянно, на каждом узле → **DaemonSet**
> - Один раз → **Job**
> - По расписанию → **CronJob**
