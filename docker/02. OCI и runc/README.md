# 02. OCI и runc

## О чём этот раздел

В предыдущем разделе мы разобрали механизмы ядра, на которых держится контейнеризация. Но как всё это собрать вместе? Как описать контейнер так, чтобы его можно было запустить одной командой? Ответ — **стандарты OCI** и **утилита runc**.

> **Ключевая мысль:** Docker не запускает контейнеры сам. Он готовит описание контейнера в формате OCI и передаёт управление `runc` — эталонной реализации стандарта.

Разберём три темы:

| Тема | Что даёт |
|------|----------|
| **Спецификации OCI** | Единый стандарт для всех инструментов контейнеризации |
| **config.json** | Описание контейнера в одном файле |
| **OCI Bundle и runc** | Минимальный набор файлов для запуска контейнера |

---

## 01. Спецификации OCI

### Что такое OCI

**OCI (Open Container Initiative)** — это организация, созданная в июне 2015 года для разработки открытых стандартов в сфере контейнеризации. В неё входят Docker, Google, Microsoft, Red Hat и другие крупные игроки.

До OCI каждый инструмент контейнеризации (Docker, rkt, LXC) имел свой формат образов и свой способ запуска контейнеров. Это создавало проблему: образ, собранный в Docker, нельзя было запустить в rkt, а контейнер, запущенный через LXC, не управлялся через Docker.

OCI решил эту проблему, введя **два основных стандарта**:

| Спецификация | Что описывает |
|--------------|---------------|
| **Runtime Specification** | Жизненный цикл контейнера: как он исполняется, в какой последовательности настраиваются все аспекты изоляции |
| **Image Specification** | Формат образов контейнеров: как они хранятся, распространяются и запускаются |

### Зачем это нужно

Благодаря OCI:

- **Совместимость** — образ, собранный в Docker, работает в Podman, containerd, Kubernetes и других инструментах.
- **Переносимость** — контейнер можно запустить на любой платформе, поддерживающей OCI.
- **Стандартизация** — все инструменты говорят на одном языке.

> **Аналогия:** OCI — это как PDF для документов. Неважно, в какой программе вы создали документ, — если он сохранён в PDF, его откроет любая программа.

### Runtime Specification

Runtime Specification описывает:

- **Жизненный цикл контейнера** — от создания до удаления
- **Конфигурацию** — как описывается контейнер (в файле `config.json`)
- **Операции** — какие команды должен поддерживать runtime (create, start, kill, delete)
- **Изоляцию** — какие механизмы ядра используются (namespaces, cgroups, capabilities)

### Image Specification

Image Specification описывает:

- **Формат образа** — как хранятся слои, метаданные, конфигурация
- **Манифест** — описание образа (какие слои входят, какие теги)
- **Слои** — как упаковываются изменения файловой системы
- **Реестры** — как образы распространяются (Docker Hub, GitHub Container Registry)

### Эталонная реализация — runc

**runc** — это эталонная реализация OCI Runtime Specification, написанная на языке Go. Именно её Docker использует под капотом.

```
Docker CLI → dockerd → containerd → runc → контейнер
```

**Что делает runc:**

1. Читает `config.json` — описание контейнера
2. Настраивает namespaces, cgroups, capabilities
3. Монтирует OverlayFS
4. Запускает процесс в изолированном окружении

**Что не делает runc:**

- Не собирает образы
- Не управляет реестрами
- Не предоставляет API для оркестрации

runc — это низкоуровневый инструмент. Он делает одну вещь и делает её хорошо: запускает контейнер по описанию.

### Другие реализации OCI

| Реализация | Особенности |
|------------|-------------|
| **runc** | Эталонная, используется в Docker |
| **crun** | Написана на C, быстрее и легче runc |
| **youki** | Написана на Rust, фокус на безопасности |
| **Kata Containers** | Запускает контейнеры в лёгких ВМ для изоляции |

> **Важно:** все они совместимы с OCI. Контейнер, описанный в `config.json`, запустится в любой из них.

## 02. config.json — описание контейнера

### Что это

**config.json** — это файл, который описывает все аспекты контейнера: какие namespaces использовать, какие cgroups настроить, какой rootfs смонтировать, какую команду запустить.

Это **стандартизированное описание** всех механизмов изоляции, которые нужно применить к процессу.

### Структура файла

Файл состоит из нескольких основных секций:

| Секция | Что описывает |
|--------|---------------|
| `ociVersion` | Версия спецификации OCI |
| `process` | Команда, пользователь, переменные окружения |
| `root` | Путь к rootfs контейнера |
| `mounts` | Точки монтирования |
| `linux` | Namespaces, cgroups, capabilities, устройства |
| `hostname` | Имя хоста контейнера |

### Пример: минимальный config.json

```json
{
  "ociVersion": "1.2.0",
  "process": {
    "terminal": true,
    "user": {
      "uid": 0,
      "gid": 0
    },
    "args": [
      "sh"
    ],
    "env": [
      "PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin",
      "TERM=xterm"
    ]
  },
  "root": {
    "path": "rootfs",
    "readonly": true
  }
}
```

**Что здесь описано:**

- `ociVersion` — версия спецификации
- `process.args` — команда, которая запустится в контейнере (по умолчанию `sh`)
- `process.env` — переменные окружения
- `root.path` — путь к rootfs контейнера (по умолчанию `rootfs`)

### Секция linux: namespaces

```json
{
  "linux": {
    "namespaces": [
      { "type": "pid" },
      { "type": "network" },
      { "type": "ipc" },
      { "type": "uts" },
      { "type": "mount" },
      { "type": "cgroup" }
    ]
  }
}
```

**Что здесь описано:** в каких namespace'ах запустится процесс. Если namespace не указан — процесс попадёт в дефолтный namespace хоста.

### Секция linux: resources (cgroups)

```json
{
  "linux": {
    "resources": {
      "memory": {
        "limit": 536870912,
        "swap": 536870912
      },
      "cpu": {
        "shares": 512,
        "quota": 50000,
        "period": 100000
      },
      "pids": {
        "limit": 100
      }
    }
  }
}
```

**Что здесь описано:**

- `memory.limit` — лимит памяти в байтах (512 МБ)
- `memory.swap` — лимит swap
- `cpu.shares` — вес CPU
- `pids.limit` — максимальное количество процессов

### Секция linux: capabilities

```json
{
  "linux": {
    "capabilities": {
      "bounding": ["CAP_NET_BIND_SERVICE"],
      "effective": ["CAP_NET_BIND_SERVICE"],
      "inheritable": ["CAP_NET_BIND_SERVICE"],
      "permitted": ["CAP_NET_BIND_SERVICE"]
    }
  }
}
```

**Что здесь описано:** какие capabilities доступны контейнеру. В примере — только `CAP_NET_BIND_SERVICE` (привязка к портам < 1024).

### Как это связано с Docker

Docker не хранит `config.json` постоянно. Он **формирует его на лету** при запуске контейнера, комбинируя:

1. **Конфигурацию образа** — что описано в Dockerfile (команда, переменные, порты)
2. **Пользовательские настройки** — флаги при `docker run` (`--memory`, `--cpus`, `--cap-drop`)

Готовый `config.json` хранится во временной директории:

```
/run/containerd/io.containerd.runtime.v2.task/moby/<container-id>/config.json
```

При остановке контейнера этот файл удаляется. При следующем запуске — собирается заново.

### Почему это важно понимать

Понимание `config.json` даёт:

- **Прозрачность** — вы знаете, что именно настраивается при запуске контейнера
- **Отладку** — если контейнер ведёт себя странно, можно посмотреть его `config.json`
- **Гибкость** — можно запускать контейнеры без Docker, напрямую через `runc`

## 03. OCI Bundle и runc

### Что такое OCI Bundle

**OCI Bundle** — это минимальный набор файлов, необходимый для запуска контейнера через `runc`:

| Компонент | Что это |
|-----------|---------|
| **config.json** | Описание контейнера |
| **rootfs/** | Корневая файловая система контейнера |

Всё. Больше ничего не нужно. `runc` читает `config.json`, находит `rootfs` и запускает контейнер.

### Как создать Bundle

**Шаг 1: Создать директорию для Bundle**

```bash
mkdir mycontainer
cd mycontainer
```

**Шаг 2: Сгенерировать config.json**

```bash
runc spec
```

**Что происходит:** `runc` создаёт шаблонный `config.json` с базовыми настройками. В нём уже описаны namespaces, базовая команда (`sh`), переменные окружения.

**Шаг 3: Подготовить rootfs**

Нужно скачать **minirootfs** — минимальное дерево каталогов какого-либо дистрибутива. Например, Alpine Linux:

```bash
mkdir alpine
wget https://dl-cdn.alpinelinux.org/alpine/v3.20/releases/x86_64/alpine-minirootfs-3.20.0-x86_64.tar.gz
tar -xzf alpine-minirootfs-3.20.0-x86_64.tar.gz -C alpine/
```

**Что происходит:** в директории `alpine` появляется стандартное дерево каталогов Alpine Linux: `bin`, `dev`, `etc`, `home`, `lib`, `proc`, `root`, `sys`, `tmp`, `usr`, `var`.

**Шаг 4: Исправить config.json**

По умолчанию `runc` ищет rootfs в директории `rootfs`. У нас она называется `alpine`. Нужно поменять в `config.json`:

```json
{
  "root": {
    "path": "alpine",
    "readonly": true
  }
}
```

**Что происходит:** теперь `runc` знает, где искать rootfs.

### Как запустить контейнер

```bash
sudo runc run mycontainer
```

**Что происходит:**

1. `runc` читает `config.json`
2. Настраивает namespaces (PID, network, UTS, mount, IPC, cgroup)
3. Настраивает cgroups (если указаны лимиты)
4. Монтирует rootfs
5. Запускает процесс `sh` в изолированном окружении

**Что вы увидите:** вы попадёте внутрь контейнера. Процесс `sh` будет считать себя PID 1, иметь своё имя хоста и только loopback-интерфейс.

### Управление контейнером через runc

| Команда | Что делает |
|---------|------------|
| `runc run <id>` | Создать и сразу запустить контейнер |
| `runc create <id>` | Создать контейнер, но не запускать |
| `runc start <id>` | Запустить созданный контейнер |
| `runc list` | Список запущенных контейнеров |
| `runc state <id>` | Состояние контейнера |
| `runc kill <id>` | Убить контейнер |
| `runc delete <id>` | Удалить контейнер |

### Что даёт понимание OCI Bundle

- **Прозрачность** — вы знаете, из чего состоит контейнер
- **Минимализм** — для запуска контейнера нужны всего два компонента
- **Независимость** — можно запускать контейнеры без Docker
- **Понимание Docker** — Docker делает то же самое, но автоматизирует процесс

### Как это связано с Docker

Docker использует `runc` под капотом. Когда вы запускаете `docker run`:

1. Docker CLI отправляет команду демону `dockerd`
2. `dockerd` формирует OCI Bundle (config.json + rootfs из образа)
3. `dockerd` передаёт Bundle в `containerd`
4. `containerd` вызывает `runc` с этим Bundle
5. `runc` запускает контейнер

> **Ключевая мысль:** Docker — это удобная обёртка вокруг `runc`. Вся тяжёлая работа по изоляции выполняется `runc` и ядром Linux.

## Итог раздела

Мы разобрали, как стандарты OCI и утилита `runc` позволяют запускать контейнеры:

| Тема | Что даёт |
|------|----------|
| **OCI** | Единый стандарт для всех инструментов контейнеризации |
| **Runtime Specification** | Описание жизненного цикла контейнера |
| **Image Specification** | Описание формата образов |
| **config.json** | Описание контейнера в одном файле |
| **OCI Bundle** | Минимальный набор файлов для запуска контейнера |
| **runc** | Эталонная реализация OCI |

> **Главный вывод:** контейнер — это не что-то инопланетное. Это процесс, описанный в `config.json` и запущенный через `runc`. Docker просто автоматизирует создание Bundle и управление контейнерами.
