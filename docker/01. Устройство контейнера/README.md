# 01. Устройство контейнера

## О чём этот раздел

Здесь разбирается **фундамент** контейнеризации — механизмы ядра Linux, на которых держится Docker. Без понимания этих пяти технологий Docker остаётся чёрным ящиком: команды работают, но непонятно почему, а при первой нестандартной ситуации всё ломается.

> **Ключевая мысль:** контейнер — это обычный процесс. Всё, что делает Docker — настраивает для него изоляцию через механизмы ядра и запускает.

Разберём пять механизмов:

| Механизм | Что изолирует |
|----------|---------------|
| **chroot** | Файловую систему |
| **Namespaces** | Ресурсы ядра (PID, сеть, UTS, mount, IPC) |
| **Cgroups v2** | Физические ресурсы (CPU, память, I/O) |
| **OverlayFS** | Слоёную файловую систему образа |
| **Capabilities** | Привилегии root |

---

## 01. chroot — первый шаг к изоляции

### Что это

`chroot` меняет корень дерева каталогов для процесса. Процесс начинает «думать», что его корень — это, например, `/hello-docker`, и не может выйти выше.

### Структура команды

```
chroot [ОПЦИИ] НОВЫЙ_КОРЕНЬ [КОМАНДА [АРГУМЕНТЫ]...]
```

Сначала указывается новый корень, затем программа, которая должна запуститься, думая, что её корень дерева каталогов находится в указанной директории.

### Пример: запускаем bash в новом корне

Создаём директорию и пытаемся запустить `bash`, который будет думать, что его корень — это `/hello-docker`:

```bash
mkdir /hello-docker
chroot /hello-docker bash
```

**Что происходит:** команда завершается ошибкой — `failed to run command 'bash': No such file or directory`.

**Почему:** когда мы запускаем программу через терминал, указывая её название, командная оболочка ищет исполняемый файл с указанным названием в стандартных каталогах (пути к ним лежат в переменной окружения `$PATH`). Ищет она их **от корня**. Так как в новом корне `/hello-docker` нет ничего, то и исполняемый файл `bash` не находится.

### Пример: копируем bash и его зависимости

Добавляем `bash` и `ls` в новый корень:

```bash
mkdir /hello-docker/bin
cp /bin/bash /bin/ls /hello-docker/bin/
```

**Что происходит:** снова ошибка — `failed to run command 'bash': No such file or directory`.

**Почему:** исполняемые файлы `bash` и `ls` полагаются на динамические библиотеки, которых нет в новом окружении.

### Пример: смотрим зависимости

Используем утилиту `ldd`, чтобы посмотреть, от каких библиотек зависят наши исполняемые файлы:

```bash
ldd /bin/bash
ldd /bin/ls
```

**Что происходит:** утилита выводит список `.so`-файлов, которые нужны для работы программы.

**Что делаем:** копируем эти библиотеки по стандартным путям в новый корень `/hello-docker`. Например:

```bash
mkdir -p /hello-docker/lib/x86_64-linux-gnu
cp /lib/x86_64-linux-gnu/libtinfo.so.6 /hello-docker/lib/x86_64-linux-gnu/
cp /lib/x86_64-linux-gnu/libc.so.6 /hello-docker/lib/x86_64-linux-gnu/
cp /lib64/ld-linux-x86-64.so.2 /hello-docker/lib64/
```

Теперь пробуем запустить снова:

```bash
chroot /hello-docker bash
```

**Что происходит:** всё работает. Процесс `bash` изолирован в контексте файловой системы и принимает за корень тот каталог, что в хостовой системе корнем не является.

### Что даёт chroot

- Изоляция файловой системы
- Процесс не может выйти за пределы указанного корня
- Основа для контейнеризации

### Чего не даёт

- Не изолирует процессы (видны все процессы системы)
- Не изолирует сеть (общие сетевые интерфейсы)
- Не ограничивает ресурсы (CPU, память)
- Не защищает от побега (root может выйти через `/proc/1/root`)

> **Вывод:** chroot — необходимый, но недостаточный механизм. Для полноценной изоляции нужны namespaces и cgroups.

## 02. Namespaces — основа изоляции

### Что это

**Namespace** — это «прослойка» между процессом и ресурсом ядра. Каждый процесс по умолчанию находится в дефолтных namespace'ах, но может быть запущен в новых.

Простыми словами: пространства имён — это точки доступа процесса к ресурсам операционной системы. Процесс может менять их в ходе исполнения или запускаться сразу в новых.

### Типы namespace'ов

| Namespace | Что изолирует | Эффект |
|-----------|---------------|--------|
| **PID** | Дерево процессов | Процесс видит только свои процессы, считает себя PID 1 |
| **Network** | Сетевые интерфейсы | Свой loopback, свои порты, свои маршруты |
| **UTS** | hostname/domainname | Своё имя хоста |
| **Mount** | Точки монтирования | Своя файловая система |
| **IPC** | Очереди сообщений, семафоры | Своё межпроцессное взаимодействие |
| **User** | UID/GID | Можно быть «root» внутри, не будучи root снаружи |
| **Cgroup** | Контрольные группы | Своя иерархия cgroups |

### Как посмотреть namespace'ы процесса

В каталоге `/proc/<PID>/ns/` находятся символические ссылки на namespace'ы процесса. Смотрим namespace'ы текущего процесса:

```bash
ls -l /proc/$$/ns/
```

**Что происходит:** вывод показывает символические ссылки вида:

```
lrwxrwxrwx ... cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx ... ipc -> 'ipc:[4026531839]'
lrwxrwxrwx ... mnt -> 'mnt:[4026531840]'
lrwxrwxrwx ... net -> 'net:[4026531992]'
lrwxrwxrwx ... pid -> 'pid:[4026531836]'
lrwxrwxrwx ... user -> 'user:[4026531837]'
lrwxrwxrwx ... uts -> 'uts:[4026531838]'
```

Числа в скобках — ID namespace'ов. Если у двух процессов они одинаковые — они в одном namespace.

### Пример: UTS namespace

Смотрим hostname в двух терминалах — он одинаковый, потому что оба процесса находятся в одном UTS namespace:

```bash
hostname
```

Запускаем новый UTS namespace и меняем hostname только внутри него:

```bash
sudo unshare --uts --fork bash
hostname new-name
hostname
```

**Что происходит:** внутри нового namespace hostname изменился на `new-name`. Второй терминал не затронут — там осталось старое имя. Изменение видно только внутри нового namespace.

### Пример: PID namespace

Запускаем новый PID namespace:

```bash
sudo unshare --pid --fork --mount-proc bash
```

**Что происходит:** процесс видит только те процессы, которые он сам породил. Он считает себя процессом `init` с PID равным 1. Дерево процессов хостовой системы ему не видно.

Проверяем:

```bash
ps aux
```

**Что происходит:** вывод показывает только процессы внутри нового namespace, а не все процессы системы.

### Namespace'ы в контейнере

Docker запускает процесс в новых namespace'ах по умолчанию. Посмотреть namespace'ы запущенного контейнера можно так:

```bash
docker run -d --name test nginx
docker inspect test | grep -A 20 '"Namespaces"'
```

**Что происходит:** вывод показывает, в каких namespace'ах работает контейнер. Это означает, что:

- Контейнер видит только свои процессы
- Контейнер имеет свой сетевой стек
- Контейнер имеет своё имя хоста
- Контейнер имеет свою файловую систему

### Ключевые моменты

1. **Namespace'ы наследуются** — дочерний процесс попадает в те же namespace'ы, что и родитель, если не указано иное.
2. **Изоляция не полная** — процессы в разных PID namespace'ах всё ещё делят ядро.
3. **User namespace** позволяет запускать контейнеры без root (rootless Docker).

## 03. Cgroups v2 — изоляция физических ресурсов

### Что это

**Cgroups** (control groups) позволяют ограничивать потребление физических ресурсов группой процессов.

Если с помощью Namespaces можно изолировать процесс относительно логических ресурсов, то Cgroups позволяют делать то же самое относительно физических ресурсов системы.

### Интерфейс

Всё управление — через файловую систему `/sys/fs/cgroup` (cgroupfs). Это не обычные файлы на диске, а интерфейс к внутренним структурам ядра.

Создание группы = создание папки. Настройка = запись в файл. Файлы создаются автоматически ядром при создании контрольной группы.

### Смотрим корневую группу

```bash
ls /sys/fs/cgroup/
```

**Что происходит:** вывод показывает файлы корневой контрольной группы:

```
cgroup.controllers  cgroup.procs  cgroup.subtree_control  ...
```

Файл `cgroup.controllers` содержит список всех возможных для ограничения ресурсов:

```bash
cat /sys/fs/cgroup/cgroup.controllers
```

**Что происходит:** вывод показывает список контроллеров, например:

```
cpuset cpu io memory hugetlb pids rdma misc
```

Файл `cgroup.procs` содержит процессы, находящиеся в группе:

```bash
cat /sys/fs/cgroup/cgroup.procs
```

**Что происходит:** вывод показывает список PID'ов процессов в корневой группе.

### Пример: создаём свою группу

Создаём папку в `/sys/fs/cgroup` — ядро автоматически создаёт файлы для настройки:

```bash
cd /sys/fs/cgroup
sudo mkdir my-new-group
cd my-new-group
ls
```

**Что происходит:** вывод показывает файлы, созданные автоматически:

```
cgroup.controllers  cgroup.procs  memory.max  memory.swap.max  pids.max ...
```

Устанавливаем лимит памяти 512 МБ:

```bash
echo "512M" | sudo tee memory.max
```

Запрещаем выгрузку в swap:

```bash
echo 0 | sudo tee memory.swap.max
```

Добавляем свой терминал в группу:

```bash
echo $$ | sudo tee cgroup.procs
```

**Что происходит:** теперь всё, что запущено из этого терминала, автоматически попадает в группу (контрольные группы наследуются дочерними процессами).

### Пример: превышаем лимит

Запускаем программу, которая бесконечно выделяет память:

```python
import time

buffer = []
while True:
    buffer.append(" " * 100 * 1024 * 1024)
    print(f"Allocated {len(buffer) * 100} MB")
    time.sleep(0.5)
```

```bash
python3 memory_hog.py
```

**Что происходит:** на 6-й итерации (600 МБ) процесс будет убит **OOM Killer**. Без ограничения swap процесс мог бы выгружать страницы памяти на диск и не превысить лимит. Поэтому важно устанавливать `memory.swap.max = 0`.

Смотрим логи ядра:

```bash
dmesg | grep -i "killed process"
```

**Что происходит:** вывод показывает, что за процессом пришёл OOM Killer:

```
Out of memory: Kill process 12345 (python) score 987
Killed process 12345 (python) total-vm:...
```

Также в логах видно название контрольной группы `my-new-group`.

### Что можно ограничивать

| Ресурс | Файл в cgroup v2 |
|--------|------------------|
| CPU | `cpu.max`, `cpu.weight` |
| Память | `memory.max`, `memory.swap.max` |
| Количество PID | `pids.max` |
| Дисковый I/O | `io.max` |
| Сетевой I/O | (через BPF) |

### Cgroups в Docker

Docker использует cgroups для ограничения ресурсов контейнера:

```bash
# Лимит памяти 512 МБ
docker run -d --memory 512m nginx

# Лимит CPU — 1.5 ядра
docker run -d --cpus 1.5 nginx

# Лимит PID — 100
docker run -d --pids-limit 100 nginx
```

**Что происходит:** флаги при запуске контейнера транслируются в настройки cgroups.

### Ключевые моменты

1. **Cgroups v2** — единая иерархия, используется в современных дистрибутивах.
2. **Ограничения применяются к группе**, а не к отдельному процессу.
3. **OOM Killer** убивает процесс при превышении лимита памяти.
4. **Swap можно отключить** для группы (`memory.swap.max = 0`).

## 04. OverlayFS — «слоёный пирог» Docker

### Что это

**OverlayFS** позволяет накладывать одно дерево каталогов (верхний слой) поверх другого (нижний слой). Нижний слой — только для чтения, верхний — для записи.

### Структура

Для работы OverlayFS нужно создать 4 директории:

| Директория | Роль |
|------------|------|
| `lower` | Базовая ФС (только чтение) — например, rootfs Ubuntu |
| `diff` | Верхний слой (запись) — изменения контейнера |
| `merged` | Объединённый вид: `lower` + `diff` |
| `work` | Рабочая директория OverlayFS (служебная) |

### Пример: монтируем overlay

Создаём слои и кладём что-то в `lower`:

```bash
mkdir -p lower diff merged work
echo "base" > lower/file.txt
```

Монтируем overlay:

```bash
sudo mount -t overlay overlay \
  -o lowerdir=lower,upperdir=diff,workdir=work \
  merged
```

**Что происходит:** монтирование OverlayFS указывает, какие директории за что отвечают. После монтирования `merged` является объединением `lower` и `diff`.

Смотрим `merged` — видим `file.txt` из `lower`:

```bash
ls merged/
```

**Что происходит:** вывод показывает `file.txt`.

Создаём файл в `merged`:

```bash
echo "new" > merged/newfile.txt
ls diff/
```

**Что происходит:** файл `newfile.txt` появился в `diff`. Изменения, сделанные в `merged`, попадают в `diff`. `lower` остаётся неизменным.

Удаляем файл из `lower` через `merged`:

```bash
rm merged/file.txt
ls diff/
```

**Что происходит:** в `diff` появилась специальная запись (whiteout), помечающая файл как удалённый. Сам файл в `lower` остался.

### Как это работает в Docker

1. **Базовый слой** — rootfs образа (например, `ubuntu:22.04`), общий для всех контейнеров на его основе.
2. **Верхний слой** — `diff` конкретного контейнера.
3. **При запуске** контейнера Docker монтирует OverlayFS и передаёт `merged` в `runc` как корень.

В контейнерах за базовое дерево каталогов обычно берут не случайную папку, а стандартное дерево каталогов Ubuntu, Debian или Alpine Linux. Такие деревья называются **minirootfs**.

На базовый слой (например, Alpine Linux) можно наложить слой с Python. В папке `diff` появится `/usr/bin/python`, а базовое дерево каталогов Alpine Linux не изменится. Всё это и называется «слоёным пирогом»: контейнеры хранят лишь изменения поверх базового дерева каталогов для экономии ресурсов, а при запуске через OverlayFS создаётся `merged`, воссоздавая дерево каталогов запущенного контейнера.

### Где это лежит

```
/var/lib/docker/overlay2/<layer-id>/diff/    # изменения контейнера
/var/lib/docker/overlay2/<layer-id>/lower/   # ссылки на нижние слои
/var/lib/docker/overlay2/<layer-id>/merged/  # точка монтирования (при запуске)
/var/lib/docker/overlay2/<layer-id>/work/    # рабочая директория
```

В файле `link` хранится уникальный идентификатор слоя. В файле `lower` — идентификаторы нижележащих слоёв через `:`.

### Пример: находим файлы контейнера на хосте

Запускаем контейнер, создаём внутри файл и выходим:

```bash
docker run -it --name test ubuntu bash
echo "hello" > /filetofind.txt
exit
```

Ищем файл на хосте:

```bash
sudo find /var/lib/docker/overlay2 -name "filetofind.txt"
```

**Что происходит:** файл находится в директории `/var/lib/docker/overlay2/<id>/diff/`. Это и есть верхний слой контейнера — все изменения, сделанные внутри.

### Ключевые моменты

1. **Слои неизменяемы** — базовый слой не меняется, изменения пишутся в diff.
2. **Экономия места** — базовый слой общий для всех контейнеров на его основе.
3. **При остановке контейнера** `merged` исчезает, остаются только `diff` и ссылки на `lower`.
4. **При запуске** `merged` собирается заново.

## 05. Capabilities — тонкая настройка привилегий

### Что это

**Capabilities** — это разбиение прав root на отдельные привилегии. Вместо «всё или ничего» (root или обычный пользователь) — набор отдельных разрешений.

Права обычного пользователя очень ограничены, в то время как права пользователя root очень обширны. Хотя процессам, запущенным под root, часто не требуются все полномочия root. Для уменьшения полномочий пользователя root были придуманы capabilities.

### Примеры capabilities

| Capability | Что разрешает |
|------------|---------------|
| `CAP_NET_BIND_SERVICE` | Привязка к портам < 1024 |
| `CAP_NET_ADMIN` | Управление сетью |
| `CAP_SYS_ADMIN` | Широкий спектр административных операций |
| `CAP_SYS_TIME` | Изменение системного времени |
| `CAP_CHOWN` | Изменение владельца файлов |
| `CAP_KILL` | Отправка сигналов другим процессам |

### Зачем это в контейнерах

По умолчанию Docker даёт контейнеру **ограниченный набор capabilities**. Это защищает хост: даже если злоумышленник получит root внутри контейнера, он не сможет выполнить опасные операции на хосте.

Capabilities очень часто используются для более тонкой настройки контейнера и указываются в `config.json` в соответствии со спецификацией OCI.

### Пример: смотрим capabilities

Смотрим capabilities текущего процесса:

```bash
capsh --print
```

**Что происходит:** вывод показывает список capabilities, доступных процессу.

Смотрим capabilities в контейнере:

```bash
docker run --rm alpine sh -c "apk add --no-cache libcap && capsh --print"
```

**Что происходит:** вывод показывает, что контейнер имеет ограниченный набор capabilities по сравнению с хостом.

### Пример: ограничиваем capabilities

Запускаем контейнер без всех capabilities:

```bash
docker run --rm --cap-drop=ALL alpine sh -c "capsh --print"
```

**Что происходит:** вывод показывает, что у контейнера нет capabilities.

Добавляем только нужную:

```bash
docker run --rm --cap-drop=ALL --cap-add=NET_BIND_SERVICE alpine sh -c "capsh --print"
```

**Что происходит:** вывод показывает, что у контейнера есть только `CAP_NET_BIND_SERVICE`.

### Capabilities в Docker

```bash
# Убрать все
docker run --cap-drop=ALL nginx

# Добавить конкретную
docker run --cap-add=NET_ADMIN nginx
```

> **Правило:** давайте контейнеру только те capabilities, которые ему действительно нужны. В идеале — `--cap-drop=ALL` и добавление необходимых.

## Итог раздела

Мы разобрали пять механизмов, на которых держится контейнеризация:

| Механизм | Что делает | Аналог в Docker |
|----------|------------|-----------------|
| **chroot** | Изоляция файловой системы | `rootfs` контейнера |
| **Namespaces** | Изоляция ресурсов ядра | `--pid`, `--network`, `--uts` |
| **Cgroups v2** | Ограничение ресурсов | `--memory`, `--cpus`, `--pids-limit` |
| **OverlayFS** | Слоёная ФС | Слои образа, `diff` |
| **Capabilities** | Привилегии | `--cap-drop`, `--cap-add` |

> **Главный вывод:** контейнер — это не «маленькая виртуалка». Это обычный процесс, для которого ядро настроило изоляцию через эти пять механизмов. Docker просто автоматизирует эту настройку.
