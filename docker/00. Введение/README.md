# 00. Введение в Docker

## О чём этот раздел

Этот раздел открывает знакомство с миром контейнеризации и Docker. Здесь закладывается понимание того, **зачем** вообще нужны контейнеры, **чем** они отличаются от виртуальных машин и **почему** Docker стал де-факто стандартом в современной инфраструктуре. Без этого фундамента все последующие команды и конфигурации превращаются в набор заклинаний, которые ломаются при первой нестандартной ситуации.

## Проблема, которую решает Docker

Представьте классическую ситуацию: приложение работает на ноутбуке разработчика, но падает на сервере. Причина — разное окружение: версии библиотек, зависимости, переменные, конфигурации. Классический ответ: «У меня работает».

Docker решает эту проблему, упаковывая приложение **вместе со всем его окружением** в единый образ. Этот образ одинаково запускается где угодно: на ноутбуке, на тестовом стенде, в продакшене, в облаке.

> **Контейнер** — это стандартизированная единица программного обеспечения, которая объединяет код и все его зависимости, обеспечивая быстрое и надёжное выполнение в любом окружении.

## Откуда взялись контейнеры

Идея изоляции процессов не нова. Путь к Docker выглядел так:

| Год | Технология | Вклад |
|-----|------------|-------|
| 1979 | **chroot** | Изоляция файловой системы процесса |
| 2002 | **Namespaces** | Изоляция ресурсов ядра (PID, сеть, mount) |
| 2007 | **Cgroups** | Ограничение физических ресурсов (CPU, память) |
| 2008 | **LXC** | Первые полноценные контейнеры на базе ядра Linux |
| 2013 | **Docker** | Удобный инструмент + экосистема + стандарт |
| 2015 | **OCI** | Открытые стандарты контейнеризации |
| 2017 | **containerd / runc** | Разделение Docker на компоненты |

> **Важно:** Docker не изобрёл контейнеры. Он сделал их **удобными** и **доступными**. Вся тяжёлая работа выполняется ядром Linux через механизмы, которые мы разберём в следующем разделе.

## Контейнер vs виртуальная машина

Это самое частое сравнение, и его нужно понять с самого начала.

| Характеристика | Контейнер | Виртуальная машина |
|----------------|-----------|---------------------|
| **Ядро** | Общее с хостом | Своё собственное |
| **Изоляция** | Namespaces + Cgroups | Гипервизор + аппаратная виртуализация |
| **Запуск** | Секунды | Минуты |
| **Размер** | Мегабайты | Гигабайты |
| **Плотность** | Сотни на хост | Десятки на хост |
| **Безопасность** | Ниже (общее ядро) | Выше (полная изоляция) |
| **Совместимость ОС** | Только Linux-ядро | Любая ОС |

### Аналогия

- **Виртуальная машина** — это отдельная квартира со своей кухней, санузлом и коммуникациями. Полная изоляция, но дорого и долго.
- **Контейнер** — это комната в общежитии с общей кухней и санузлом. Быстро, дёшево, но соседи могут повлиять.

> **Правило выбора:** контейнеры — для микросервисов, CI/CD, быстрого масштабирования. ВМ — для полной изоляции, разных ОС, критичных к безопасности нагрузок.

## Где Docker применяется

| Сценарий | Что даёт Docker |
|----------|-----------------|
| **Микросервисы** | Каждый сервис в своём контейнере, независимое развёртывание |
| **CI/CD** | Одинаковое окружение для сборки, тестов и деплоя |
| **Локальная разработка** | Быстрый подъём БД, Redis, очередей одной командой |
| **Изоляция приложений** | Разные версии Python/Node/Java на одном хосте |
| **Облачные среды** | Стандарт для Kubernetes, ECS, Cloud Run |
| **Воспроизводимость** | «У меня работает» → «работает везде» |

## Философия Docker

**Контейнер — это процесс, а не «маленькая виртуалка»**  
Docker не эмулирует железо. Он запускает обычный процесс в изолированном окружении. Всё, что делает Docker — настраивает механизмы ядра и запускает процесс.

**Один контейнер — одна задача**  
Вместо монолита из десяти сервисов — десять контейнеров, каждый со своей ролью. Это упрощает масштабирование, обновление и отладку.

**Образы неизменяемы (immutable)**  
Собранный образ не меняется. Если нужно обновление — собирается новый образ. Это обеспечивает воспроизводимость и предсказуемость.

**Слоёная файловая система**  
Образы состоят из слоёв. Базовый слой общий для всех контейнеров на его основе, изменения пишутся в отдельный слой. Это экономит место и ускоряет сборку.

**Стандартизация через OCI**  
Docker следует открытым спецификациям OCI. Это значит, что образы работают не только в Docker, но и в Podman, containerd, Kubernetes.

**Инфраструктура как код**  
`Dockerfile` и `docker-compose.yml` — это текстовые файлы, которые можно версионировать, ревьюить и автоматизировать.
