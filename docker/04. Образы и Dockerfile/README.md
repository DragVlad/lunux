# 04. Образы и Dockerfile

## О чём этот раздел

Мы разобрали, как устроен контейнер изнутри, как работают OCI и runc, как установить Docker и работать с основными командами. Теперь переходим к тому, **что именно запускается** — к образам. Образ — это фундамент контейнера: без него нечего запускать. А Dockerfile — это способ описать, как этот образ собрать.

| Тема | Что даёт |
|------|----------|
| **Образ** | Понимание, из чего состоит контейнер |
| **Слои** | Как Docker экономит место и ускоряет сборку |
| **Dockerfile** | Как описать сборку образа |
| **Multi-stage build** | Как собирать маленькие и безопасные образы |
| **Кэширование** | Как ускорить сборку |

> **Ключевая мысль:** образ — это неизменяемый шаблон, состоящий из слоёв. Контейнер — это запущенный экземпляр образа с добавленным слоем для записи.

---

## 01. Что такое образ

### Определение

**Образ (image)** — это неизменяемый (immutable) шаблон, из которого создаются контейнеры. Он содержит:

- Корневую файловую систему (rootfs) — файлы, библиотеки, бинарники
- Метаданные — команда запуска, переменные окружения, порты, тома
- Слои — изменения файловой системы, наложенные друг на друга

> **Аналогия:** образ — это как класс в программировании, а контейнер — экземпляр этого класса. Один образ — много контейнеров.

### Образ vs контейнер

| Характеристика | Образ | Контейнер |
|----------------|-------|-----------|
| **Изменяемость** | Неизменяемый | Изменяемый (верхний слой) |
| **Состояние** | Только для чтения | Чтение + запись |
| **Хранение** | `/var/lib/docker/image/` | `/var/lib/docker/containers/` |
| **Слои** | Все слои только для чтения | Нижние — только чтение, верхний — запись |
| **Создание** | `docker build` | `docker run` / `docker create` |

### Из чего состоит образ

```
┌─────────────────────────────────────────┐
│           Метаданные (JSON)              │
│  - Команда запуска (CMD/ENTRYPOINT)     │
│  - Переменные окружения (ENV)           │
│  - Открытые порты (EXPOSE)              │
│  - Тома (VOLUME)                        │
│  - Рабочая директория (WORKDIR)         │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│              Слои (layers)               │
│  ┌───────────────────────────────────┐  │
│  │ Слой 3: COPY app.py /app/         │  │
│  ├───────────────────────────────────┤  │
│  │ Слой 2: RUN pip install flask     │  │
│  ├───────────────────────────────────┤  │
│  │ Слой 1: FROM python:3.12-slim     │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

### Где хранятся образы

```bash
ls /var/lib/docker/
```

**Что происходит:** вывод показывает директории Docker:

```
containers/  image/  network/  overlay2/  volumes/  ...
```

| Директория | Что хранится |
|------------|--------------|
| `image/` | Метаданные образов (JSON) |
| `overlay2/` | Слои образов (файловая система) |
| `containers/` | Метаданные контейнеров |

### Просмотр образа

```bash
docker images
```

**Что происходит:** вывод показывает список локальных образов:

```
REPOSITORY   TAG       IMAGE ID       CREATED       SIZE
ubuntu       22.04     abc123def456   2 weeks ago   77.8MB
nginx        latest    def456abc123   1 week ago    187MB
```

| Колонка | Что означает |
|---------|--------------|
| `REPOSITORY` | Имя образа (например, `ubuntu`) |
| `TAG` | Версия (например, `22.04`, `latest`) |
| `IMAGE ID` | Уникальный идентификатор (SHA256) |
| `CREATED` | Когда образ был создан |
| `SIZE` | Размер образа (сумма всех слоёв) |

### Теги и digest

**Тег** — это человекочитаемая метка версии. Например, `ubuntu:22.04`, `nginx:latest`, `myapp:1.0.0`.

**Digest** — это уникальный хеш образа. Например, `ubuntu@sha256:abc123...`.

```bash
docker pull ubuntu:22.04
docker pull ubuntu@sha256:abc123...
```

**Что происходит:** тег может быть перезаписан (например, `latest` всегда указывает на последнюю версию), а digest — неизменяемый. Для production рекомендуется использовать digest для воспроизводимости.

> **Важно:** тег `latest` — это не «последняя версия», а просто тег по умолчанию. Если вы не указали тег, Docker использует `latest`. Но `latest` может указывать на что угодно — не полагайтесь на него в production.

## 02. Слои образа

### Как работают слои

Каждая инструкция в Dockerfile, которая изменяет файловую систему, создаёт **новый слой**. Слои накладываются друг на друга через OverlayFS (мы разбирали это в разделе 01).

```
┌─────────────────────────────────────────┐
│ Слой 4: CMD ["python", "app.py"]        │  ← метаданные
├─────────────────────────────────────────┤
│ Слой 3: COPY . /app                     │  ← файлы приложения
├─────────────────────────────────────────┤
│ Слой 2: RUN pip install flask           │  ← установленные пакеты
├─────────────────────────────────────────┤
│ Слой 1: FROM python:3.12-slim           │  ← базовый образ
└─────────────────────────────────────────┘
```

### Почему это важно

**Экономия места:** если у вас 10 контейнеров на базе `ubuntu:22.04`, базовый слой хранится один раз. Каждый контейнер добавляет только свой верхний слой.

**Кэширование:** если слой не изменился, Docker не пересобирает его. Это ускоряет сборку.

**Неизменяемость:** слои только для чтения. Это обеспечивает воспроизводимость.

### Просмотр слоёв образа

```bash
docker history ubuntu:22.04
```

**Что происходит:** вывод показывает историю слоёв:

```
IMAGE          CREATED       CREATED BY                                      SIZE
abc123def456   2 weeks ago   /bin/sh -c #(nop) CMD ["bash"]                  0B
def456abc123   2 weeks ago   /bin/sh -c #(nop) ADD file:abc123 in /           77.8MB
```

| Колонка | Что означает |
|---------|--------------|
| `IMAGE` | ID слоя |
| `CREATED BY` | Команда, создавшая слой |
| `SIZE` | Размер слоя |

> **Важно:** слои с размером `0B` — это метаданные (CMD, ENV, WORKDIR). Они не создают новых файлов, но добавляют информацию в конфигурацию образа.

### Как слои связаны с OverlayFS

Когда вы запускаете контейнер, Docker монтирует OverlayFS:

- **lowerdir** — все слои образа (только для чтения)
- **upperdir** — верхний слой контейнера (для записи)
- **merged** — объединённый вид

```
lowerdir: layer1:layer2:layer3
upperdir: container-layer
merged:   /var/lib/docker/overlay2/<id>/merged
```

**Что происходит:** контейнер видит объединённую файловую систему. Когда он пишет файл — изменение попадает в `upperdir`. Когда удаляет — создаётся whiteout в `upperdir`. Нижние слои не меняются.

### Пример: находим слои контейнера на хосте

```bash
docker run -d --name test nginx
docker inspect test | grep -A 10 '"GraphDriver"'
```

**Что происходит:** вывод показывает пути к слоям:

```json
"GraphDriver": {
  "Data": {
    "LowerDir": "/var/lib/docker/overlay2/l/abc123...",
    "MergedDir": "/var/lib/docker/overlay2/def456.../merged",
    "UpperDir": "/var/lib/docker/overlay2/def456.../diff",
    "WorkDir": "/var/lib/docker/overlay2/def456.../work"
  }
}
```

| Путь | Что это |
|------|---------|
| `LowerDir` | Слои образа (только чтение) |
| `UpperDir` | Верхний слой контейнера (запись) |
| `MergedDir` | Объединённый вид (точка монтирования) |
| `WorkDir` | Рабочая директория OverlayFS |

## 03. Dockerfile

### Что это

**Dockerfile** — это текстовый файл с инструкциями по сборке образа. Каждая инструкция создаёт новый слой.

### Структура Dockerfile

```dockerfile
# Комментарий
INSTRUCTION arguments
```

### Основные инструкции

| Инструкция | Что делает |
|------------|------------|
| `FROM` | Базовый образ |
| `RUN` | Выполнить команду при сборке |
| `COPY` | Скопировать файлы из контекста в образ |
| `ADD` | Скопировать файлы (с поддержкой URL и tar) |
| `WORKDIR` | Установить рабочую директорию |
| `ENV` | Установить переменную окружения |
| `ARG` | Аргумент сборки |
| `EXPOSE` | Открыть порт (документация) |
| `VOLUME` | Объявить том |
| `CMD` | Команда по умолчанию |
| `ENTRYPOINT` | Точка входа |
| `USER` | Пользователь для запуска |
| `LABEL` | Метаданные |
| `HEALTHCHECK` | Проверка здоровья |

### Пример: простой Dockerfile

```dockerfile
# Базовый образ
FROM python:3.12-slim

# Рабочая директория
WORKDIR /app

# Копируем зависимости
COPY requirements.txt .

# Устанавливаем зависимости
RUN pip install --no-cache-dir -r requirements.txt

# Копируем код
COPY . .

# Открываем порт
EXPOSE 5000

# Команда запуска
CMD ["python", "app.py"]
```

**Что происходит:** Docker собирает образ по шагам:

1. Скачивает `python:3.12-slim`
2. Создаёт `/app` и делает её рабочей
3. Копирует `requirements.txt`
4. Устанавливает зависимости
5. Копирует остальной код
6. Открывает порт 5000
7. Устанавливает команду запуска

### Сборка образа

```bash
docker build -t myapp:1.0 .
```

**Что происходит:**

- `-t myapp:1.0` — имя и тег образа
- `.` — контекст сборки (текущая директория)

**Что такое контекст сборки:** это директория, файлы из которой доступны для `COPY` и `ADD`. Docker отправляет весь контекст демону. Поэтому важно использовать `.dockerignore`, чтобы не отправлять лишнее.

### .dockerignore

Файл `.dockerignore` работает как `.gitignore` — исключает файлы из контекста сборки.

```
.git
node_modules
*.log
.env
__pycache__
*.pyc
.pytest_cache
```

**Что происходит:** эти файлы не попадут в контекст сборки. Это ускоряет сборку и уменьшает размер образа.

> **Важно:** без `.dockerignore` в образ могут попасть `.git`, `.env`, `node_modules` — всё, что не нужно в production.

## 04. Инструкции Dockerfile подробно

### FROM

```dockerfile
FROM python:3.12-slim
```

**Что делает:** указывает базовый образ. Все последующие инструкции выполняются в контексте этого образа.

**Варианты:**

```dockerfile
FROM ubuntu:22.04
FROM alpine:3.20
FROM scratch  # пустой образ (для статически скомпилированных бинарников)
```

> **Важно:** `FROM scratch` — это пустой образ. Он используется для минимальных образов, где есть только статически скомпилированный бинарник. Например, Go-приложения.

### RUN

```dockerfile
RUN apt-get update && apt-get install -y curl
```

**Что делает:** выполняет команду при сборке. Каждый `RUN` создаёт новый слой.

**Важно:** объединяйте команды в один `RUN`, чтобы уменьшить количество слоёв:

```dockerfile
# Плохо: 3 слоя
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# Хорошо: 1 слой
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
```

**Что происходит:** в первом случае создаётся 3 слоя, и `rm` не уменьшает размер — файлы остаются в предыдущем слое. Во втором случае всё в одном слое, и `rm` реально уменьшает размер.

### COPY vs ADD

```dockerfile
COPY app.py /app/
ADD https://example.com/file.tar.gz /tmp/
ADD file.tar.gz /tmp/
```

| Инструкция | Что делает |
|------------|------------|
| `COPY` | Копирует файлы из контекста |
| `ADD` | Копирует + распаковывает tar + поддерживает URL |

> **Правило:** используйте `COPY`, если не нужна распаковка или URL. `ADD` менее предсказуем.

### WORKDIR

```dockerfile
WORKDIR /app
```

**Что делает:** устанавливает рабочую директорию для последующих инструкций (`RUN`, `CMD`, `ENTRYPOINT`, `COPY`, `ADD`).

**Важно:** `WORKDIR` создаёт директорию, если её нет. Можно использовать несколько раз:

```dockerfile
WORKDIR /app
WORKDIR /app/src  # теперь рабочая директория /app/src
```

### ENV vs ARG

```dockerfile
ENV APP_ENV=production
ARG VERSION=1.0
```

| Инструкция | Когда доступна | Сохраняется в образе |
|------------|----------------|----------------------|
| `ENV` | При сборке и при запуске | Да |
| `ARG` | Только при сборке | Нет |

**Пример:**

```dockerfile
ARG VERSION=1.0
RUN echo "Building version $VERSION"
ENV APP_VERSION=$VERSION
```

```bash
docker build --build-arg VERSION=2.0 -t myapp .
```

**Что происходит:** `ARG` передаётся при сборке, `ENV` сохраняется в образе и доступен при запуске контейнера.

> **Важно:** не используйте `ARG` для секретов — они видны в истории сборки.

### EXPOSE

```dockerfile
EXPOSE 8080
```

**Что делает:** документирует, что контейнер слушает порт 8080. Это **не** открывает порт — для этого нужен `-p` при запуске.

```bash
docker run -p 8080:8080 myapp
```

**Что происходит:** `EXPOSE` — это метаданные. Реальный проброс портов делается при запуске.

### CMD vs ENTRYPOINT

```dockerfile
CMD ["python", "app.py"]
ENTRYPOINT ["python", "app.py"]
```

| Инструкция | Что делает | Переопределяется |
|------------|------------|------------------|
| `CMD` | Команда по умолчанию | Да, аргументами `docker run` |
| `ENTRYPOINT` | Точка входа | Нет, только `--entrypoint` |

**Комбинация:**

```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
```

```bash
docker run myapp          # python app.py
docker run myapp test.py  # python test.py
```

**Что происходит:** `ENTRYPOINT` — это команда, `CMD` — аргументы по умолчанию. Если передать аргументы при запуске, они заменят `CMD`.

**Формы записи:**

```dockerfile
# Exec form (рекомендуется)
CMD ["python", "app.py"]

# Shell form
CMD python app.py
```

> **Важно:** используйте exec form (`["..."]`). Shell form запускает команду через `/bin/sh -c`, что может привести к проблемам с сигналами (SIGTERM не доходит до процесса).

### USER

```dockerfile
USER appuser
```

**Что делает:** устанавливает пользователя для последующих инструкций и для запуска контейнера.

**Пример:**

```dockerfile
RUN useradd -m appuser
USER appuser
CMD ["python", "app.py"]
```

**Что происходит:** контейнер запускается от пользователя `appuser`, а не от root. Это безопаснее.

> **Правило:** всегда запускайте контейнер от непривилегированного пользователя, если это возможно.

### HEALTHCHECK

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
```

**Что делает:** Docker периодически проверяет здоровье контейнера. Если проверка не проходит — контейнер помечается как `unhealthy`.

**Статусы:**

- `starting` — начальный период
- `healthy` — проверка проходит
- `unhealthy` — проверка не проходит

```bash
docker ps
```

**Что происходит:** вывод показывает статус здоровья:

```
CONTAINER ID   IMAGE   STATUS                    PORTS
abc123def456   myapp   Up 5 min (healthy)        0.0.0.0:8080->8080/tcp
```

### LABEL

```dockerfile
LABEL maintainer="dev@example.com"
LABEL version="1.0"
LABEL description="My application"
```

**Что делает:** добавляет метаданные к образу.

```bash
docker inspect myapp | grep -A 5 '"Labels"'
```

**Что происходит:** вывод показывает метаданные.

## 05. Multi-stage build

### Проблема

Обычная сборка включает всё: компиляторы, зависимости для сборки, временные файлы. Это делает образ большим.

```dockerfile
FROM golang:1.22
WORKDIR /app
COPY . .
RUN go build -o myapp .
CMD ["./myapp"]
```

**Что происходит:** образ содержит весь Go-тулчейн (~800 МБ), хотя для запуска нужен только бинарник.

### Решение: multi-stage build

```dockerfile
# Stage 1: сборка
FROM golang:1.22 AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp .

# Stage 2: запуск
FROM alpine:3.20
WORKDIR /app
COPY --from=builder /app/myapp .
CMD ["./myapp"]
```

**Что происходит:**

1. **Stage 1** — собирает бинарник в образе `golang:1.22`
2. **Stage 2** — копирует только бинарник в чистый `alpine:3.20`

**Результат:** образ ~10 МБ вместо ~800 МБ.

### Пример: Python multi-stage

```dockerfile
# Stage 1: сборка зависимостей
FROM python:3.12 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user -r requirements.txt

# Stage 2: запуск
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "app.py"]
```

**Что происходит:** зависимости устанавливаются в builder, затем копируются в финальный образ. Компиляторы и временные файлы не попадают в финальный образ.

### Пример: Node.js multi-stage

```dockerfile
# Stage 1: сборка
FROM node:20 AS builder
WORKDIR /app
COPY package*.json .
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: запуск
FROM node:20-slim
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/index.js"]
```

**Что происходит:** сборка происходит в полном образе Node.js, а запуск — в slim-версии.

### Преимущества multi-stage

| Преимущество | Что даёт |
|--------------|----------|
| **Маленький размер** | Только необходимое в финальном образе |
| **Безопасность** | Меньше инструментов — меньше уязвимостей |
| **Скорость** | Быстрее скачивание и запуск |
| **Чистота** | Нет временных файлов и компиляторов |

## 06. Кэширование слоёв

### Как работает кэш

Docker кэширует каждый слой. Если инструкция и её входные данные не изменились — слой берётся из кэша.

```
Step 1/6 : FROM python:3.12-slim
 ---> abc123def456  (из кэша)

Step 2/6 : WORKDIR /app
 ---> def456abc123  (из кэша)

Step 3/6 : COPY requirements.txt .
 ---> 123abc456def  (из кэша)

Step 4/6 : RUN pip install -r requirements.txt
 ---> 456def123abc  (из кэша)

Step 5/6 : COPY . .
 ---> 789abc123def  (новый слой)

Step 6/6 : CMD ["python", "app.py"]
 ---> 012def345abc  (новый слой)
```

**Что происходит:** если `requirements.txt` не изменился — шаг 4 берётся из кэша. Если изменился только код — пересобираются только шаги 5-6.

### Правило порядка

**Слои, которые меняются реже, должны быть выше.**

```dockerfile
# Плохо: код копируется до установки зависимостей
COPY . .
RUN pip install -r requirements.txt

# Хорошо: зависимости копируются отдельно
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

**Что происходит:** в первом случае любое изменение кода инвалидирует кэш зависимостей. Во втором — зависимости пересобираются только при изменении `requirements.txt`.

### Инвалидация кэша

Кэш инвалидируется, если:

- Изменилась инструкция
- Изменились файлы, которые копируются (`COPY`, `ADD`)
- Изменился базовый образ (`FROM`)
- Изменились `ARG` или `ENV`

### Пример: оптимизация Dockerfile

```dockerfile
FROM python:3.12-slim

# 1. Системные зависимости (меняются редко)
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc && \
    rm -rf /var/lib/apt/lists/*

# 2. Зависимости Python (меняются редко)
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 3. Код (меняется часто)
COPY . .

# 4. Команда запуска
CMD ["python", "app.py"]
```

**Что происходит:** при изменении кода пересобирается только шаг 3. Шаги 1-2 берутся из кэша.

## 07. Best practices

### Безопасность

| Практика | Почему |
|----------|--------|
| **Не запускать от root** | `USER appuser` |
| **Минимальный базовый образ** | `alpine`, `slim`, `distroless` |
| **Не хранить секреты** | Используйте `--secret` или переменные при запуске |
| **Обновлять базовый образ** | Регулярно пересобирать с новым `FROM` |
| **Сканировать уязвимости** | `docker scout`, `trivy` |
| **Multi-stage build** | Меньше инструментов — меньше уязвимостей |

### Размер образа

| Практика | Почему |
|----------|--------|
| **Multi-stage build** | Только необходимое в финальном образе |
| **`.dockerignore`** | Не копировать лишнее |
| **Объединять `RUN`** | Меньше слоёв |
| **Удалять временные файлы** | `rm -rf /var/lib/apt/lists/*` |
| **Использовать `--no-install-recommends`** | Меньше пакетов |
| **`--no-cache-dir` для pip** | Не кэшировать пакеты |

### Воспроизводимость

| Практика | Почему |
|----------|--------|
| **Фиксировать версии** | `python:3.12.1-slim`, а не `python:latest` |
| **Использовать digest** | `ubuntu@sha256:...` |
| **Фиксировать зависимости** | `requirements.txt` с версиями |
| **Не использовать `latest`** | Непредсказуемость |

### Пример: production-ready Dockerfile

```dockerfile
# Stage 1: сборка
FROM python:3.12.1-slim AS builder

WORKDIR /app

# Системные зависимости для сборки
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc && \
    rm -rf /var/lib/apt/lists/*

# Зависимости Python
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# Stage 2: запуск
FROM python:3.12.1-slim

# Метаданные
LABEL maintainer="dev@example.com"
LABEL version="1.0"

# Непривилегированный пользователь
RUN useradd -m -u 1000 appuser

WORKDIR /app

# Копируем зависимости из builder
COPY --from=builder /root/.local /home/appuser/.local
COPY --from=builder /app /app

# Копируем код
COPY --chown=appuser:appuser . .

# Переменные окружения
ENV PATH=/home/appuser/.local/bin:$PATH
ENV PYTHONUNBUFFERED=1
ENV PYTHONDONTWRITEBYTECODE=1

# Пользователь
USER appuser

# Порт
EXPOSE 8080

# Healthcheck
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')" || exit 1

# Команда
CMD ["python", "app.py"]
```

**Что происходит:** этот Dockerfile:

- Использует multi-stage build
- Фиксирует версию Python
- Создаёт непривилегированного пользователя
- Убирает временные файлы
- Добавляет healthcheck
- Использует exec form для CMD

## Итог раздела

Мы разобрали образы и Dockerfile:

| Тема | Что даёт |
|------|----------|
| **Образ** | Неизменяемый шаблон для контейнеров |
| **Слои** | Экономия места и кэширование |
| **Dockerfile** | Описание сборки образа |
| **Инструкции** | `FROM`, `RUN`, `COPY`, `CMD`, `ENTRYPOINT` и другие |
| **Multi-stage build** | Маленькие и безопасные образы |
| **Кэширование** | Ускорение сборки |
| **Best practices** | Безопасность, размер, воспроизводимость |

> **Главный вывод:** образ — это слоёный пирог. Dockerfile — это рецепт. Multi-stage build — это способ испечь только нужное. Кэширование — это способ не переделывать работу.
