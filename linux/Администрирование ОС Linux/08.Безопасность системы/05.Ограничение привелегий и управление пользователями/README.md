# Ограничение привилегий и управление пользователями

> *Комментарий: можно ли соединить группы в sudoers с группами на файловой системе и с чем-то в SELinux, чтобы комплексно ввести ограничение? Например, закрыть и файловый доступ, и доступ командам, и доступ вообще к каким-то действиям?*

Ограничение привилегий – один из ключевых принципов безопасности, позволяющий минимизировать потенциальный ущерб от взлома или ошибки. Вместо предоставления пользователям и процессам полных привилегий система должна использовать разграничение доступа, контроль выполнения команд и изоляцию процессов.

## Принцип наименьших привилегий

**Принцип наименьших привилегий (Least Privilege Principle)** — это фундаментальный принцип безопасности, который заключается в том, что каждый пользователь, процесс или служба должны иметь только те права, которые необходимы для выполнения их задач, и не больше. Зачем это нужно?

- Снижение риска атак – если злоумышленник получит доступ к учётной записи с минимальными привилегиями, он не сможет выполнить критические изменения в системе.
- Ограничение последствий ошибок – даже если пользователь случайно выполнит опасную команду (`rm -rf /`), она не сработает без необходимых прав.
- Защита системных данных – критически важные файлы и конфигурации остаются недоступными для тех, кому они не нужны.
- Повышение управляемости – администратор может легко контролировать, кто и что может делать в системе.

Примеры внедрения этого принципа:

- Пользователи не работают под `root` без необходимости.
- Доступ к конфиденциальным файлам и системным командам разграничивается.
- Используются MAC (Mandatory Access Control) системы (AppArmor, SELinux).
- С помощью таких механизмов контроля доступа как членство в группах, ACL, настройки sudoers, мандатный контроль доступа и аудит, реализуется ролевая модель доступа RBAC, где каждый пользователь получает ту или иную роль, однозначно описывающую его рабочие функции и предоставляющую лишь те привилегии, которые нужны для этой роли.
- Процессы запускаются от отдельных пользователей с минимальными правами.

## Концепция RBAC (Role-Based Access Control) в Linux

**RBAC (Role-Based Access Control, ролевое управление доступом)** – это модель контроля доступа, в которой права пользователей определяются не напрямую, а через их роли. Вместо того чтобы каждому пользователю давать отдельные привилегии, они назначаются ролям, а пользователи получают доступ через эти роли.

Традиционная модель прав в Linux (`chmod`, `sudo`) основана на владельце, группе и всех остальных (`user-group-others`). Однако в сложных системах это становится неудобным и небезопасным, так как пользователям приходится вручную назначать доступ к файлам, сервисам и командам.

RBAC решает несколько проблем:

1. Минимизация прав – пользователи получают только нужные им привилегии.
2. Гибкость управления – изменение доступа делается на уровне ролей, а не отдельных пользователей.
3. Лучший контроль – можно легко отслеживать, какие пользователи обладают определёнными правами.
4. Соответствие требованиям безопасности – RBAC часто используется для соответствия стандартам (PCI DSS, ISO 27001).

## Мандатный контроль доступа (Mandatory Access Control)

**Мандатный контроль доступа (Mandatory Access Control, MAC)** – это модель безопасности, в которой доступ к ресурсам определяется централизованными правилами и политиками, а не владельцами файлов или процессов. В отличие от традиционного дискреционного контроля доступа (DAC), где пользователи, как владельцы, самостоятельно управляют правами, в MAC администратор или система жёстко регулируют, какие процессы, пользователи и службы могут обращаться к определённым объектам.

В классической модели DAC (Discretionary Access Control), используемой в Linux (`chmod`, `chown`, `ACL`), владелец файла сам решает, кому и какие права выдавать. Это удобно, но создаёт серьёзные риски безопасности:

1. **Ошибка конфигурации** – пользователь может случайно выдать права другим пользователям, делая данные доступными для всех.
   - В модели DAC владелец файла может случайно или намеренно раздать слишком широкие права (`777`), делая критически важные данные доступными для всех.
   - В MAC доступ не определяется только правами владельца файла. Даже если администратор поставит `chmod 777`, процесс без соответствующего разрешения всё равно не сможет прочитать или изменить файл.

2. **Компрометация пользователя** – если злоумышленник взломает аккаунт, он получит все права владельца, что позволяет удалять, изменять файлы и запускать вредоносные процессы. В MAC политика безопасности жёстко ограничивает даже привилегированного пользователя:
   - Даже взломанный веб-сервер не сможет читать файлы в `/home`, если политика это запрещает.
   - Даже скомпрометированный пользователь не сможет выполнить `su root`, если не имеет соответствующего уровня безопасности.

3. **Отсутствие контроля над взаимодействием процессов** – в DAC процессы, запущенные пользователем, наследуют его права, даже если они не должны иметь доступ к определённым данным.
   - Если один процесс скомпрометирован, он может взаимодействовать с любыми файлами и процессами того же пользователя.
   - В MAC каждый процесс имеет отдельный контекст безопасности, и взаимодействие между процессами жёстко ограничено.

В MAC доступ определяется централизованной политикой или их набором, а не волей владельца. Основные отличия от DAC:

- Жёсткие ограничения, заданные администратором – пользователи не могут самостоятельно менять правила доступа.
- Контроль доступа между процессами и файлами – предотвращает ситуации, когда один скомпрометированный процесс может получить доступ к чувствительным данным.
- Ограничение привилегий `root` – даже root в MAC-системах не обладает абсолютной властью, если политика запрещает определенные действия. Максимум его возможностей - отдать команду на отключение этого механизма защиты. Однако это вступит в силу только после перезагрузки сервера.

MAC был разработан для высокозащищённых систем, где важно жёсткое разграничение доступа и предотвращение эскалации привилегий. Изначально эта модель применялась в:

- Военных и правительственных системах – где есть строгая иерархия секретности.
- Критической инфраструктуре – банковские системы, управление промышленными объектами, где компрометация одной службы не должна затронуть другие.
- Многопользовательских средах – облачные сервисы и серверные системы, где важно, чтобы пользователи не могли случайно или намеренно вмешиваться в работу друг друга.

### Реализации MAC в Linux

**SELinux (Security-Enhanced Linux)** была разработана NSA и представлена в 2000-х годах как часть ядра Linux. Она использует контексты безопасности (`labels`), жестко контролируя взаимодействие между процессами, файлами и пользователями. Эти контексты состоят из нескольких компонентов, таких как тип объекта, его роль и уровень доверенности. Вместо традиционных прав доступа в Linux (`chmod`, `chown`), SELinux определяет, какие процессы могут взаимодействовать с какими файлами и сервисами, независимо от владельца. SELinux обеспечивает детализированное разграничение доступа, но сложна в настройке, что делает её предпочтительной для **корпоративных и государственных систем**, где важна строгая изоляция процессов.

**AppArmor** появился в Ubuntu и SUSE как более простая альтернатива SELinux. Вместо меток он использует **профили безопасности**, которые применяются к конкретным программам и ограничивают их доступ к файлам, сетевым соединениям и системным ресурсам. В отличие от SELinux, который требует явного назначения контекстов, AppArmor использует файловые пути для определения ограничений. Такой метод проще в настройке, но менее детализирован, чем SELinux. AppArmor часто используется в Ubuntu и Debian, где упор делается на удобство администрирования, тогда как SELinux чаще встречается в CentOS, RHEL и Fedora, где критична строгая изоляция процессов.

**SMACK (Simplified Mandatory Access Control Kernel)** разработан Intel для встроенных и IoT-устройств. В отличие от SELinux, он проще и использует **фиксированные метки**, что делает его удобным в средах с ограниченными ресурсами. SMACK широко применяется в **автомобильных и мобильных системах**.

**Tomoyo Linux** появился в Японии как экспериментальная система MAC, ориентированная на контроль процессов. В отличие от SELinux, который требует предварительной настройки политик, Tomoyo **сам изучает поведение системы** и предлагает политику на основе наблюдений. Он удобен в средах, где политики безопасности должны адаптироваться к реальным сценариям использования.

Далее будут рассмотрены SELinux и AppArmor как самые распространенные реализации MAC.

## AppArmor

**AppArmor (Application Armor)** — это модуль безопасности ядра Linux, реализующий механизм мандатного контроля доступа (MAC). Он позволяет **ограничить права приложений** с помощью специальных профилей, определяя, к каким ресурсам (файлам, каталогам, сетевым портам и пр.) программа может обращаться. Иными словами, даже если злоумышленнику удастся скомпрометировать приложение, AppArmor не позволит ему выйти за рамки разрешённых действий, что значительно снижает возможный ущерб.

Профили AppArmor могут работать в одном из двух режимов: **enforce** (режим принудительного применения) и **complain** (режим жалоб/режим обучения). В режиме **enforce** AppArmor строго применяет политики из профиля — запрещает любые неразрешенные действия приложения и фиксирует эти попытки в логах. В режиме **complain** AppArmor **не блокирует** действия, выходящие за рамки профиля, но **регистрирует** такие попытки в журнале для анализа. Режим complain упрощает отладку и разработку профилей.

### Проверка состояния и включение AppArmor

Ubuntu Server поставляется с AppArmor **установленным и активным по умолчанию**. Для проверки состояния используется команда:

```bash
sudo aa-status
```

Утилита `aa-status` (она же `apparmor_status`) показывает текущее состояние AppArmor: загружен ли модуль ядра, сколько профилей загружено, сколько из них в enforce-режиме, сколько в complain-режиме, какие процессы защищены и т.д. Пример вывода:

```text
apparmor module is loaded.
29 profiles are loaded.
29 profiles are in enforce mode.
   /snap/snapd/19122/usr/lib/snapd/snap-confine
 ...
0 profiles are in complain mode.
0 profiles are in kill mode.
0 profiles are in unconfined mode.
0 processes have profiles defined.
0 processes are in enforce mode.
0 processes are in complain mode.
0 processes are unconfined but have a profile defined.
0 processes are in mixed mode.
0 processes are in kill mode.
```

### Управление профилями

**Профиль AppArmor** – это набор правил, определяющих, что позволено и что запрещено конкретной программе. Профили хранятся в виде текстовых файлов в директории `/etc/apparmor.d/`. Название профиля обычно отражает путь к приложению.

**Переключение режимов профиля:**

- `aa-complain <путь_к_приложению>` — перевести профиль в режим complain.
- `aa-enforce <путь_к_приложению>` — перевести профиль в режим enforce.

Эти утилиты устанавливаются пакетом **apparmor-utils**.

**Включение/отключение профилей:**

- Отключение профиля: `sudo aa-disable /etc/apparmor.d/usr.sbin.mysqld`
- Включение профиля: `sudo aa-enforce /etc/apparmor.d/usr.sbin.mysqld`

**Перезагрузка профилей:**

```bash
sudo systemctl reload apparmor.service
```

или

```bash
sudo service apparmor reload
```

Для перезагрузки одного профиля:

```bash
sudo apparmor_parser -r /etc/apparmor.d/<имя_профиля>
```

### Анализ логов, отладка и диагностика

Все сообщения от AppArmor ядро отправляет в системный журнал. В Ubuntu используется journald (просмотр через `journalctl`), а также дубляж в `/var/log/syslog`. Просмотр последних сообщений AppArmor:

```bash
sudo journalctl -xe | grep -i apparmor
```

или

```bash
grep -i "apparmor" /var/log/syslog
```

Полезно искать по слову `"DENIED"` (отклонено) — именно так помечаются запрещённые операции.

Пример сообщения об отказе:

```text
apparmor="DENIED" operation="open" profile="/usr/sbin/nginx"
name="/etc/nginx/nginx.conf" pid=1234 comm="nginx" requested_mask="r" 
denied_mask="r" fsuid=0 ouid=0
```

**aa-logprof** — утилита, которая автоматически сканирует журнал AppArmor, находит все события, связанные с нарушениями политик, и интерактивно предлагает разрешить или запретить каждое обнаруженное действие для профиля. Запуск:

```bash
sudo aa-logprof
```

### Автоматическая и ручная настройка профилей

**Автоматическое создание профиля:**

- **aa-autodep**: генерирует минимальный профиль на основе зависимостей приложения. Создает пустой профиль с базовыми настройками и сразу ставит его в complain-режим.
- **aa-genprof**: выполняет пошаговое профилирование приложения. Создает профиль, помещает его в complain-режим, а затем предлагает в интерактивном режиме выполнить приложение и произвести с ним нужные действия.

**Ручная настройка профиля:** профили AppArmor представляют собой текстовые файлы с правилами. Основные моменты синтаксиса:

- Правила доступа к файлам: `/path/to/file flags`, где flags — набор букв: `r` (чтение), `w` (запись), `x` (выполнение), `k` (блокировка файла), `m` (memory map).
- Пример: `/var/www/html/** r` разрешит чтение всех файлов в каталоге и подкаталогах.
- `deny /tmp/secret.txt r` — явный запрет чтения файла.

Профили могут включать готовые наборы правил — **абстракции** из каталога `/etc/apparmor.d/abstractions/`. Например, `#include <abstractions/base>`.

### Глоссарий ключевых директив AppArmor

1. **capability** – Управление привилегиями процессов.
   - `capability sys_tty_config` – изменять параметры терминала.
   - `capability dac_override` – игнорировать стандартные DAC ограничения.
   - `capability setuid / setgid` – изменять UID или GID.

2. **unix** – Контроль межпроцессного взаимодействия через UNIX-сокеты.
   - `unix (receive) type=dgram` – принимать датаграммы.
   - `unix (receive) type=stream` – принимать поточные соединения.

3. **network** – Управление сетевыми возможностями процессов.
   - `network packet` – работа с низкоуровневыми пакетами.
   - `network raw` – доступ к сырым сокетам.
   - `network tcp` – разрешение TCP-соединений.

4. **signal** – Ограничение отправки сигналов.
   - `signal (receive) peer=/usr/sbin/NetworkManager` – принимать сигналы только от NetworkManager.

5. **ptrace** – Управление отладкой процессов.

6. **profile** – Определение профиля безопасности.

7. **include** – Подключение внешних файлов (абстракций).

8. **owner** – Разрешения только для владельца процесса.

9. **attach_disconnected** – Работа с разделёнными пространствами имен.

10. **Pxrm / Uxrm / Ux / Cx** – Политики запуска других программ.

11. **r, w, x, k, m, l** – Разрешения для файлов и директорий.

### Создание и настройка профиля на примере nginx

**Шаг 1: Установка утилит AppArmor**

```bash
sudo apt install apparmor-utils
```

**Шаг 2: Создание базового профиля**

```bash
sudo aa-autodep /usr/sbin/nginx
```

**Шаг 3: Активация профилей для запущенного процесса**

```bash
sudo systemctl restart nginx
```

**Шаг 4: Нагрузка приложения для сбора логов**

```bash
curl -I http://localhost/
curl -I http://localhost/some_page.html
```

**Шаг 5: Анализ логов и обновление профиля**

```bash
sudo aa-logprof
```

**Шаг 6: Переключение профиля в enforce-режим**

```bash
sudo aa-enforce /usr/sbin/nginx
sudo systemctl reload apparmor && sudo systemctl restart nginx
```

**Шаг 7: Отладка при проблемах**

```bash
sudo journalctl -xeu nginx.service
```

### Общие рекомендации по использованию AppArmor

- **Держите AppArmor включённым** — не стоит отключать его без веской причины.
- **Используйте готовые профили** из пакета `apparmor-profiles`.
- **Минимально необходимые права** — разрешайте только то, что действительно нужно.
- **Постепенное внедрение** — сначала режим complain, затем enforce.
- **Мониторинг и реагирование** — регулярно проверяйте логи на `DENIED`.
- **Обновление профилей** — корректируйте профили при обновлении ПО.
- **Используйте abstractions и переменные** для упрощения и гибкости.
- **Документируйте свои профили** комментариями.
- **Используйте AppArmor вместе с другими мерами безопасности**.

## SELinux

**SELinux (Security-Enhanced Linux)** – это механизм безопасности ядра Linux, реализующий мандатный контроль доступа поверх стандартных дискреционных прав. SELinux накладывает дополнительные правила, определяющие, какие процессы к каким ресурсам могут обращаться. Это помогает предотвратить эскалацию привилегий и ограничить ущерб от уязвимостей.

Далее рассматриваются практические аспекты работы с SELinux на Fedora Server.

### Часть первая: Повседневное использование SELinux

#### Статус SELinux и режимы работы

SELinux может работать в двух режимах:

- **Enforcing** – политика применяется, нарушения блокируются.
- **Permissive** – политика не блокирует, а только логирует нарушения.
- **Disabled** – SELinux отключён полностью.

Проверка статуса:

```bash
getenforce
sestatus
```

**Временное переключение режима:**

```bash
setenforce 0  # Permissive
setenforce 1  # Enforcing
```

**Постоянное включение/выключение** — в файле `/etc/selinux/config` параметр `SELINUX=` (enforcing, permissive или disabled). После изменения требуется перезагрузка.

#### SELinux-контексты: метки объектов

Контекст безопасности записывается в формате:

```text
user:role:type:[level]
```

Пример для файла:

```text
-rw-rw-r--. user1 group1 unconfined_u:object_r:user_home_t:s0 file1
```

- `unconfined_u` – SELinux-пользователь
- `object_r` – роль
- `user_home_t` – тип
- `s0` – уровень

**Просмотр контекстов:**

- Для файлов: `ls -Z`
- Для процессов: `ps -eZ`
- Для портов: `semanage port -l`

**Наследование меток:** новый файл наследует тип родительского каталога. При перемещении (mv) файл сохраняет старую метку.

**Перелейблирование (relabel) – восстановление меток:**

- Полный релейблинг: `fixfiles onboot` (создаёт `/.autorelabel`, при загрузке метки пересоздаются)
- Частичный: `restorecon -v /path/to/file`

#### SELinux-параметры (booleans)

Просмотр всех boolean-флагов:

```bash
getsebool -a
```

Включение/выключение:

```bash
setsebool -P httpd_enable_homedirs on
```

### Часть вторая: Отладка и устранение ошибок SELinux

#### Поиск причин: логи SELinux

Основной лог: `/var/log/audit/audit.log` (записи `AVC denied`). Пример:

```text
type=AVC msg=audit(1692612134.123:456): avc:  denied  { name_connect } for  pid=1234 
comm="nginx" dest=8080 scontext=system_u:system_r:httpd_t:s0 
tcontext=system_u:object_r:http_cache_port_t:s0 tclass=tcp_socket
```

**Утилиты для анализа:**

- `ausearch -m AVC -ts recent` – поиск по audit.log
- `journalctl -t setroubleshoot` – сообщения setroubleshoot
- `audit2why` – расшифровка причин отказа

#### Типичные сценарии и их решение

**Сценарий 1: Перенос веб-контента в нестандартный каталог**

Проблема: веб-сервер выдаёт 403 при попытке открыть сайт из `/srv/mywebsite`.

Решение:

```bash
semanage fcontext -a -t httpd_sys_content_t "/srv/mywebsite(/.*)?"
restorecon -R -v /srv/mywebsite
```

Альтернатива с эквивалентностью директорий:

```bash
semanage fcontext -a -e /var/www /srv/mywebsite
restorecon -R /srv/mywebsite
```

**Сценарий 2: Сервис на нестандартном порту**

Проблема: веб-сервер не может слушать порт 9000.

Решение:

```bash
semanage port -a -t http_port_t -p tcp 9000
```

Для MySQL на порту 3307:

```bash
semanage port -a -t mysqld_port_t -p tcp 3307
```

**Сценарий 3: Необходимость дополнительных разрешений (booleans)**

Проблема: веб-сервер должен делать исходящие сетевые соединения.

Решение:

```bash
setsebool -P httpd_can_network_connect on
```

Другие примеры boolean:

- `httpd_enable_homedirs` – разрешить доступ к `~/public_html`
- `virt_use_nfs` – разрешить KVM использовать NFS
- `ftpd_allow_write` – разрешить FTP-запись
- `domain_can_mmap_files` – разрешить mmap файлов

### Часть третья: Разработка собственных политик SELinux

#### Инструменты и исходные файлы политики

Установка пакета разработки политик:

```bash
dnf install selinux-policy-devel
```

**sepolicy generate** – утилита для генерации шаблона модуля политики.

#### Создание политики для своего сервиса (пример Flask)

**Шаг 1: Генерация шаблона**

```bash
sepolicy generate --init -n myflask -p myflask_port_t -t myflask_tmp_t -d myflask_var_run_t "/usr/local/bin/myflask"
```

Если возникает ошибка, можно упростить:

```bash
sepolicy generate --init -n myflask /usr/local/bin/myflask
```

Создаются файлы:

- `myflask.te` – Type Enforcement policy
- `myflask.if` – Interface file
- `myflask.fc` – File context definitions
- `myflask.sh` – Сценарий для установки
- `myflask.md` – man-страница

**Шаг 2: Анализ сгенерированных файлов**

Файл `myflask.te` содержит определения типов и базовые правила. Файл `myflask.fc` содержит сопоставления путей типам.

**Шаг 3: Сборка и установка модуля**

```bash
sh myflask.sh
```

Проверка установки:

```bash
semodule -l | grep myflask
restorecon -v /usr/local/bin/myflask
```

**Шаг 4: Тестирование политики**

```bash
systemctl start myflask
ps -eZ | grep python
```

**Отладка политики:** при необходимости можно сгенерировать недостающие правила из лога:

```bash
ausearch -m AVC -c myflask -ts recent | audit2allow -M myflask_local
semodule -i myflask_local.pp
```

Однако рекомендуется вручную добавлять правила в `myflask.te` и пересобирать модуль.

**Пересборка модуля:**

```bash
make -f /usr/share/selinux/devel/Makefile myflask.pp
semodule -i myflask.pp
```

### Заключение по SELinux

Алгоритм создания собственной политики:

1. Определить, что сервису действительно нужно (файлы, порты, действия).
2. Сгенерировать шаблон с помощью `sepolicy generate`.
3. Скорректировать `*.te` файл, ориентируясь на логи и audit2allow.
4. Установить модуль и протестировать, повторяя шаг 3 при необходимости.
5. Зафиксировать контексты через `semanage fcontext`.
