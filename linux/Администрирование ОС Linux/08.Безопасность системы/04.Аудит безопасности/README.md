# Журналирование и мониторинг событий

Говоря про безопасность, нельзя обойти стороной вопросы журналирования происходящего в системе. Не стоит путать это с процессом логирования. Между журналированием и логированием есть принципиальные отличия.

**Логирование** – это общий процесс записи событий, происходящих в системе, приложениях и сети. Логи могут включать в себя информацию о работе сервисов, ошибках, доступе пользователей, трафике сети и многом другом. Логирование является неотъемлемой частью мониторинга и помогает анализировать поведение системы в режиме реального времени, а также выявлять проблемы.

**Журналирование**, в контексте безопасности, фокусируется на сохранении, контроле и управлении записями о критически важных событиях. Это могут быть попытки аутентификации, изменения конфигураций, работа с привилегиями, доступ к критическим файлам и команды, выполняемые пользователями. Основная цель журналирования – гарантировать целостность и доступность данных о событиях, чтобы можно было проводить аудит, расследование инцидентов и обеспечивать соответствие требованиям безопасности.

В этой лекции рассматривается журналирование с точки зрения безопасности (тема логирования как части мониторинга разбирается в другой лекции).

Основные аспекты, которые здесь рассматриваются:

- Где и как в Linux записываются события, важные с точки зрения безопасности.
- Какие механизмы обеспечивают защиту журналов от модификации.
- Как анализировать и управлять журналами в целях аудита.
- Как настроить автоматическое управление журналами для долгосрочного хранения.

Журналирование – это не просто сбор логов, а управляемый процесс хранения данных, обеспечивающий доказательства действий пользователей и процессов.

## Обзор инструментов журналирования в Linux

В Linux журналирование безопасности обеспечивается несколькими ключевыми системами. Каждая из них отвечает за разные аспекты сбора и хранения данных о событиях, связанных с пользователями, процессами и доступом к системе.

### journalctl и systemd-journald

Современные дистрибутивы Linux используют `systemd-journald` для централизованного сбора журналов системы и сервисов.

- Собирает все системные события, включая логи аутентификации, запуск сервисов, ошибки приложений.
- Работает без ротации файлов, храня данные в бинарном формате.
- Позволяет фильтровать события по пользователям, сервисам, временным интервалам.

Пример просмотра последних 50 записей журнала:

```bash
journalctl -n 50
```

Просмотр только ошибок:

```bash
journalctl -p err
```

Просмотр попыток входа в систему:

```bash
journalctl -u sshd
```

### syslog и rsyslog

Исторически в Linux использовался протокол `syslog` — стандартный протокол журналирования, который появился ещё в 1980-х годах в UNIX-системах. Его основная задача – собирать системные события и записывать их в лог-файлы. Он позволяет:

- Централизованно управлять логами различных сервисов.
- Делить события на разные уровни важности (ошибки, предупреждения, информационные сообщения и т. д.).
- Перенаправлять логи на удалённые серверы, что удобно для масштабных инфраструктур.

В традиционных системах `syslog` записывал события в текстовые файлы в `/var/log/`, например:

- `/var/log/auth.log` – попытки входа в систему.
- `/var/log/syslog` – общий системный журнал.
- `/var/log/kern.log` – сообщения ядра.

Хотя `syslog` долгое время был основным инструментом журналирования, он имел ограничения:

- Не поддерживал фильтрацию и сложные правила маршрутизации логов.
- Не мог эффективно обрабатывать большие объёмы данных.
- Не поддерживал шифрование и сжатие логов при передаче на удалённые серверы.

В начале 2000-х появился `rsyslog` ("Rocket-fast syslog") – расширенный и более мощный вариант `syslog`, который добавил:

- Поддержку TCP и шифрования (TLS) для передачи логов.
- Возможность записывать логи в базы данных (MySQL, PostgreSQL).
- Гибкую фильтрацию и маршрутизацию логов.
- Поддержку структурированных логов (JSON, форматы SIEM-систем).
- Лучшее управление ротацией логов, чем у syslog.

В большинстве современных дистрибутивов syslog больше не используется, а вместо него установлен `rsyslog`, который полностью обратно совместим с `syslog`, но предлагает лучшие возможности.

Пример просмотра последних 50 строк `/var/log/auth.log`:

```bash
tail -n 50 /var/log/auth.log
```

Пример фильтрации логов по ключевому слову:

```bash
grep "FAILED" /var/log/auth.log
```

В современных Linux-системах `systemd-journald` и `rsyslog` работают вместе, потому что выполняют разные задачи. `journald` интегрирован с `systemd`, собирает логи сервисов, ядра и пользователей в бинарном формате, поддерживает структурированные данные и удобен для быстрого анализа через `journalctl`. Однако он не создаёт привычных текстовых логов и не передает данные на удаленные серверы.

`rsyslog`, в свою очередь, сохраняет логи в `/var/log/`, позволяет фильтровать и маршрутизировать их, а также отправлять в SIEM-системы и другие централизованные хранилища. Он поддерживает классический `syslog`, что важно для совместимости с устаревшими системами. В современных дистрибутивах `journald` собирает события, а `rsyslog` дополняет его, записывая их в файлы и передавая дальше. Вместе они обеспечивают полный контроль над логированием и аудитом событий.

### auditd – система аудита безопасности

Если `rsyslog` и `journalctl` собирают общие события системы, то `auditd` – это специализированный инструмент для детального аудита безопасности. `auditd` (Linux Audit Daemon) — это система аудита, которая позволяет отслеживать изменения в файлах, запуск программ, доступ к конфиденциальным данным и другие события безопасности. В отличие от `rsyslog` или `journald`, которые фиксируют общесистемные логи, `auditd` работает на уровне ядра, что делает его полезным для детального контроля и расследования инцидентов.

- Фиксирует изменения конфигураций, доступ к файлам, выполнение команд.
- Позволяет отслеживать, кто и когда изменял системные файлы.
- Логирует доступ к важным ресурсам (`/etc/passwd`, `/etc/sudoers`).
- Используется для выполнения требований безопасности (например, PCI-DSS, CIS).

Пример просмотра логов аудита:

```bash
ausearch -m USER_LOGIN -m USER_AUTH
```

Эта команда выполняет поиск в журнале аудита (`audit.log`) событий, связанных с входом пользователей в систему.

- `ausearch` — утилита для поиска событий в логах auditd.
- `-m USER_LOGIN` — фильтрует только события входа в систему (успешные и неуспешные попытки).
- `-m USER_AUTH` — дополнительно показывает события аутентификации (например, неудачные попытки ввода пароля).

Пример отслеживания изменений в `/etc/passwd`:

```bash
auditctl -w /etc/passwd -p wa -k passwd_changes
```

Эта команда настраивает `auditd` для отслеживания изменений в файле `/etc/passwd`.

- `auditctl` — инструмент для управления правилами аудита.
- `-w /etc/passwd` — указывает, что нужно следить за файлом `/etc/passwd` (он содержит учётные записи пользователей).
- `-p wa` — устанавливает права доступа, которые отслеживаются:
    - `w` (write) — запись или изменение файла.
    - `a` (attribute change) — изменение атрибутов файла (например, chown, chmod).
- `-k passwd_changes` — задаёт метку (key), по которой можно легко искать эти события в логах.

После выполнения команды любые попытки изменения файла `/etc/passwd` будут записываться в логи аудита, и их можно будет найти командой:

```bash
ausearch -k passwd_changes
```

## Настройка auditd для отслеживания критичных событий

В большинстве современных дистрибутивов `auditd` предустановлен. Если его нет, установка:

```bash
sudo apt install -y auditd 
sudo systemctl enable --now auditd
```

Несколько примеров применения.

### 1. Отслеживание изменений в `/etc/passwd` и `/etc/shadow`

Эти файлы содержат информацию о пользователях системы, и любое их изменение должно фиксироваться. Добавление правил:

```bash
sudo auditctl -w /etc/passwd -p wa -k passwd_changes
sudo auditctl -w /etc/shadow -p wa -k shadow_changes
```

Где:

- `auditctl` – команда для управления правилами аудита в `auditd`.
- `-w /etc/passwd` – указывает, что нужно следить за файлом `/etc/passwd`.
- `-w /etc/shadow` – аналогично, но для файла `/etc/shadow`.
- `-p wa` – определяет какие операции отслеживать:
    - `w` (write) – фиксировать все изменения содержимого файла.
    - `a` (attribute change) – фиксировать изменения прав доступа, владельца или других метаданных файла.
- `-k passwd_changes` / `-k shadow_changes` – задаёт ключевое слово (key) для удобного поиска в логах.

После добавления этих правил любое изменение файлов `/etc/passwd` или `/etc/shadow` будет записываться в журнал `/var/log/audit/audit.log`. Для поиска событий:

```bash
ausearch -k passwd_changes
ausearch -k shadow_changes
```

### 2. Контроль запуска критически важных команд

Для отслеживания выполнения команд `usermod` (изменение пользователей) или `chmod` (изменение прав):

```bash
sudo auditctl -a always,exit -F path=/usr/sbin/usermod -F perm=x -k usermod_exec
sudo auditctl -a always,exit -F path=/bin/chmod -F perm=x -k chmod_exec
```

- `-a always,exit` – добавляет правило аудита для всех событий завершения (exit) системного вызова, связанных с этим файлом.
- `-F path=/usr/sbin/usermod` – фильтр, указывающий, что нужно следить за файлом `/usr/sbin/usermod`.
- `-F path=/bin/chmod` – фильтр для `/bin/chmod`.
- `-F perm=x` – указывает, что отслеживается запуск (x – execute) команды.
- `-k usermod_exec` / `-k chmod_exec` – задаёт ключ (key) для поиска событий в логах.

После настройки выполнение команд:

```bash
sudo usermod -aG sudo user1
# или
chmod 777 /etc/passwd
```

будет записано в `/var/log/audit/audit.log`. Просмотр записей:

```bash
ausearch -k usermod_exec
ausearch -k chmod_exec
```

### 3. Мониторинг доступа к конфиденциальным файлам

Отслеживание попыток чтения или изменения конфиденциального файла (например, SSH-ключей):

```bash
sudo auditctl -w /root/.ssh/ -p rwxa -k ssh_keys_access
```

- `-w /root/.ssh/` – указывает путь к директории, за которой нужно следить (все файлы в `/root/.ssh/`).
- `-p rwxa` – определяет отслеживаемые операции:
    - `r` (read) – фиксировать попытки чтения.
    - `w` (write) – фиксировать изменения файлов.
    - `x` (execute) – фиксировать выполнение файлов.
    - `a` (attribute change) – фиксировать изменения прав, владельца.
- `-k ssh_keys_access` – задаёт метку (key) для поиска событий в логах.

После этого `auditd` зафиксирует любые попытки чтения, записи, выполнения или изменения атрибутов в директории `/root/.ssh/`.
