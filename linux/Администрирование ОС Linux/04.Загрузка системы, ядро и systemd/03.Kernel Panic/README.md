# Kernel Panic

Kernel panic — это состояние ядра Linux, когда происходит серьёзная и непредвиденная ошибка, которая делает ядро неспособным продолжать нормальную работу. Это аналог «синего экрана смерти» в операционных системах Windows.

Когда возникает kernel panic, ядро Linux прекращает свою работу и выводит сообщение об ошибке на экране. Это сообщение обычно содержит информацию о причине kernel panic, такую как название ошибки, трассировку стека и другие диагностические данные.

## Причины kernel panic

Причины могут быть различными и включают в себя:

1. **Ошибка в драйвере устройства** — неправильная работа драйвера устройства может привести к kernel panic, особенно если драйвер работает в привилегированном режиме и имеет доступ к ядру.

2. **Ошибка в файловой системе** — некорректные операции с файловой системой, такие как попытка доступа к повреждённому файлу или каталогу, могут вызвать kernel panic.

3. **Недостаток памяти** — избыточное использование памяти или истощение доступной памяти может привести к kernel panic из-за невозможности ядра выполнить необходимые операции.

4. **Ошибка в ядре** — неправильные или повреждённые части кода ядра Linux могут вызвать kernel panic. Это может быть вызвано как программными ошибками, так и аппаратными проблемами.

5. **Проблемы с оборудованием** — ошибки или неисправности в аппаратной части компьютера, такие как дефектная оперативная память или проблемы с жёстким диском, могут привести к kernel panic.

> Когда происходит kernel panic, система приостанавливается, и дальнейшая работа становится невозможной до перезагрузки компьютера. Для определения причины и поиска решения проблемы необходимо проводить анализ журналов системы и сообщений о kernel panic.

## Практика: имитация kernel panic

Для изучения механизмов диагностики kernel panic можно искусственно вызвать сбой системы. Рассмотрим два способа.

### Подготовка

По умолчанию Ubuntu 22.04 поставляется с ядром версии 5.15.0-60-generic. Для работы с отладочными символами потребуется более свежая версия, например, 5.15.0-100-generic из пакета `linux-image-unsigned-5.15.0-100-generic/jammy-updates`:

```bash
# просмотр текущей версии ядра
uname -r

# установка нового ядра
sudo apt install -y linux-image-unsigned-5.15.0-100-generic/jammy-updates

# перезагрузка системы
sudo reboot

# проверка версии после перезагрузки
uname -r
```

### Способ 1 — волшебная кнопка (SysRq)

Вызов сбоя встроенными средствами ядра с использованием механизма SysRq, описанного в [документации ядра](https://docs.kernel.org/admin-guide/sysrq.html):

```bash
sudo -s
echo 1 > /proc/sys/kernel/sysrq
echo c | tee /proc/sysrq-trigger
```

**Что происходит:**
- Первая команда включает поддержку специальных «горячих» клавиш SysRq, которые позволяют мгновенно влиять на работу системы.
- Вторая команда эмулирует нажатие клавиши `c`, которая согласно документации выполняет системный краш (system crash).

Результат выполнения команд — система переходит в состояние kernel panic с соответствующим сообщением на экране.

### Способ 2 — сбойный модуль ядра

Более сложный способ — написание, компиляция и загрузка специального модуля ядра, который вызывает панику.

**Установка инструментов для сборки:**

```bash
sudo apt install -y build-essential make gcc linux-headers-$(uname -r) linux-source flex bison
```

**Создание файла kernelpanic.c:**

```c
#include <linux/kernel.h>
#include <linux/module.h>

MODULE_LICENSE("GPL");

int init_module(void){
    panic("Kernel Panic test");
    return 0;
}
```

**Создание файла Makefile:**

```makefile
obj-m += kernelpanic.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
```

В этом коде используется специальная функция `panic` из библиотеки ядра Linux, которая вызывает kernel panic при выполнении.

**Компиляция модуля:**

```bash
make
```

В результате компиляции в том же каталоге появляется бинарный файл `kernelpanic.ko`.

**Загрузка сбойного модуля:**

```bash
sudo insmod kernelpanic.ko
```

После выполнения этой команды система немедленно переходит в состояние kernel panic.

### Сравнение сообщений о панике

При сравнении сообщений обоих падений видна разница в определении причины:

1. **При использовании SysRq** сообщение указывает, что проблема вызвана обработкой вызова sysrq (`sysrq_trigger`).

2. **При загрузке сбойного модуля** сообщение указывает на попытку загрузить модуль, а также отображается текст паники `"Kernel Panic test"`, переданный в функцию `panic`.

## Сбор и анализ дампов kernel panic

Crashdump — это процесс сохранения состояния операционной системы в момент возникновения критической ошибки, такой как kernel panic, и запись этого состояния в файл для последующего анализа. Crashdump позволяет разработчикам и администраторам анализировать причины сбоев ядра и искать способы их исправления.

В Linux crashdump обычно включает сохранение содержимого оперативной памяти (дамп памяти) и другой отладочной информации о состоянии ядра в момент сбоя: стеки вызовов, состояние процессов, регистры процессора и многое другое.

### Компоненты crashdump в Linux

1. **kdump** — инфраструктура в ядре Linux, позволяющая создавать дампы крашей. Использует второе ядро (mini-kernel) для сохранения содержимого оперативной памяти после критического сбоя и записи его на диск.

2. **Crash utilities** — специальные утилиты (например, `crash`) для анализа дампа краша. Позволяют анализировать содержимое дампа, изучать состояние ядра, стеки вызовов, регистры процессора.

3. **Настройка параметров ядра** — параметры `kernel.panic`, `kernel.sysrq` и другие определяют поведение системы в критических ситуациях.

> Crashdump является важным инструментом для диагностики и решения проблем с ядром Linux. Он позволяет быстро обнаруживать и анализировать критические сбои и предоставляет ценную информацию для исправления проблем и улучшения стабильности системы.

### Настройка kdump в Ubuntu

Для Ubuntu и Debian процесс установки и настройки предельно прост:

```bash
sudo apt install -y linux-crashdump
```

В процессе установки необходимо утвердительно ответить на оба вопроса, после чего перезагрузить хост.

После настройки kdump при возникновении kernel panic система не остаётся в состоянии паники, а перезагружается, а в каталоге `/var/crash` сохраняются дампы:

```bash
ls -l /var/crash
```

Пример вывода:
```
total 80000
-rw-r--r-- 1 root root 40000000 Jan 15 10:30 dump.202401151030
-rw-r--r-- 1 root root    50000 Jan 15 10:30 dmesg.202401151030
```

### Установка отладочных символов

Прочитать текстовый файл `dmesg` можно без дополнительных инструментов. Сам же dump-файл является бинарным, для его разбора требуется утилита `crash` и отладочные символы.

Отладочные символы (debug symbols) представляют собой информацию, добавляемую к исполняемому или объектному файлу программы, которая содержит дополнительные данные о структуре программы: имена функций, переменных, типов данных и другие отладочные метаданные. Эта информация обычно удаляется из исполняемых файлов в процессе компиляции для экономии места, однако она остаётся доступной в отдельных файлах с расширением `.debug`.

В контексте анализа дампов памяти отладочные символы необходимы для корректного отображения стека вызовов и другой информации о программе при анализе дампа с использованием инструментов, таких как `gdb` или `crash`. Без отладочных символов отладчик может предоставлять менее информативный вывод, что затрудняет понимание причин сбоев.

**Установка репозитория с отладочными символами:**

```bash
# установка ключа репозитория
sudo apt install ubuntu-dbgsym-keyring

# добавление репозитория ddebs
echo "deb http://ddebs.ubuntu.com $(lsb_release -cs) main restricted universe multiverse
deb http://ddebs.ubuntu.com $(lsb_release -cs)-updates main restricted universe multiverse
deb http://ddebs.ubuntu.com $(lsb_release -cs)-proposed main restricted universe multiverse" | sudo tee -a /etc/apt/sources.list.d/ddebs.list

# обновление кеша пакетов
sudo apt-get update
```

**Поиск и установка отладочного ядра:**

```bash
# просмотр версии ядра
uname -r

# поиск отладочного (dbgsym) ядра соответствующей версии
apt search dbgsym | grep 5.15.0-100 | grep generic

# установка отладочного ядра (версия должна точно совпадать!)
sudo apt install linux-image-unsigned-5.15.0-100-generic-dbgsym/jammy-updates

# проверка — после установки должен появиться каталог с отладочным ядром
ls -l /usr/lib/debug/boot/
```

Пример вывода:
```
-rw-r--r-- 1 root root 50000000 Jan 10 08:00 vmlinux-5.15.0-100-generic
```

### Анализ дампа с помощью crash

**Вызов kernel panic с включённым kdump:**

```bash
sudo -s
echo 1 > /proc/sys/kernel/sysrq
echo c | tee /proc/sysrq-trigger
```

После автоматической перезагрузки системы можно приступить к анализу дампа:

```bash
# просмотр доступных дампов
ls -l /var/crash

# анализ дампа с помощью crash
sudo crash /usr/lib/debug/boot/vmlinux-5.15.0-100-generic /var/crash/202401151030/dump.202401151030
```

**Результат анализа (способ 1 — SysRq):**

```
PANIC: "Kernel panic - not syncing: sysrq triggered crash"
...
COMMAND: "tee"
```

Утилита `crash` показывает причину сбоя — паника вызвана обработчиком sysrq, а команда, вызвавшая панику, — `tee`.

**Результат анализа (способ 2 — сбойный модуль):**

```
PANIC: "Kernel panic - not syncing: Kernel Panic test"
PID: 8084
COMMAND: "insmod"
```

Здесь причина очевидна — загруженный сбойный модуль, который вызвал панику с текстом "Kernel Panic test", а команда, приведшая к панике, — `insmod`.

В реальных условиях диагностика может быть сложнее, но полученная информация является отправной точкой для расследования причин падения ядра.
