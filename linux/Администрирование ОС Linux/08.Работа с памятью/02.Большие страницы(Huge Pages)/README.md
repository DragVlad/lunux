# Большие страницы (Huge Pages)

По умолчанию размер обычного блока-страницы памяти составляет 4 КБ. Однако эти страницы могут быть и больше. Такая технология называется **huge pages** или «большие страницы».

> Huge Page (HP) — это механизм виртуальной памяти, который позволяет использовать страницы памяти большего размера, чем обычные страницы в операционных системах Linux.

Страницы могут иметь размеры 2 МБ, 4 МБ или 1 ГБ (зависит от архитектуры процессора). Это необходимо потому, что современные системы могут оперировать сотнями гигабайт оперативной памяти. При большом количестве страниц промахи в TLB (Translation Lookaside Buffer) происходят чаще, что ведёт к замедлению системы. Huge Pages решают эту проблему: вместо 4096 байт, требующих одну запись в TLB, одна запись теперь может указывать на 2 МБ.

**Пример эффективности:** если TLB вмещает 512 записей, то без HP можно быстро сопоставлять 4096 байт × 512 = 2 МБ адресного пространства. С HP: 2 МБ × 512 = 1 ГБ. При том же размере кэша TLB можно работать с бóльшим объёмом оперативной памяти без потери производительности.

Однако у этой технологии есть обратная сторона — дополнительные накладные расходы при сбросе данных на диск и проблемы фрагментации памяти при выделении.

Существует 2 технологии больших страниц:
- **Classic huge pages** (классические)
- **Transparent huge pages** (прозрачные)

## Сброс Huge Pages на диск

[Они не сбрасываются на диск](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html)

Ядро автоматически отслеживает частоту использования каждой страницы памяти. При недостатке физической памяти ядро перемещает менее важные (реже используемые) страницы на жёсткий диск.

Это же касается и huge pages, так как ОС не делает разницы между страницами памяти. Однако ядро оперирует страницами, а не отдельными байтами.

**Пример на C-подобном псевдокоде:**

```c
char* mymemory = malloc(2*1024*1024*1024); // Одна Huge page
// Заполнение mymemory данными
// Выполнение других операций, приводящих к подмене страницы
// ...
// Запрос доступа только к первому байту
putchar(mymemory[0]);
```

В этом примере выделяется 2 МБ памяти, после чего запрашивается доступ только к 1 байту. Если страница оказалась выгружена на диск, ядру нужно будет прочитать целых 2 МБ информации с диска только для доступа к одному байту. Для обычных страниц потребовалось бы прочитать всего 4096 байт.

Таким образом, если huge page попадает в swap, выигрыш по сравнению с обычными страницами возможен только при доступе **ко всему объёму данных, хранимых на странице**.

При чтении 2 МБ данных:
- в случае большой страницы — 1 операция чтения
- в случае страниц по 4 КБ — 512 операций чтения

**Вывод:**
- При случайном доступе к различным частям памяти с чтением нескольких килобайт следует использовать **обычные страницы**.
- При последовательном доступе к большой части памяти **huge pages** увеличивают производительность.

## Выделение памяти с Huge Pages

Во время выполнения программы ей динамически выделяется область памяти для хранения данных, созданных в процессе работы. Такая память называется **heap** («куча»).

Из кучи могут быть запрошены небольшие объёмы памяти с помощью функции `malloc()`:

```c
char* test_memory = malloc(30);
```

**Проблема фрагментации:** память может быть выделена на уже используемой странице, но если следующий запрос не влезает в текущую страницу, ему выделяется отдельная страница, а предыдущая остаётся полупустой. При чередовании запросов разного размера число свободных, но неиспользуемых мест растёт, что приводит к перерасходу памяти.

> Эти и подобные примеры называются **фрагментацией памяти**. В случае страниц по 4 КБ это явление также присутствует, но менее ощутимо.

Современные языки программирования (Java, Python, JavaScript) имеют встроенные механизмы — **сборщики мусора** — для управления фрагментацией. Однако каждый запуск сборщика — это дорогая операция, и чем чаще происходит фрагментация, тем чаще запускается сборка мусора.

### Преимущества использования больших страниц

1. **Уменьшение накладных расходов на управление памятью** — требуется меньше обращений к таблицам страниц.
2. **Уменьшение потребления памяти** — снижается объём таблиц страниц и TLB.
3. **Улучшение кэширования** — большие страницы кэшируются эффективнее.

### Недостатки использования больших страниц

1. **Фрагментация памяти** — может увеличиться, что приводит к неэффективному использованию адресного пространства.
2. **Менее оптимальный сброс и подъём страниц с диска**.
3. **Нестандартные размеры страниц** — не все приложения оптимизированы для работы с большими страницами.

## Transparent Huge Pages (THP)

**Классические huge pages:**
- могут явно выделяться при загрузке системы
- приложение явно запрашивает выделение HP
- память выделяется без возможности динамической замены больших страниц на малые или обратно

**Transparent Huge Pages (THP)** — технология, при которой:
- при любой возможности ядро старается использовать большие (2 МБ) страницы, даже без явного запроса
- при выделении памяти создаются большие страницы
- при чтении 4 КБ страницы из области подкачки создаётся большая страница (мелкие страницы объединяются)
- если HP попадают в swap, они могут быть разбиты на более мелкие
- системные вызовы `mlock`, `mprotect` приводят к разделению большой страницы
- специальный поток ядра `khugepaged` в фоне просматривает таблицы страниц и сливает мелкие страницы в крупные

Всё это происходит прозрачно для пользовательских программ. Однако такая техника замедляет работу приложений, особенно тех, что рассчитаны на работу с мелкими страницами.

### Рекомендации по использованию THP

Большинство разработчиков баз данных рекомендуют отключать THP в продакшен-системах:

| Продукт | Рекомендация |
|---------|--------------|
| **MongoDB** | [Рекомендуется отключить](https://www.mongodb.com/docs/manual/tutorial/transparent-huge-pages/) из-за потенциальных проблем с производительностью |
| **Redis** | [Рекомендуется отключить](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/) из-за увеличения задержки |
| **PostgreSQL** | Не имеет официальных рекомендаций, но [поддерживает Huge pages](https://www.postgresql.org/docs/current/kernel-resources.html#LINUX-HUGE-PAGES) для общих буферов |
| **MySQL** | [Поддерживает Huge pages для InnoDB](https://dev.mysql.com/doc/refman/8.0/en/large-page-support.html) без включения THP |
| **Oracle DB** | [Рекомендует отключить](https://docs.oracle.com/en/database/oracle/oracle-database/19/ladbi/disabling-transparent-hugepages.html) из-за задержек выделения памяти |
| **Apache Cassandra** | [Рекомендуется отключать](https://docs.datastax.com/en/cassandra-oss/3.0/cassandra/install/installRecommendSettings.html) из-за проблем с производительностью |
| **Elasticsearch** | Обнаружено [снижение производительности на 7%](https://github.com/elastic/elasticsearch/issues/26551) |
| **JVM-приложения** | Неоднозначные результаты — у некоторых улучшение, у других увеличение пауз при сборке мусора |
| **KVM/QEMU** | Результаты зависят от рабочей нагрузки; для БД рекомендуется отключить |

### Перспективы THP

Хотя THP пока не рекомендуется для продакшен-систем, в будущем эта технология может стать стандартом де-факто для крупных серверных систем. Согласно [статье на LWN](https://lwn.net/Articles/929492/) (апрель 2023 г.), на веб-серверах Meta с объёмом 64 ГБ почти 20% циклов выполнения тратятся на обработку промахов в TLB при использовании «классических» 4-килобайтных страниц. HP перестают быть просто оптимизацией и становятся необходимостью.

Вокруг THP ведётся активная деятельность. Всё больше обсуждений патчей к ядру ([например](https://lwn.net/Articles/817905/)) утверждают, что проблема увеличения задержек из-за дефрагментации становится менее острой.

## Практическая работа с Huge Pages

### Просмотр поддержки HP

Проверка поддержки huge pages в системе:

```bash
cat /proc/meminfo | grep -i hugepages
```

Если видна статистика по HP (даже нулевая), значит поддержка на уровне ядра включена. Размер страниц по умолчанию — 2 МБ.

### Ручное выделение Huge Pages

Создание 100 больших страниц:

```bash
# Проверка текущего состояния
free --mega

# Выделение 100 страниц по 2 МБ
sudo sh -c 'echo 100 > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages'

# Проверка результата
free --mega
cat /proc/meminfo | grep -i hugepages
```

Файл `/sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages` позволяет управлять количеством huge pages размером 2 МБ.

**Результат:**
- Создано 100 страниц по 2 МБ
- Объём доступной памяти уменьшился на 200 МБ
- Объём использованной памяти вырос на 200 МБ
- Показатели буферов, кэшей и общей памяти не изменились

Страницы **резервируются** для последующего использования.

### Настройка параметров ядра

Параметры загрузки ядра для huge pages:

- `default_hugepagesz` — размер huge pages по умолчанию (например, `default_hugepagesz=2M`)
- `hugepagesz` — явное указание размера (например, `hugepagesz=1G`)
- `hugepages` — количество страниц при загрузке (например, `hugepages=64`)

**Настройка через GRUB:**

Редактирование `/etc/default/grub`:

```bash
GRUB_CMDLINE_LINUX="${GRUB_CMDLINE_LINUX_DEFAULT} default_hugepagesz=2MB hugepagesz=2M hugepages=20"
```

Перегенерация конфига GRUB:

```bash
sudo update-grub
```

Проверка применения:

```bash
grep hugepages /boot/grub/grub.cfg
```

Перезагрузка системы:

```bash
sudo reboot
```

Проверка после перезагрузки:

```bash
cat /proc/meminfo | grep -i hugepages
```

### Мониторинг фрагментации памяти

Информация о фрагментации памяти доступна в файле `/sys/kernel/debug/extfrag/extfrag_index`:

```bash
sudo cat /sys/kernel/debug/extfrag/extfrag_index
```

**Интерпретация значений:**
- Чем ближе индекс к 0, тем больше вероятность сбоя при выделении памяти из-за её нехватки
- При приближении к 1000 увеличивается вероятность сбоя из-за чрезмерной фрагментации
- Индекс -1 означает, что сбоя не произойдёт
